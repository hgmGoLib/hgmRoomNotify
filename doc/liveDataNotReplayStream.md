# LiveData 不可靠, 为什么还提供它 —— 它是机会主义快路径, 不是可靠重放流

本文以问答形式回应一个常见误区: "`LiveData` 会合并(coalescing)、又不存历史, 拿它做增量 apply
必然漏步、甚至数据损坏; 既然这么不可靠, 干脆删掉, 让 `hgmRoomNotify` 只当纯变化触发器。"

一句话结论: **不该删。该推理把"机会主义快路径 + ajax 兜底"误当成了"可靠、按序、无空洞的重放流"——
那是两个不同的目标。`LiveData` 从来不是后者; 它是可选的延迟优化, 不用不付代价, 用了就在常见情形省一个
RTT 并避免 ajax 惊群。它的"不可靠"是设计内的, 且背后永远有 ajax 兜底, 因此安全。**

与 [`whyNotifyNotPush.md`](whyNotifyNotPush.md) 的关系: 那篇反驳的是**镜像方向**的误区——"`LiveData`
本身已经可靠传每条消息"(误以为它*可靠*)。本文反驳的是反方向——"`LiveData` 不可靠, 所以无用/该删"。
两个方向同错于一处: **把传输层快路径和可靠性来源混为一谈**。可靠性始终在 DB 的业务 `MsgIndex` + ajax,
不在 `LiveData`。

---

## Q1: 合并(coalescing)会丢中间 diff, 打在缺中间步的 snapshot 上, 不就数据损坏了吗?

不会损坏。需要分两层看。

**事实层**: 合并确实存在, 但只在**客户端**, 且只在业务回调(ajax)处理不过来时发生
(`client_room.go` 的 `pendingEv` 原子指针新值覆盖旧值 + `singleUnd.Do`)。服务端**不合并**
(每连接是字节 FIFO 环, 过载直接断开, 见 [`hotRoomFanout.md`](hotRoomFanout.md))。

**概念层(要害)**: 合并丢掉中间 `LiveData` 不会损坏数据。对接契约规定, `LiveData` 只在
"序号正好接在本地最后一条之后"时才走快路径直接 apply; **一旦跳号(中间被合并掉了)立刻落到 ajax 兜底**,
拉本地最后序号之后的全部, 补齐缺口。

举例: 连发 m1、m2, 回调慢, 合并后只剩带 m2 的事件 → 客户端发现 `MsgIndex(2) != lastIndex(0)+1` →
跳号 → ajax 把 m1、m2 一起补回。**合并只是把一次快路径降级成一次 ajax, 从不牺牲正确性。**

"数据损坏"只在消费方**不做序号空洞检查、盲目把 `LiveData` 当增量直接 apply** 时才发生。
那是误用(反模式), 不是 `LiveData` 的问题, 见 [Q5](#q5-正确的对接契约是什么)。

## Q2: 重连后服务端只有当前状态, 漏掉的 diff 怎么补?

不需要补 diff。服务端确实不存历史、不补发 diff, 但 ajax 给的是**权威全量**
(`WHERE idx > lastLocalIdx`), 不是一条条 diff。

重连 / 服务器重启(`RoomEpoch` 变)统一表现为"`LiveData` 缺失 / 序号跳号", 被同一条 ajax 路径兜住。
这条 ajax 路径同时就是"离线消息 / 历史 / 回放 / 断线补发"的实现, 无需单独编写。

## Q3: 那要在通知层"保留增量"是不是就得重搭一套重放机制, 两头不讨好?

这是在追求一个本库**故意不设**的目标。"可靠、按序、无空洞的增量重放流"(SSE ring buffer +
Last-Event-Id 那套)要求服务端存历史、管 offset、重启重放, 正是 [`whyNotifyNotPush.md`](whyNotifyNotPush.md)
论证过的"把队列塞回连接"的坑。

正解不是"保留增量重放", 而是改用**机会主义快路径 + ajax 兜底**: 同样拿到常见情形的低延迟, 还甩掉了
服务端历史 / 重启重放 / buffer 管理这一整类包袱。所谓"两头不讨好"不成立——因为根本没有"重搭重放"这一头,
那一头是误设目标凭空造出来的。

## Q4: 既然不可靠, 为什么还要提供 `LiveData`? 直接删掉不更干净?

因为它的不可靠是**设计内的、且背后有可靠兜底**, 换来两个实打实的好处:

1. **延迟**: 纯触发器模式下, 每次变化都是 `notify → ajax` 一个 RTT。`LiveData` 快路径让常见情形
   (顺序到达 + ≤1024 字节)在 push 里直接带上数据, **0 额外 RTT**。
2. **抗惊群**: 大量客户端同时收到通知 → 同时 ajax 同一个 server = thundering herd。
   快路径命中时根本不打 ajax, 只有空洞 / 丢弃才回源。

而对不使用它的调用方, 它的成本是 **0**: `LiveData` 是 `RoomEvent_t` 的可选字段, 长度 0 = 不传,
此时 `hgmRoomNotify` 就是个纯变化触发器(配合 `CVersionId` 给"当前状态量")。

**删掉 `LiveData` = 强制所有调用方走 ajax 慢路径**, 平白丢掉上面两个好处, 却换不回任何简化
(它不传时本就不产生任何复杂度)。这是经典的"乐观快路径 + 可靠慢路径"模式。

## Q5: 正确的对接契约是什么?

`LiveData` 是提示, 不是真理来源。消费方必须按下表对接(完整可运行代码见
[`../example/ReliableChat/`](../example/ReliableChat/)):

| 收到 onChange 时 | 动作 |
|---|---|
| `LiveData` 有内容 **且** 序号正好接续本地最后一条 | 快路径: 直接 apply, 0 额外 RTT |
| 其它一切情况(无 `LiveData` / 被丢弃 / 超上限 / 重连 / 重启 / **序号跳号**) | 慢路径: ajax 拉本地最后序号之后的全部 |

**反模式(会真的损坏数据)**: 不看序号、直接把每个 `LiveData` 当增量 append。本库无法、也不应阻止这种写法,
但它把"提示"当成了"真理来源", 后果由调用方承担。序号空洞检查 + ajax 兜底是使用 `LiveData` 的**前提**,
不是可选项。

---

## 总结

`hgmRoomNotify` 默认就是纯变化触发器; `LiveData` 是叠在上面的**可选**延迟优化。它不可靠是有意的,
因为可靠性本就不该由它承担(由 DB `MsgIndex` + ajax 承担)。删掉它只会失去免费的快路径, 换不来任何东西。
误区的根源是想在通知层重建一套"可靠增量重放", 而那正是本库刻意不背的包袱。
