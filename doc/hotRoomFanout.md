# 热房间扇出成本 与 合并缓冲(conflating buffer) —— 分析记录

记录一次讨论的结论。**当前未实现下面说的合并缓冲, 是有意为之**(见末尾「为什么暂不做」)。
本文只是把"问题是什么、能不能自动零延迟解决、为什么先不做"记下来, 遇到实际性能问题再回看。

---

## 起因

`FireChange(roomId)` 时, 服务端要遍历该 room 的在线连接, 逐个 push `roomValue`(`02server.go`)。
于是有人指出: 通知成本 ≈ 每条变更 × 当前在线订阅者数。对"很多小房间"很好,
对"少数超大热房间"可能变贵, 并据此说"不只是参数问题, 还需要房间级合并策略"。

核对代码后, 这句话要拆成**两个独立的成本**才准确:

- **A. 慢消费者积压**: 某个客户端读得慢, 它那条连接的写缓冲堆了一串同房间的旧帧 ——
  浪费带宽、甚至触发服务端断开它(`pushMsgResult_bufFull` → `setObsCloseReason("writeBufFull")` → 断开)。
- **B. 扇出遍数**: 每次 `FireChange` 都要遍历 `connSet` 给每个在线连接 push 一遍, 成本 ∝ 在线数 × 变更频率。

## 现状: 各层的"只留最新"机制

- **服务端: 没有**"同房间排队合并只留最新"。每连接写缓冲是字节 FIFO 环(`Frame16BipBuf`),
  排的是一帧帧已序列化消息, 同房间不合并。过载策略是**直接断开慢连接**, 客户端重连后重新进房、
  收到当前 `roomValue` —— 最新状态靠**重连**补回来, 不靠服务端合并。
- **客户端: 有**。`onChangeAsync`(`client_room.go`)用 `pendingEv`(原子指针, 新值覆盖旧值)+
  `singleUnd.Do`(排队再跑一次): 业务回调(ajax)处理慢时, 中间事件被合并, 只拿最新 `pendingEv`。
  TS 客户端等价(定时器合并)。

## A 能否零延迟全自动解决? 能 —— 改成"合并缓冲(conflating buffer)"

把每连接的写缓冲从"字节 FIFO 环"换成"**按 room 键、每个 room 一个槽、新值覆盖旧值**"
(外加一个"哪些 room 脏了"的顺序表):

- 写线程**空闲**时, 第一条 `FireChange` 立刻进槽、立刻发 → **零额外延迟**。
- 写线程**正忙**(慢客户端/正在发上一帧)时, 同房间后续 `FireChange` **覆盖那个槽**, 不追加。
  写线程空出来时发的是**最新值**。

被合并掉的只有"本来就因客户端慢而要排队等"的那些帧 —— 合并发生在写线程本就忙、消息本就发不出去的
那段时间里, **免费**。`v3` 出去的时刻不会比 FIFO 晚, 反而更早(跳过 `v1`/`v2`)。
所以对延迟**只会更好或持平, 永不更差**。

**不破坏任何承诺**: README 的「保证与不保证」本就写明"中间状态可能丢失, v1→v2→v3 可能只收到 v3"。
合并缓冲只是把"本就允许丢中间态"实现得更主动更省, 契约不变。

### 关于"客户端没给服务端背压"

没有应用层显式 credit/ack 背压, 这点对。但 **TCP 给了隐式背压**: 客户端读得慢 → 内核 send buffer 满 →
`WriteFrame` 发不动 → 写线程 `writeLoop` 卡住。于是"**这个 room 的槽里还有没发出去的值吗?**"这一个 bit,
**就是该连接对该 room 的背压信号**。合并缓冲靠这个隐式信号驱动, 不需要新增协议。

## B 能否零延迟全自动解决? 不能 —— 这是 push 扇出的物理下限

B 是"N 个在线订阅者每人都得被唤醒一次", **任何实时 push 系统都付这个 O(在线数)**。
要**减少扇出遍数**(热房间 1ms 变 100 次不想推 100 轮), 只有两条路, 都不是零延迟:

- **批一个 tick 窗口再推**(标脏 + 周期 flush)→ 省遍数, 但 tick = 延迟。
- **调用方自己节流 `FireChange`** → 还是延迟, 只是把决定权交给业务(即 [`whyNotifyNotPush.md`](whyNotifyNotPush.md) 里说的"增量合并窗口"参数)。

为什么 B 不能像 A 那样免费合并: A 能免费是因为有"写线程正忙"这段**已存在的等待**可以塞合并进去;
而源头那个扇出循环是**瞬时**的, 没有"正在进行的扇出"可供 conflate, 想少推就只能**主动等**, 延迟由此而来。

缓和: 即便 B 的循环照跑 N 遍, 配合 A 的合并缓冲, 每遍只是"覆盖一个槽"的廉价操作, 昂贵的序列化 +
`WriteFrame` 系统调用只在写线程 drain 时按最新值做一次。B 里真正贵的 I/O 部分被 A 顺带消掉一大块,
剩下不可消除的只有 O(在线数) 的遍历。要再降这个只能**分片**(每节点房间在线数变少, 见
[`multiNodeDistribute.md`](multiNodeDistribute.md))。

## 历史: 第一版就考虑过

本库的前身(早年一个内部的 ws 状态同步服务)里, `room_t` 当年就带 `value string`(房间直接存当前最新值),
慢/重连的客户端读这个最新值即可。"只关注最新状态、不管历史"从第一版就内建了。
这次讨论等于绕一圈回到同一个点。

## 结论

- **A(慢消费者积压)可以零延迟全自动解决**: 把每连接写缓冲改成 conflating(按 room 存最新值),
  靠 TCP 隐式背压驱动, 延迟只降不升, 且不破坏现有契约。比"tick 合并"更优雅(后者会加延迟)。
- **B(扇出遍数)的 O(在线数) 是 push 物理下限**, 减遍数必然要么加延迟(批)要么分片;
  但 B 里真正贵的 I/O 会被 A 顺带解决。
- 所以"完美全自动零延迟"对**整体**不可能(B 卡着), 但对**真正让热房间踢人的那部分(A)是可能的**。

## 为什么暂不做

不实现 A 的合并缓冲, 是因为**它不一定更快, 甚至可能更慢**:

- 现状的字节 FIFO 环, push 就是一次**连续内存 copy**, 极廉价、零额外分配。
- 合并缓冲要按 room 键存槽 —— **map 访问 + 可能的 alloc** 总归比纯 buffer copy 多。
  对绝大多数"房间不热、写线程根本不积压"的常态, 合并缓冲是**净增开销**(为一个几乎不发生的热房间场景,
  给所有连接的每次 push 都加上 map 成本), 很可能把常态性能拖差。
- "map 访问/alloc vs buffer copy 谁快"在本场景没实测过, 不确定。

所以**先不做**, 保持现状(常态最快, 热房间靠"断开 + 重连补最新"兜底, 调用方可自行节流 `FireChange`)。
等遇到真实的热房间性能问题、有真实数据可测时再回来评估。

## 真到那一天, 这三样按这个顺序看(2026-09-10 补)

上面 A / B 那两项之外, 热房间还有三笔账, 都在
[`pushDesignAndReview.md`](pushDesignAndReview.md) 里落了规矩, 这里只记它们的顺序和量级:

1. **扇出循环别待在共用锁里**(手册 §4.1)。这一条和房间热不热无关, **本来就该做** ——
   在全局锁里给一万个人各入一次队, 卡的是**别的房间的进房**。
   办法是收件人名单用 `atomic.Pointer[[]*Conn_t]` + copy-on-write, 扇出 `Load` 一次在锁外遍历。
   代价是进 / 退房时锁内一次 O(在线数) 的复制 —— 帧比进房多几个数量级, 这笔划算。
2. **`permessage-deflate` 保留上下文, 在热房间里可能是最大的一项**(手册 §9.1 / 理由篇 R12.5)。
   保留上下文 = 压缩状态**每条连接各一份**(gorilla/flate 几百 KB), 而且**压缩结果没法共享**:
   序列化 O(1) 次, **压缩 O(在线数) 次**。
   所以它的定位是"默认开, 热房间要能关" —— 它买的是带宽(第 4 优先级),
   而这里顶的是并发(第 3 优先级), 冲突时关掉它, **不影响任何正确性**。
3. **名单再大就切片**(分成 N 份各自 CoW), 或者按 [`multiNodeDistribute.md`](multiNodeDistribute.md) 分节点。
   这一步才是"O(在线数) 的物理下限"真正被动的地方, 前两条都还没到那儿。

> 顺序不能反: 1 是纠正一个 bug 形状, 2 是关一个开关, 3 才是改结构。
> 先做 3 等于为一个还没量过的瓶颈改结构。
