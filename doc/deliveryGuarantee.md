# 最终收敛保障: 两个必须做对的事

任何"服务端推一下、客户端刷新状态"的系统(WebSocket 通知、SSE、pg `LISTEN`/`NOTIFY`、
自己撸的长轮询…)都在解决同一个问题, 也都极易在同两个地方翻车:

- **TCP 不可靠**: 连接可能在你毫不知情的情况下变成"死链"。
- **重连丢状态**: 断开期间发生的变更, 重连后拿不回来。

本文说明 hgmRoomNotify 把保障目标定成什么, 以及**任何人自己实现同类系统时, 必须各自做对
的两件正交的事**。照着做, pg notify / 手写 SSE 上反复踩的坑就能一次性绕开。

> **更上层的抽象见 [`pushCorrectness.md`](pushCorrectness.md)**: 那篇把正确性压成三条规则
> (必须存在"全量对齐"这条路 / 必须能触发它 / 通知窗口必须覆盖快照点), 并给出十种真实推送形式
> 在 正确性 / 实时性 / 性能 上的分类分析。**判断"对不对"看那篇, 要落地看本篇** ——
> 本文这 8 条就是那三条规则在 "戳一下 + 拉取" 上的展开。
>
> **本文的清单是传输模型无关的**: 不管你用"戳一下 + 拉取"(本库)还是"直接推内容 + 序号"
> (聊天正文的主流做法), 下面 8 条正确性必须都要满足, 一条都不能省。
> 具体到 web + app 聊天该选哪种模型(六条判据)、以及"推内容 + 序号"那条路的完整协议设计
> 与本清单的逐条落地, 见 [`webChatBestPractice.md`](webChatBestPractice.md)。
> 那篇同时补了本文没覆盖的两条聊天特有项: **上行幂等**(`ClientMsgId` + ack, 本文的保障命题
> 只讲下行)和**补拉必须分页**。
>
> **走"推内容 + 序号"那条路时还要多做两条**, 本文没有、因为它们只在那个形状里存在:
> 每一条降级路径"再来一次"的输入必须严格改变(否则是活锁), 以及每一个"等 X 期间收到的东西
> 不能直接用"的状态都必须有独立于连接的超时和上限(**连接活着 != 房间活着**)。
> 这两条连同性能侧的取舍顺序见 [`pushDesignAndReview.md`](pushDesignAndReview.md)。

## 自查清单(先看这个)

不想看原因的, 直接拿这张表逐条对照即可 —— 不用本库、自己撸 ws / SSE / pg notify 刷状态时。
分两组: **正确性必须**缺一就漏状态 / 不收敛; **建议**不破坏收敛, 但防抖动 / 防风暴 / 省资源。

**正确性必须(缺一就漏状态或不收敛):**

- [ ] 客户端**每次(重)连接**都会重新拉一次当前全量状态(而非只订阅之后的事件)?
- [ ] **订阅"未来变更"先生效、再拉快照** —— 否则两者之间发生的变更会漏(详见下方条件一)?
- [ ] 服务端保存的是**当前状态**(可在重连时全量下发), 不是只往连接里推增量?
      (这里存的是**通知层的版本锚点 + 可选短状态**, 真源仍在业务 DB —— 本库不替业务持久化数据)
- [ ] 有**应用层心跳 + 读超时**主动探活, 不只依赖 socket 的关闭回调?
- [ ] 重连是**无限重试**直到成功(不能失败几次就放弃)?
- [ ] 变更判定能识别**服务器重启**(纪元 / epoch), 不会把重启后的新变更当旧消息忽略?
- [ ] 任何"推送里带的加速数据"缺失 / 不可比 / 跳号时, 都能**回退到全量拉取**?
- [ ] 若存在**通知级联**(上游还有别的 notify 机制), 上面每条对**每一环**都各跑一遍了?

**建议(不破坏收敛, 但防抖动 / 防风暴 / 省资源):**

- [ ] 心跳间隔 `<<` 读超时, 健康连接不会被误判断开?(缺了是误杀健康连接 / 抖动重连, 不漏状态;
      本库自动强制 `心跳*2 <= 读超时`)
- [ ] 重连之间有**最小间隔 / 限流**(最好再加随机抖动)? —— 防 "connect→立刻掉→connect" 的
      flap 把 CPU / 网络打爆, 也防服务器重启时所有客户端惊群同时重连。
- [ ] **客户端和服务端都能"合法中断重连"**(显式终态信号, 不是静默关连接)? —— 服务端能强制
      下线 / 版本门 / 封禁并让客户端**停止重试**(本库 `CloseConn(isTemp=false)` / `Deny`, 带
      `reason`), 客户端也能主动停(本库 `SetIsStopListen(true)`); 且终止**用户可见**(如提示升级),
      不是静默冻结。

十一条里**上面八条是正确性必须**: 只要有一条没做, 就会在"某次换网""某台中间路由器丢包""某次
服务器重启""某段网络抖动"下**悄悄漏状态或不收敛**, 且往往难复现、难定位。**下面三条是建议**:
缺了不会漏状态, 但会让健康连接被误杀 / 抖动、在重启瞬间自我惊群, 或者没法干净地下掉老客户端。
下面解释每条为什么必要。

还有一条是**减法**, 和上面十一条同样重要: **不要在这十一条之外再叠一层"兜底", 尤其不要叠
轮询兜底。** 见下方《不要加兜底: 尤其不要轮询兜底》。

## 保障目标(精确)

> **只要客户端与服务端"最终"都在线、且网络"最终"双向通畅并保持一段足够完成一次收敛的时间
> (此前允许任意长时间的断开、丢包、阻塞、换网、服务器重启), 客户端最终一定收敛到房间的
> 最新状态。**

这是一条**活性(liveness)**命题, 注意它的三个部分:

- **前提**: "最终在线 + 网络最终通畅", 且通畅窗口 **≥ 一次收敛所需时长**(重连 + 重进房 +
  业务回源一个来回)。严格说, 要收敛到**最新**, 这段通畅得延续到"**最后一次变更发生之后**再加
  一次收敛时长"(变更恰好落在收敛过程里的, 靠 live 订阅再补一个来回)。此前中间断多久都行;
  但若网络抖动得比一次收敛还快, 可能一直凑不齐一次完整收敛 —— 那不属于保障覆盖范围。
- **保证**: 最终收敛到**最新**状态。
- **不保证**: 中间经历了几次变更、中间态是什么 —— 会丢失 / 塌缩(v1→v2→v3, 客户端可能只看到
  v3)。

一句话: 它是"**最终收敛到最新值**", **不是**"可靠、按序、无空洞的事件流"。很多人默认拿到的是
后者, 于是漏掉下面两件事。用 pg `NOTIFY` / 手写 SSE 尤其容易默认成后者。

## 两个正交的必要条件

下面两条**各自独立**都是必要条件: **缺任何一条, 都单独把上面的保障打破**。它们不是因果链、
不分先后 —— 是两个不同的洞, 得分别堵上。

- 缺**一**(只探活、不全量对齐): 静默死链能被发现、也能重连, 但重连只"续上往后的流",
  断开窗口内的变更永久丢 → 不收敛。
- 缺**二**(只全量对齐、不探活): 每次重连都能全量对齐, 但静默死链根本不触发重连 →
  对齐永远不会发生 → 状态就此冻住。

所以别去论证"谁依赖谁", 两件事都得做对。

### 必要条件一: 每次(重)连接都做一次"全量重新对齐"

**naive 实现的翻车点**: pg `LISTEN`/`NOTIFY`、手写 SSE 通常是"订阅之后只收到之后发生的
事件"。断开窗口内发生的变更直接丢, **重连后也不会补** —— 客户端状态从此永久偏差、再也不收敛。

严格说, 这一条真正必要的是"**重连后能补回断开窗口内错过的变更**"。理论上"可靠回放断开窗口的
增量"也能满足, 但那等于在通知层重建一套"可靠、按序、无空洞的事件流"(要服务端存历史、管 offset、
重启重放), 正是本保障目标(只收敛到最新、允许中间态塌缩)刻意不背的包袱。所以我们**选全量重新
对齐、放弃回放** —— 这是本目标下最自然、也最省事的实现。

> 补充: 这里写成了二分(重建可靠事件流 / 全量对齐), 实际还有**第三档** —— 服务端存一个**有限**的
> 近期事件内存 buffer, 重连时命中就回放、**满了或太旧就降级到全量对齐**(Discord 的 RESUME →
> INVALID_SESSION 就是这个)。它是**纯优化, 全量兜底始终在**, 所以不背上面那个包袱。
> 本库没做这一档(戳可丢可合并, 回放没意义); 自己实现"推内容 + 序号"型系统时可以考虑,
> 见 [`webChatBestPractice.md`](webChatBestPractice.md) 3.6 节。

**正确机制**: 服务端保存房间的**当前状态**, 客户端每次(重)进房**无条件领一次当前状态**,
并触发一次业务回源(ajax / snapshot / 按业务序号拉)。于是"中间断开任意久"都不要紧 ——
**重连那一刻本身就是一个收敛点**, 把断开窗口里错过的一切一次性对齐回来。

**注意一个藏在本条里的排序洞**: 对"未来变更"的订阅, 必须**先于**快照生效。若做成"先拉快照、
再订阅", 就会出现经典空洞 —— t0 拉到 v3、t0.5 发生 v4(还没订上, 这条通知不送达)、t1 才订阅
生效; 此后若无新变更, 客户端**永远卡在 v3**、不自愈。本库天然没这个洞: re-enter 是先进房
(先订阅), 服务端在那一刻下发当前 seq, 之后任何变更都会 `onChange` → 回源。自己实现时务必
**先订阅、再取快照**。

**本库对应**: re-enter 时服务端下发当前 `ChangeSeq` / `RoomEpoch` / `CVersionId`;
客户端 `onRoomValue` 用 `(RoomEpoch, ChangeSeq)` 判定是否有新变化, `RoomEpoch` 变化
(房间重建 / 服务器重启导致 `ChangeSeq` 归零)时**无条件**接受并触发一次 `onChange`。

### 必要条件二: 独立主动探活, 不假设"TCP 没报错 = 连接正常"

**真实会遇到的故障(这才是关键)**:

- **中间路由器 / 中间盒把包全部丢弃**;
- **客户端自己换了 IP**(wifi↔蜂窝切换、NAT 重绑定、休眠唤醒…)。

这两种情况下, **对 TCP 的 API 来说连接仍然是 ESTABLISHED, 不产生任何 error、不产生任何
关闭事件**, 但双向数据再也不通。这就是"**静默死链**": 看着活的, 实际已死。

**naive 实现的翻车点**: 只依赖 socket 的关闭 / 错误回调来判断"是否还在线"。静默死链下这些
回调永远不来 → 客户端永不重连 → **必要条件一的收敛点永不触发** → 状态就此冻住, 永不收敛。

**注意, 探活不是为了覆盖所有断开**: 正常的 TCP RST、对端进程退出、服务器重启, 都会正常报错 /
触发关闭事件, 客户端"免费"就能感知并重连。探活专门补的是上面那种 **TCP 不会主动告诉你**的
静默死链。

**正确机制**: 应用层**主动心跳 + 读超时** —— 客户端空闲时主动发 ping, 只要在 readTimeout
内没读到**任何**下行(连 ping 的回声都没有), 就主动关闭连接走重连。强制 `心跳间隔 << 读超时`,
保证健康连接不被误杀。算法、参数与测试见 [`pingTime.md`](pingTime.md)。

**本库对应**: `client.go` 的 `timerClientLastReadToReconnect`(读超时→关连接→重连) +
keepalive ping 调度; 服务端有对偶的读超时。默认心跳 4.5s、读超时 10s。

## 通知级联: 短板决定整条链, hgmRoomNotify 补不回上游丢的

现实里 hgmRoomNotify 常常不是"第一环", 它上游还接着别的通知机制。最典型的:
**数据变更 → pg `NOTIFY` → 服务端收到后 `FireChange` → hgmRoomNotify 推给浏览器**。

这时要害是: **保障不会自动跨环节继承。整条链能不能最终收敛, 等于"每一环都各自满足上面两个
必要条件"的逻辑与(AND) —— 任何一环漏了, 下游做得再对也补不回来。**

原因很直接: **下游的"全量回源"只能回到"它取数的那个源当前呈现的状态"**。这里有个前提要说破 ——
**全量对齐必须读上游的真源, 而不是"被通知增量喂养的本地缓存"**。

- 若服务端每次回源都直接读**真源**(如 DB), 那么单次丢 `NOTIFY` 不会永久跑偏: 下一次成功送达
  的通知会触发一次回源, 把真源的最新值拉回来。永久卡住只发生在"**此后再无通知、且 (重)`LISTEN`
  后不主动全量扫**"(那正是 pg 那一环的条件一没做)。
- 若服务端回源读的是"被 `NOTIFY` 增量更新、丢一条就永久错位的本地缓存", 则浏览器无论怎么重连、
  怎么回源, 都会**忠实地收敛到那个错误旧值** —— 它拉的就是那个没被更新的缓存。

两种情形的结论一样: **hgmRoomNotify 这一环健康, 也救不了上游那一环的洞**。

而 pg `LISTEN`/`NOTIFY` 默认**两个必要条件都不满足**(某项目实际踩的就是这个):

- **条件一(全量对齐)没做**: `NOTIFY` 是纯 fire-and-forget, 不存当前状态; 监听方断开 / 重连
  空档期内发出的 `NOTIFY` 全部丢失, 重连后不会补。**必须在每次(重)`LISTEN` 之后主动全量扫一遍
  真源做对齐**, 否则监听端状态永久偏差。很多接法漏了这一步。
- **条件二(探活)没做**: 到 pg 的那条 TCP 连接同样会因中间盒丢包 / 换 IP 变成**静默死链**,
  libpq 不会告诉你"`LISTEN` 已经收不到通知了"。**需要自己给这条连接加心跳 / 读超时**(或周期性
  兜底全量扫描), 否则监听端会"以为自己还在听, 其实早聋了"。

所以级联时的规矩:

- **逐环自检**: 把本文的两个必要条件 + 顶部清单, 对**每一环**各跑一遍(pg→服务端一环,
  服务端→浏览器一环), 不能只检查 hgmRoomNotify 这一环。
- **短板即全局**: 只要有一环漏, 整条链就在"某次换网 / 某次重启 / 某段抖动"下悄悄漏状态,
  且现象往往表现在最下游(浏览器状态不对), 却根源在上游, 极难定位。
- **别指望下游兜底上游**: hgmRoomNotify 能保证"服务端相信什么, 浏览器最终就收敛到什么";
  它**不能**保证"服务端相信的就是对的" —— 那是上游那一环自己的条件一 + 条件二的责任。

## 不要加兜底: 尤其不要轮询兜底

前面把该做对的事列完了, 这一节讲**不该做的事**。最常见的一个念头是:

> "主线(推送 + 重连全量对齐)已经按上面做了, 但万一它有没预料到的 bug 呢? 再叠一层
> 30 秒轮询兜一下吧, 反正也不贵。"

**不建议。** 这个念头看着稳妥, 实际是拿"复杂度 + 一条平时不跑的代码路径"去换一个
**你自己都不知道有没有生效的**保险。请把这份精力原样投到主线上: **主线做对 + 主线测透**,
比任何兜底都靠谱。

> 同一结论的抽象版见 [`pushCorrectness.md`](pushCorrectness.md) 第三部分(那里从三条规则的
> 角度论证)。本节讲的是落地视角: 代价具体贵在哪、以及"该做什么代替它"。

### 为什么不要

1. **它和正确性无关, 只会掩盖问题。** 上面八条做到了, 兜底层永远救不到什么(它永远跑在
   "已经收敛完了"之后); 上面八条没做到, 兜底层做的是**掩盖**: 症状从"永久卡在旧值"变成
   "慢 30 秒自愈"。而"永久卡死"是必现的、能被测试和用户报出来的; "慢 30 秒偶发"是查不动的。
   **你花力气把一个可定位的 bug 改造成了一个不可定位的 bug。**

2. **平时不跑、出事才跑的代码, 几乎必然是错的。** 兜底路径按定义只在低概率场景触发, 于是
   开发期跑不到、测试也难构造, 而"没被执行过的代码一次写对"的概率极低。它第一次真正执行的
   时刻, 恰好是线上出故障、你最没有余量 debug 的时刻。

3. **路径组合爆炸, 难以测试。** 加一条兜底不是加 1 条路径, 是加一组: 兜底单独触发 / 兜底与
   主线同时触发 / 兜底跑到一半主线恢复 / 主线跑到一半兜底插进来。这些组合里**两条路径并发写
   同一份本地状态**, 重复 apply、旧值覆盖新值、序号游标回退这类 bug 全长在这里 ——
   而且全是开发时想不到、线上才第一次跑到的那种。

4. **它会反过来侵蚀主线。** 有了"反正有轮询兜着"这个心理许可, 上面八条就会一条条松掉:
   探活懒得做了、订阅与快照的先后懒得较真了、`RoomEpoch` 懒得处理了。设计实际退化成
   "轮询 + 一个不可靠的加速通道", 但没人会把这句话写进设计文档, 于是这个退化是无声的。
   **注意这不是"退化成纯轮询"那么无害** —— 纯轮询本身是自洽且正确的(每轮就是一次全量对齐,
   见 `pushCorrectness.md` 形式 1); 你得到的是"两个都没做对"的混合体。

5. **轮询兜底的成本是常态的, 收益是概率的。** 99.99% 的轮询是空转, 却要按 客户端数 × 房间数
   持续压真源(DB), 参数还两头堵: 间隔短 → 打爆自己的 DB / 服务端(房间热的时候尤其, 见
   [`hotRoomFanout.md`](hotRoomFanout.md)); 间隔长 → 真出事时用户照样看几十秒陈旧状态, 兜了
   等于没兜。**为 0.01% 的场景付 100% 的开销**, 而且这笔开销会在业务量涨上来时第一个被拿掉 ——
   于是兜底在你最需要它的那天正好被关掉了。

### 什么样的"兜底"是可以加的

判据只有一条: **它是不是主线的一部分、是不是被测试过、是不是每天都在跑。** 满足下面全部
三点才加:

1. **它是降级回主线已有路径, 而不是新写一条平行实现。** 例如下方《一并要做对的细节》第 2 条的
   "加速字段不可比 / 跳号 / 纪元变 → 回退全量回源" —— 走的还是主线那条回源代码, 没有新增
   路径, 这属于**必要条件一本身**, 必须有、必须测。再如 Discord 的 `RESUME` 失败 →
   `INVALID_SESSION` → 全量, 同理。**被否掉的是"在一个已经正确的设计之上再叠一层冗余"。**
2. **有能主动触发它的自动测试。** 测试里必须有手段强制走这条路径(改本地游标成远古值、
   防火墙静默丢包、强制清空加速字段…)。没有触发手段 = 这条路径永远没被执行过 = 见上面第 2 条。
3. **触发时可观测。** 兜底被触发要打日志 / 打指标计数。**如果兜底触发率不为零而你不知道,
   那就等于主线有 bug 而你被自己蒙住了。** 兜底的触发计数应当被当成主线的告警项, 而不是
   "反正兜住了就没事"。

另有一种情况**看着像兜底、其实是主线**: 上游那一环你改不动(典型如 pg `LISTEN`/`NOTIFY`),
只能靠"每次 (重)`LISTEN` 后 + 周期性全量扫真源"来满足那一环的必要条件一 / 二。这时全量扫**就是
那一环唯一的收敛机制**, 是主线, 必须测; 它不是"额外加的保险"。

### 应该拿这份精力去做什么

与其写兜底, 不如把同样的时间花在下面三件事上 —— 它们直接提高主线正确性, 而且**每一项都是
能跑、能重复、出问题当天就报警的**:

1. **给主线的异常路径补自动测试。** 主线的正常路径谁都会测, 出事的从来是异常路径。至少覆盖:
   断网重连 / 静默丢包的半开连接(不发 RST) / 服务器重启导致 `ChangeSeq` 归零 + `RoomEpoch`
   变化 / 客户端换 IP / 先订阅后快照的时序洞(在两个动作之间人为插一次变更, 断言最终收敛) /
   加速字段为空或跳号 / 通知重复与乱序 / 同一用户多标签页多设备。这些**恰恰就是你想用兜底
   盖住的那些场景** —— 测一遍比盖一层划算得多。
2. **真机自动测试, 不要 mock。** 真实服务端 + 真实客户端 + 真实网络故障注入(防火墙丢包、
   拔网线、重启进程)。mock 出来的"断开"只会走到你已经想到的那条分支, 而 bug 长在你没想到的
   分支上。
3. **让重连变便宜, 并且让收敛点可观测。** 出问题就干净地断开 → 重连 → 走必要条件一, 这条
   路径**每天都在跑**, 有问题当天暴露; 再把重连原因、收敛耗时、回源次数打成日志 / 指标,
   出事能定位。这两样加起来, 比一条平时不跑的兜底路径可靠一个数量级。

统一的验收断言(与实现无关): **停止一切变更, 等 N 秒, 断言每个客户端的本地状态 == 服务端
权威状态**(N 取 心跳间隔 + 读超时 + 重连最大间隔 之和再留余量)。故障注入清单与测法见
[`pushCorrectness.md`](pushCorrectness.md) 第四部分。

**一句话**: 兜底解决不了正确性问题, 只会把"必现的 bug"换成"低概率、难测、难查的 bug",
然后在正式上线后挑最糟的时刻发作。正确性只能靠主线做对 + 主线测透来拿。

## 一并要做对的细节(否则前两条打折)

1. **变更判定要正确**: 去重锚点用 `(RoomEpoch, ChangeSeq)`, 且必须有 `RoomEpoch` 这类
   "纪元"字段兜服务器重启 —— 重启后 `ChangeSeq` 归零, 没有纪元就会把新变更当成"旧消息"忽略
   而漏掉。

2. **回源是可靠兜底, 加速字段是机会主义优化**: 收到 `onChange` 默认回源拉全量; 只有命中
   加速字段的契约时才跳过回源省一个 RTT —— `CVersionId` 命中契约(**非空 且 可比 且 同
   `RoomEpoch` 且 `<= 本地`)时跳过回源是正确且预期的优化**, 不是偷懒; `LiveData` 序号正好
   接续时直接 apply 同理。**其余一切情况(空 / 不可比 / 纪元变 / 跳号 / 重连 / 重启)一律回源**。
   千万别把"会缺失的加速字段"当成跳过回源的唯一闸门 —— 那会漏掉真实更新。完整契约与两个对称
   误区见 [`accelFieldsNotReliable.md`](accelFieldsNotReliable.md)。

3. **重连必须无限重试直到成功**, 不能失败几次就放弃 —— 否则"最终在线"的前提下仍不收敛。
   本库满足。

   **唯一合法打破"无限重试"的口子: 两端都能主动"合法中断重连"。** 这是对本保障的**有意豁免**,
   不是它的反例, 也不是丢变更的 bug:
   - **服务端主动下掉**(版本门 / 封禁 / 强制下线 / 服务下线): 本库 `CloseConn(isTemp=false, reason)`
     / `CloseConnBySessionId(...)` 发 `Cmd_closeConn` 让客户端**永久停止重连**; `Deny(reason)`
     发 `Cmd_deny`。都带 `reason` 字符串, 可编码"请升级客户端"之类。
   - **客户端主动停**: `SetIsStopListen(true)`(并立即中断正在进行的 reconnect sleep)。
   - **关键: 必须是"显式终态信号", 不能靠"静默关连接"去卡老客户端。** 静默关连接会被客户端当成
     普通临时断 → **无限重试风暴**(既连不上、又砸自己服务端、UX 还一直转圈)。所以"合法中断"
     同时也是**抗惊群 / 资源保护**——让被拒的客户端**停下来**而不是风暴重试。
   - **前向兼容悖论**: 你只能优雅停掉"已经认识这个停止信号"的客户端; 所以"停"的能力要**尽早内建
     进协议**(本库 `Cmd_closeConn` / `Cmd_deny` 即是), 早于 deny 机制的远古客户端没法干净喊停。
   - **必须用户可见**: 终止 = 故意让该客户端不再收敛, app 要显式提示(如"请升级"/"登录已失效"),
     不能静默冻结。本库把"收到 `deny` 却没注册 `OnDenyFn`"直接判定为对接 bug。

4. **重连之间要有最小间隔(资源保护, 非收敛必需)**: 每次重连之间设一个**最小时间间隔**,
   不足就 sleep 到点, 防止 "connect→立刻掉→connect" 的 flap 循环把 CPU / 网络打爆。本库是
   `ClientReconnectMinDur`(默认 5s, 从上次开始连接算起, 不足则可中断地 sleep 补足)。两点注意:
   - 它是**固定下限, 不是指数退避**。好处: 服务器恢复后最坏等 ≈ 一个间隔就能连上, 没有"指数
     退避涨到几分钟、服务器早回来了客户端还傻等"的问题; 代价: 长时间宕机期间保持恒定重试压力
     (不会越退越松)。这是"优先快速恢复"的刻意取舍。
   - **固定间隔 + 无随机抖动时, 服务器重启会让同时掉线的客户端同时重连(惊群), 周期性砸自己的
     服务端。** 客户端多时建议给这个间隔加**随机抖动**(如 5s ± 随机)把重连时刻摊开。本库当前
     是固定间隔、未加抖动。注意: 这是"礼貌 / 抗惊群"层面的问题, 打的是**自己的**服务端, 不构成
     对第三方站点的 DoS(客户端只连自己配置的服务端)。
