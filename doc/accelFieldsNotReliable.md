# LiveData 与 CVersionId: 都是加速字段, 不是可靠字段

`RoomEvent_t` 上有两个可选字段 —— `LiveData` 和 `CVersionId`。它们是**同一类东西**: 机会主义的**加速字段**,
命中就省一次回源(省一个 RTT / 省一次请求), 没命中就回源, 而回源永远安全。**两者都不是可靠传输/可靠版本通道。**

一句话原则: **可靠性永远在那次带校验的全量回源(ajax / snapshot / DB 业务序号), 不在这两个字段。把任何一个
当成"可以据此跳过回源"的可靠依据, 都是同一类错误。** 它们不传时, 本库就是个纯变化触发器, 不付任何代价;
传了就在常见情形加速, 丢了也只是退回纯触发器的慢路径。

两个对称的误区都源于同一处混淆 —— **把传输层快路径当成了可靠性来源**:

- 把 `LiveData` 误当"可靠按序增量重放流"(以为它*可靠*) → 见下 A 节;
- 把 `CVersionId` 误当"可靠单调版本号、`<= 本地` 就能跳过全量"(也以为它*可靠*) → 见下 B 节。

通用对接契约(两个字段一样):

| 收到 onChange 时 | 动作 |
|---|---|
| 加速字段命中(`LiveData` 接续 / `CVersionId` 可比且不更新) | 快路径: 省一次回源 |
| 其它一切(缺失 / 被丢弃 / 超限 / 不可比 / 跳号 / `RoomEpoch` 变 / 重连 / 重启) | 慢路径: 回源拉全量 |

**反模式(会真的出错)**: 不做校验、把加速字段当真理来源直接用 / 据此跳过回源。本库无法也不应阻止这种写法,
但后果由调用方承担。

## A. LiveData —— 机会主义快路径, 不是可靠重放流

常见误区: "`LiveData` 会合并(coalescing)、又不存历史, 拿它做增量 apply 必然漏步甚至数据损坏; 既然这么不可靠,
干脆删掉, 让本库只当纯变化触发器。" 不该删。该推理把"机会主义快路径 + ajax 兜底"误当成了"可靠、按序、无空洞的
重放流"——那是两个不同目标, `LiveData` 从来不是后者。

### A1: 合并(coalescing)会丢中间 diff, 打在缺中间步的 snapshot 上, 不就数据损坏了吗?

不会。**事实层**: 合并确实存在, 但只在**客户端**, 且只在业务回调处理不过来时发生
(`client_room.go` 的 `pendingEv` 原子指针新值覆盖旧值 + `singleUnd.Do`)。服务端**不合并**
(每连接是字节 FIFO 环, 过载直接断开, 见 [`hotRoomFanout.md`](hotRoomFanout.md))。

**概念层(要害)**: 对接契约规定 `LiveData` 只在"序号正好接在本地最后一条之后"时才走快路径直接 apply;
**一旦跳号(中间被合并掉)立刻落到 ajax 兜底**, 拉本地最后序号之后的全部补齐。
例: 连发 m1、m2, 回调慢, 合并后只剩带 m2 的事件 → 客户端发现 `MsgIndex(2) != lastIndex(0)+1` →
跳号 → ajax 把 m1、m2 一起补回。**合并只是把一次快路径降级成一次 ajax, 从不牺牲正确性。**
"数据损坏"只在消费方**不做序号空洞检查、盲目把 `LiveData` 当增量直接 apply**(反模式)时才发生。

### A2: 重连后服务端只有当前状态, 漏掉的 diff 怎么补?

不需要补 diff。服务端确实不存历史, 但 ajax 给的是**权威全量**(`WHERE idx > lastLocalIdx`), 不是一条条 diff。
重连 / 服务器重启(`RoomEpoch` 变)统一表现为"`LiveData` 缺失 / 序号跳号", 被同一条 ajax 路径兜住。
这条 ajax 路径同时就是"离线消息 / 历史 / 回放 / 断线补发"的实现, 无需单独编写。

### A3: 既然不可靠, 为什么不删掉它更干净?

因为它的不可靠是**设计内的、且背后有可靠兜底**, 换来两个实打实的好处, 且对不用它的调用方成本为 0:

1. **延迟**: 纯触发器下每次变化是 `notify → ajax` 一个 RTT; `LiveData` 快路径让常见情形(顺序到达 + ≤1024 字节)
   在 push 里直接带上数据, **0 额外 RTT**。
2. **抗惊群**: 大量客户端同时收到通知就同时 ajax = thundering herd; 快路径命中时根本不打 ajax, 只有空洞/丢弃才回源。

删掉它 = 强制所有调用方走 ajax 慢路径, 平白丢掉上面两个好处, 却换不回任何简化(它不传时本就不产生复杂度)。
这是经典的"乐观快路径 + 可靠慢路径"。可靠"按序无空洞重放流"(SSE ring buffer + Last-Event-Id 那套)要服务端存历史、
管 offset、重启重放, 正是 [`whyNotifyNotPush.md`](whyNotifyNotPush.md) 论证过的"把队列塞回连接"的坑 —— 本库刻意不背。

## B. CVersionId —— 机会主义跳过提示, 不是可靠单调版本号

常见误区(对接策略下发 / 版本号场景): "让 `CVersionId = 全局单调版本号`, 端点 `onChange` 拿到它跟本地比,
`CVersionId <= 本地` → 直接 no-op、**连 snapshot 都不请求**; `> 本地` → 才拉全量。安全上伪造更低/相等顶多让你跳过,
但你本来就 ≥ 那个版本, 跳过无害。" —— 这把 `CVersionId` 误当成了"总是存在、连续、单调、可比"的可靠通道。它不是。

### B1: 它到底有多"不保证总是有" —— 看代码

`CVersionId` 存在房间结构里, 内存、单值、可选。下面四件事都会让 `onChange` 收到一个**空的 / 旧的 / 不可比的**值:

1. **每次 FireChange 无条件覆盖, 没带就清空。** `FireChange` 里是 `room.CVersionId = ev.CVersionId`(`02server.go`),
   不是"取最大"也不是"没传就保留旧值", 而是直接赋值。**只要有一次 `FireChange` 没带, 存的值就被重置成空串。**
   除非你保证*每一次* `FireChange` 都带, 否则它既不连续也不单调; 框架并不强制你每次都带。
2. **服务器重启全丢。** `roomMap` 在内存。重启后房间表为空, 在下次 `FireChange` 回填前该房间 `CVersionId` 是空串(且 `RoomEpoch` 换新)。
3. **首次进房就是空。** 进一个还没被 `FireChange` 过的房间时, 房间按需创建, 下发 `ChangeSeq=0`、`CVersionId=""`(`02server_auth.go`)。
4. **框架不解释它的内容。** 它是 ≤100 字节的 opaque 字符串, 框架既不校验它是数字也不保证单调。"`CVersionId = 全局单调号`"
   完全是 app 层自己的约定, 框架不提供不维护。即使你这样约定, 上面 1/2/3 仍会让它缺失 / 被重置 / 不可比。

另外, 客户端去重锚点是 `(RoomEpoch, ChangeSeq)`, **不是** `CVersionId`(`client_room.go` 的 `onRoomValue`)。
`CVersionId` 只是搭车下发的字段; `RoomEpoch` 变(重建/重启)会无条件触发一次 `onChange`, 此时完全可能带着空 `CVersionId`。

### B2: 为什么"`CVersionId <= 本地` 就跳过"会漏数据

误区方案默认"真实更新一定带着 `> 本地` 的 `CVersionId`"。但由 B1, 一次真实更新完全可能带着**空串**
(生产者那次没带 / 重启后还没回填)或**被重置后的旧值 / 不可比的值**。其"安全性论证"——"伪造相等/更低让你跳过,
但你本来就 ≥ 那个版本, 跳过无害"——只在"真实更新必然 `> 本地`"成立时才对。真实更新可能根本不带可比的 `CVersionId`,
于是"跳过无害"不成立: 你会漏掉一次真正的更新。问题不在攻击者, 在于**把一个会缺失的字段当成跳过的唯一闸门**。

### B3: 正确契约 —— 跳过只是机会主义优化, 全量才是可靠兜底

和 `LiveData` 完全对称。`CVersionId` 命中省一次请求, 没命中就回源, 回源永远是安全默认:

| `onChange` 收到时 | 动作 |
|---|---|
| `CVersionId` 非空 **且** 可比 **且** `RoomEpoch` 没变 **且** `<= 本地` | 跳过这次全量(机会主义去重: 重连回放 / 重复戳) |
| 其它一切(空 / 不可比 / `RoomEpoch` 变了 / `> 本地`) | 拉全量(ajax / snapshot) |

- **任何疑点都回源**: 空、不可比、`RoomEpoch` 变了, 一律当"必须拉全量", 绝不当"`<= 本地` 跳过"。
- **跳过只是省一次冗余请求**(去掉重连回放 / 重复戳的白拉), 不是可靠机制。可靠性永远在那次全量 + 它自带的校验(如签名)。
- **依赖它做去重就别在真实 `FireChange` 上漏带 `CVersionId`** —— 漏带会清空存值(见 B1 第 1 点), 反而让后续都被迫回源。
  要么每次都带, 要么干脆不依赖它跳过、纯靠全量。

完整可运行的"软件更新"对接(ws 推 + check api 回源)演示这套契约, 见
[`../example/SoftwareUpdate/`](../example/SoftwareUpdate/); 可靠聊天(`LiveData` 快路径 + ajax 兜底)见
[`../example/ReliableChat/`](../example/ReliableChat/)。

那个软件更新例子把这条原则推到极致: **正确性保底(启动时 + 周期 check api)完全不依赖 ws, 哪怕 ws 被封也照常拿到更新;
`CVersionId`/ws 事件只是把"发现更新"从"等下个 check 周期"提前到"实时", 命不命中都不影响最终能否更新。**
软件更新坏了代价大, 这种"正确性绝不押在加速字段上"的对接方式尤其值得照搬。

---

## 总结

`LiveData` 和 `CVersionId` 是同一类**加速字段**: 可选、尽力而为、命中省一次回源、没命中就回源。它们的"不可靠"是
设计内的, 因为可靠性本就不该由它们承担(由 DB 业务序号 + ajax/snapshot 全量承担)。删掉 `LiveData` 只会失去免费快路径;
把 `CVersionId` 当唯一跳过闸门会漏掉真实更新。两个误区同根: 想在通知层重建一套"可靠重放/可靠版本", 而那正是本库刻意不背的包袱。
