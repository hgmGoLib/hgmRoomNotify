# 类一 正文流: 字节流追加

> 四类共用的部分(连接 / 进房三步 / 写缓冲 / 参数 / 测试纪律)在
> [`../pushDesignAndReview.md`](../pushDesignAndReview.md); 协议信封在 [`protocol.md`](protocol.md);
> 选型在 [`index.md`](index.md)。

**一句话**: 数据是一条**连续的字节流**, 只在尾部追加, 从不重写中间, 也从不变短。
典型是 AI 流式吐字、工具调用交错输出的正文。

**id 是内生的**: 区间 `(BaseLen, BaseLen + len(Text)]` —— **数据自己的字节长度就是版本号**,
服务端一把锁都不用。

**这一类是四类里最凶的一个。** 它的翻车形状是**静默错位**: 界面上是一段乱码或者少一截,
没有任何报错, 而且 `BaseLen` 一路连续, 没有任何东西会自己纠正它。

## 1. 什么时候选它

选型三问的第一问答"是" + 载体是连续字节流。

**别用类三代替它**: 每次把全文重推一遍是 O(n²)。
**别让它走 `NeedFullReload`**(见第 5 节), 那是无限重拉。

## 2. 帧字段

    段: {Mode: append|full, BaseLen: int, Text: string}
    外层帧带: CallSeq          // 命名空间代号, 一帧里多段正文共用一份
    roomEnter 申报: {CallId, 我手上有多少字节}
    roomEntered 回带: CallSeq  // 客户端从这一帧把代号对齐过来

* **帧里必须同时有区间两端**: `BaseLen`(接在哪) + `Text` 的长度(接完到哪)。
  > 违反后果: 只有一端时, 客户端**只能靠"双方都记得上次到哪"**对齐,
  > 而这份记忆会因为断线/重连/整页重拉而分叉; 分叉后每次追加都接到错位置, 且 id 一路连续,
  > 没有任何东西会纠正它 —— **静默且不可恢复**。
* **别在每段正文里各带一份 `CallSeq`**, 放外层 —— 一帧里多段正文永远属于同一条 call。
  > 违反后果: 每批变更白扔七八十字节, 而一批正文才 24 字节。
* **带 `full` 段的那一帧必须带 `Seq`**, 带 `append` 段的不带。
  这就是[协议篇](protocol.md)那条"只有重放会出错的帧才带 `Seq`"点名的那一格。
  > 为什么: `full` 是整份替换, **不幂等**; 而 `CallSeq` 只判等、判不出新旧,
  > `BaseLen` 又只在同一个命名空间里有意义 —— **能判 `full` 新旧的只有 `Seq`**。
  > 违反后果: 进房重放时(手册 §5.2), 缓冲里一帧旧代号的 `full` 会被当成"该整份换掉"直接应用,
  > **屏幕回退** —— 那时候只剩"下一帧广播会盖回来"这条隔得很远的兜底(第 5 节末尾)。

## 3. 命名空间: 这一类的全部难点

**`CallId` 不是版本号, 是字节空间的命名空间。**
正文会变短的所有情况(一次调用结束 / 换一条调用)它必须跟着变, 变了就走 `full` 整份换。
**这是"只追加"这条前提的唯一守卫。**

四条连着的规矩, 一条都不能少:

1. **每一帧都必须带这个命名空间**, 而且客户端**每一帧都要判它**(第 5 节第 0 条)。
   它不是"只在换的时候带一下"的东西 —— `BaseLen` 只在同一个命名空间内有意义,
   没有它, 一帧属于旧 call 的 `append` 会被硬接到新 call 的正文屁股上。
2. **帧里带的是"代号"(进程内递增的小整数 `CallSeq`), 不是那个二十来字节的 `CallId` 字符串。**
   这是每帧都要判的东西, 带字符串等于每批变更白扔二十字节。两者是同一件事的两个字节版本:
   `CallId` 只出现在 `roomEnter` 申报里(客户端是从全量拉取那条路知道它的, 那条路给不出房间内部的
   代号), 服务端进房时把代号回给客户端, 从此每帧只比代号。
3. **只判等, 不比大小。** 它是命名空间不是版本号, 客户端光看代号分不出"更老"还是"更新"。
4. 客户端"还不知道代号"要有一个表示法(用 0)。刚整页拉过、还没进房时就是这个状态,
   此时**不判命名空间**(判不了), 由随后那次进房把代号对齐过来。

## 4. 服务端: 进房时怎么算这一份

在进房三步的**第三步**(无锁, 有 DB IO):

    类一: **先比命名空间**: 申报的 CallId != 快照的 -> 回 full 整份;
          一样才拿快照正文 vs 申报长度, 只回那一截
    // 应答里回上快照的 CallSeq, 客户端从这一帧把代号对齐过来

* **客户端申报的长度允许超过服务端房间那份**(它可能刚拉过全量, 而房间要等 worker 才前进)。
  这时服务端**一个字都不补**, 由随后那帧广播自带的偏移让客户端自己裁。
* **进房不许为了对齐把房间"拽到现在"**(再读一次库并给全房间推一帧)。只用房间手上那份快照算差值。
* **worker 那边的三笔 O(n) 也要省掉**(手册 §4.3 最后一条): 别每次读全文(读 `substr` 那一截)、
  别拷贝整份正文组装新快照(单写者只追加, 新快照可以是同一块底层数组上更长的 `[]byte`)、
  别拿正文做 `DeepEqual`(比长度就够了)。
  > 这一桶按 token fire, 三笔加起来是**服务端 CPU 的 O(n²)**;
  > 带宽仍然是 O(n), 所以带宽那条断言照样全绿, **抓不到它**。

## 5. 客户端: 怎么应用

**第 0 条: 三条规则之前先判两件事, 顺序不能换。**

    (a) 剔重(**带 Seq 的帧**, 也就是带 full 段的那些): Seq <= 我的
            -> 这一段扔掉, 到此为止(它出自一版不比我新的快照)
    (b) 命名空间(**只判 append 段**): 两边的代号都已知 且 帧的代号 != 我的代号
            -> 重新进房。**不许往下走**(两份根本不是一套字节空间)
        (我的代号 = 0 "还不知道", 判不了, 跳过这一条; 由这次进房把代号对齐过来)

> (b) 的违反后果: 拿旧 call 的 `BaseLen` 和新 call 的长度比大小, 然后把旧 call 的字节接到新 call 后面
> —— **静默错位**, 而且 `BaseLen` 一路连续, 没有任何东西会纠正它。
> 这一条**对每一段 `append` 都必须判**, 不是"换的时候判一下"。
>
> **(b) 为什么只判 `append`**: `append` 是"接在某个位置上", 换了命名空间就**无处可接**, 只能重新进房;
> `full` 是整份替换, 换不换命名空间它都能原地应用, 它唯一缺的是"谁新谁旧" —— 那由 (a) 回答。
> 让 `full` 也进 (b), 换 call 之后的第一帧(整份)就会被判成重新进房, **白绕一圈**。
>
> **(a) 是唯一能判 `full` 新旧的东西**: 代号只判等(第 3 节), 长度跨代号没有可比性 ——
> 所以带 `full` 段的帧必须带 `Seq`(第 2 节), 这就是那个字段唯一的用处。

`append` 模式(过了第 0 条之后):

    我 >= BaseLen + len(Text)   整帧我都有 -> 扔
    BaseLen <= 我               裁掉重叠的一截再接
    我 <  BaseLen               中间缺了   -> 重新进房(带上我现在的长度)

`full` 模式(过了第 0 条 (a) 之后, 所以它一定不比我旧):

    同代号 且 我不比它短           -> 保留我的(防回退)
    换了代号 / 我的代号还是 0      -> 整份换掉(旧 call 的残留不能留在屏幕上), 并把代号对齐过来

* **"同代号且我不比它短"这一格**为什么在 `Seq` 之外还留着: 客户端可能刚整页拉过,
  手上那份比这一版快照还新(第 4 节明确允许), 这时帧的 `Seq` 更大, 但正文更短。
* **"换了代号 -> 整份换掉"这一格现在有 `Seq` 把关了。** 以前没有 ——
  进房重放里一帧旧代号的 `full` 会把新的那份盖回去, 当时是当成"屏幕上闪一下, 是体验不是正确性"
  接受的。**现在第 0 条 (a) 直接把它扔了, 那一下闪也没有了。**
* 应用完之后**把我的代号更新成帧里那个**; 被第 0 条扔掉的段**不更新代号, 也不更新 `Seq`**。
* **按长度的防回退只在同一个代号内成立** —— 代号只判等, 长度跨代号没有可比性。
  **跨代号的防回退全部落在 `Seq` 上**(第 0 条 (a)), 别指望长度。
  > 即使 `Seq` 那道关漏了, 还有一条兜底论证: **手册 §4.3 的"Store 必配广播"+ 同连接 FIFO** ——
  > 让快照前进到新 call 的那一次 `Store` 后面必然紧跟一帧广播, 而这条连接在进房第一步就订阅好了,
  > 所以那一帧必然排在旧帧后面、必然被应用, **最后落地的一定是最新那一帧**(代价是屏幕上闪一下)。
  > **这条兜底不是让你省掉 `Seq` 的理由**: 它隔得很远, 而且
  > **一旦有人在 §4.3 里加了"Store 了但这次不广播"的分支, 它就断了**。

## 6. 这一类的降级路径

| 触发 | 动作 | 再来一次哪里不一样 | 有效? |
| --- | --- | --- | --- |
| `BaseLen` 对不上(中间缺了) | **重新进房**, 带上我现在的长度 | 进房带的是客户端**当前**的基准, 服务端据此重算, 一定接得上 | ✅ |
| **`append` 段的**代号对不上 | **重新进房** | 同上, 而且进房应答会把代号对齐过来 | ✅ |
| **`full` 段的**代号对不上 | **不是降级**: 按 `Seq` 剔重, 该应用就原地整份换掉 | —(它本来就接得上, 整份替换不需要基准) | — |
| **正文本身就长** | **不许 `NeedFullReload`** | 全文多大和重拉过几次**没有任何关系** | ❌ **无限重拉** |

> 最后一行是[协议篇第 5 节推论一](protocol.md#5-needfullreload-唯一用途--有效判据)的落点:
> 类一的"太大"只能靠"申报基准 + 只回差值"解决, 它压根不该走到"太大"这一步,
> 因此**也不属于任何一组降级**。

## 7. 测试: 这一类必须有的场景

* **两个客户端停在正文的不同字节上**, 收同一帧广播 —— 各自裁各自的, 都要对。
* **换命名空间**: 旧 call 跑完接新 call, 断言客户端没把新 call 的字节接到旧 call 屁股上
  (手册验收清单 D25)。
* **重放里的旧代号 `full`**: 撑开进房窗口, 在窗口里换一次 call(于是缓冲里留下一帧旧代号的 `full`,
  而应答里的快照已经是新 call)。断言重放之后**没有回退到旧 call 的正文**,
  而且**没有触发重新进房**(它应该被第 0 条 (a) 的 `Seq` 静静扔掉, 不是绕一圈)。
* **进房窗口的 A 段 / B 段**各压一遍(手册 §8.1): A 段是"广播比快照旧, 必须剔掉",
  B 段是"广播比快照新, 必须重放"。**这一桶单独压一次**, 别和别的桶混在一个场景里 ——
  混在一起时一桶的 id 判错会被另一桶掩盖。
* 每加一个场景**做一次变异验证**: 把对应那条规则改坏, 看场景是不是当场变红。
