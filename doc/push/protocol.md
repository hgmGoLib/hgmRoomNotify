# 协议: 四类共用的那一层

> 事实来源是 [`../pushDesignAndReview.md`](../pushDesignAndReview.md) §3(以及 §3.4)。
> 本篇是它的重排。选型和四类的分工见 [`index.md`](index.md)。

这一层**不按类分叉** —— 四类跑在同一个信封、同一套帧类型、同一个句柄体系上。
按类分叉的字段在各自的类文件里。

## 1. 帧信封: 只放每帧真的会变的东西

**信封预算: <= 64 字节。这是硬断言, 不是目标。**

一帧的信封只允许有: 帧类型 / **房间句柄** / 该桶的 id 字段 / map 头 / ws 帧头。

必须做的三件事:

1. **房间用整数句柄, 不用房间名字符串。** 句柄 = 进程内递增的小整数, 房间销毁重建时换号。
   > 违反后果: `"房间类型:20 位 id"` 这种字符串每帧要 30+ 字节, 而一帧正文才 24 字节。
2. **不要单独的纪元字段(房间级、进程级都不要) —— 句柄一个字段全兼任了**(见第 4 节)。
   房间只在最后一条连接离开时销毁, 所以"客户端还在房里期间号不会变"是**结构性成立**的。
3. **用整数键的二进制编码**(msgpack 整数键或等价物), 不用可读字段名。
   > 违反后果: 可读字段名 164 字节 → 整数键 37 字节。只换二进制不换键只能到 136 字节,
   > **换键才是大头**。

再加两条纪律:

* **别让零值上线。** 计数从 0 起算, 编码器跳过零值 —— 否则那些"戳一下"类的帧会白背一个恒为 0 的 `Seq`。
  守这条的就是上面那 64 字节的硬断言: **加字段之前先看它还剩多少。**
* **只有"重放会出错"的帧才带 `Seq`。** 判据是"重放会不会出错", **不是"带没带状态桶"**。
  幂等的追加帧不带。
  > 违反后果: 用"带没带状态桶"当判据, 会漏掉"同一条 call 的第一截正文也是整份替换"那一格
  > (那一格属于[类一](class1TextStream.md), 不属于类三)。
  >
  > 落到具体的段上就是: **[类三](class3FullPush.md)的段、[类一](class1TextStream.md)的 `full` 段
  > —— 这两种在的帧带 `Seq`**; 类一的 `append` 段、[类二](class2MsgStream.md)的段不带。
  > 客户端的 `Seq` **由所有带 `Seq` 的帧共同推进**(一帧出自一版快照), 跨桶比大小是合法的。

## 2. 帧类型清单(可直接抄)

    // 连接级
    ping / pong
    hello                      // 客户端第一帧, 带协议版本
    deny{Reason}               // 服务端拒绝, Reason 必须让用户看得见

    // 进房
    roomEnter{RoomKey, 客户端申报的基准...}    // 基准: 各类文件里的"申报"那一行
    roomHandle{RoomKey, RoomHandle}            // "这个房间的句柄是几号", 见第 3 节
    roomEntered{RoomHandle, 快照 + 差值 + Seq, NeedFullReload: bool}
    roomLeave{RoomHandle}

    // 推送
    roomChange{RoomHandle, [各桶的段, 每段可缺席], Seq?}

**一帧 `roomChange` 里可以同时带四类的段, 每段可缺席。** 这是"一个房间里混用多类"在协议上的样子:
客户端**逐段用各自的规则判**, 一段判失败不影响另一段(但按各自的规则可能都要求重新进房)。

**清单里没有任何一个"单独发的降级帧", 这是故意的。**

* `NeedFullReload` **不是一帧**, 它是进房应答 `roomEntered` 上的**一个布尔字段**(第 5 节)。
* 没有 `roomResync{RoomHandle}`("我丢过帧, 你重新进房")这种帧 —— **这件事不存在**:
  连接活着的时候不丢帧, 缓冲装不下一律断线(手册 §4.4)。
  > 违反后果: 那一帧"我丢过东西"**自己也在同一个装不下的队列里**。为了让它发得出去要给它单开
  > 一笔预算, 那笔预算的容量算不出来于是要按房间去重, 去重会漏所以客户端又不能按 id 丢它 ——
  > 一条修补链长出四个互相咬合的设计, 而它们服务的是一个"关掉连接"就消失的问题。

## 3. `roomHandle`: 必须有, 而且必须在订阅的那把锁里就排进写队列

`roomChange` 只带整数句柄不带房间名(第 1 节), 而客户端是**按房间**缓冲 pending 广播的 ——
所以它必须在收到第一帧 `roomChange` 之前就知道这个房间的句柄。
`roomEntered` 来得太晚: 进房第一步订阅之后广播就开始发了, 而应答要等第二、三步(手册 §4.2)。

    第一步(锁内): 登记连接进房间 -> **同一把锁里** pushFrame(roomHandle)
    // 于是"roomHandle 一定排在本房间任何一帧 roomChange 之前"由 FIFO 结构性保证

> 违反后果: 客户端收到一个认不出的句柄, 只能整帧扔掉 —— **首次进房窗口内的广播全部静默丢失**。
> (退而求其次的做法是"按连接缓冲所有未知句柄的帧, 拿到应答再按句柄捞出来", 那要多一个
> 连接级的缓冲和它自己的上限 —— 多一个状态, 不如多一帧十几字节。)
>
> 重新进房(应答超时重发等)时**句柄不要清**: 房间只在最后一条连接离开时销毁, 重进一次不换号。
> 清掉反而会让这次应答回来之前的广播全被当成"不认识的号"扔掉。要清的是"我和服务端对齐着"这个标记。
> **断线是另一回事, 那时候必须清**(手册 §5.1)。

## 4. 纪元: 所有 id 的作用域, 它本身不是 id

**只要一级: `RoomHandle`(房间句柄, 房间销毁重建换号)。**

纪元一变, 下面所有的号(字节长度 / 消息 id 链 / `Seq`)全部作废, 客户端无条件重新对齐。

> 违反后果: 没有纪元, 重启后的新变更会被当成旧消息忽略; 或者拿旧句柄下的号去比新句柄下的号, 撞上。
> 有了纪元, "跨重启单调的 id"这个不可能的需求就消失了, "房间不存在期间的变更"也不需要任何补偿逻辑。

**不要再加一个进程级的纪元字段(`ServerEpoch` 之类)。** 句柄一个字段就把进程重启也盖住了:
进程重启必然先断线, 而客户端**断线就清空整张句柄表并对每个房间重新进房**, 重连之后手上的号
全是新进程发的。新进程的发号器从头开始、可能发出和上一代同号的句柄也不要紧 —— 旧号在断线那一刻
就已经不在表里了。

> 这条是 2026-09-10 从生产代码里**删掉**一个字段得到的, 不是设计时想到的: 那个字段服务端每条连接
> 发一次, 客户端存进一个变量之后再也没人读。判据是手册 §9.3 的 D23 ——
> **"这个字段推送侧谁读它?"** 没人读的字段, 写错了也不会有任何症状, 于是它既保护不了什么,
> 也测不出来, 只会让人误以为重启识别是靠它。

**注意区分两种"号"**: 句柄和 `Seq` 是**版本号**(比大小), 而[类一](class1TextStream.md)的
`CallSeq` 是**命名空间**(只判等)。判错方向就是一个静默 bug, 详见类一那篇。

## 5. `NeedFullReload`: 唯一用途 + 有效判据

**这是整套协议里最容易被想歪的一个字段, 别跳过。** 它看着像"通用的出错通知口子", 而它不是。

**它唯一的用途: 这次的进房应答太大了, 服务端让客户端走 http 拉一次。**

| | |
| --- | --- |
| **它是什么** | 进房应答 `roomEntered` 上的**一个布尔字段**。不是一帧, 没有独立的帧类型 |
| **谁在什么时候发** | 服务端, 在**组装这份应答的时候**, 发现这一份给不了 |
| **"给不了"是什么意思** | 只有一个意思: **太大**。没有第二个意思 |
| **客户端收到干什么** | 一件事: 发一个普通的 http 请求把整页拉回来, 然后带着新基准重新进一次房。<br>**不重连、不重试、不碰这条连接** —— 连接一直好好的 |
| **为什么 http 接得住** | http 响应体**没有体积上限**(流式下发, 只有请求头有上限); 长连接上那些上限全是你自己设的。<br>所以"退回 http"是整套设计的**最终兜底**, 它下面没有别的路了 |

**不许拿它干别的。** 下面这些看着都像"出问题了要告诉客户端", 但每一件都有自己的路:

    连接跟不上了 / 写队列满了       -> **断线**(手册 §4.4)。这里一个 NeedFullReload 都不该出现
    客户端发现某一桶接不上          -> **重新进房**(各类文件的"客户端怎么应用")
    服务端拒绝这条连接 / 要用户刷新  -> **deny**(它才是终态信号, 带 Reason 给用户看)
    "我丢过一帧, 你重新对齐一下"    -> **这件事不存在**(第 2 节)

**有效判据(写窄了就会漏):**

> **`NeedFullReload` 有效, 当且仅当"这次应答有多大"是客户端申报游标的函数。**

理由一句话: 它的全部作用是让客户端**换一份新的游标再来问**。拉完再来问, 如果答案还是一样大,
那这条路什么都没改变 —— 那不叫降级, 那叫每 5 秒白拉一次的死循环。
客户端能申报的游标就那么几个(各类文件里的"申报"那一行)。
**应答里的每一样东西, 要么它的大小被这些游标管着(拉完就变小), 要么它就不该在应答里 ——
没有第三种情况。**

从这一句直接推出两条硬规矩:

**推论一: [类一(正文流)](class1TextStream.md)那一桶永远不许走 `NeedFullReload`。**
全文有多大, 和客户端重拉过几次没有任何关系 —— 拉完还是一样大, 无限重拉。

**推论二: 进房应答里不许出现"大小由用户决定、又不在任何游标里"的字段。**
这种字段一旦把应答顶过上限就触发推论一那个死循环, 而且**界面上完全正常**
(http 那条路没有上限, 内容照常显示), 只是每 5 秒白烧一次全量拉取, 没人会发现。

> 真踩过: 用户输入框里还没发出去的**草稿**跟着会话状态整份进了应答,
> 粘一段几百 KB 的日志进输入框就永久循环。
> **修法不是给它做降级, 是把它从推送这条路上摘掉**(组装应答时清空; 推送这一侧本来就一个消费者都没有)。
> 检查手法见手册 §9.3 D23。

反过来说清楚它为什么**够用**: 现在触发它的只有两条, 都被游标管着 ——
[类二](class2MsgStream.md)重拉把消息游标推到最新, 下次要补的条数变少;
整份应答太大时重拉之后客户端手上就是全文, 申报的长度等于全文长度, 差值直接归零。
**两条都是一次就收敛**, 所以场景里可以把"整页重拉恰好 1 次"直接写成断言。
