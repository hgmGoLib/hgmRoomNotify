# 类二 消息流: 离散 id 追加

> 四类共用的部分在 [`../pushDesignAndReview.md`](../pushDesignAndReview.md);
> 协议信封在 [`protocol.md`](protocol.md); 选型在 [`index.md`](index.md)。

**一句话**: 数据是**一条条自带全序 id 的条目**, 只在尾部追加。典型是聊天消息列表。

**id 是内生的**: 区间 `(客户端的 LastMsgId, 快照的 LastMsgId]` —— 条目自带的 id 就是版本号,
服务端一把锁都不用。

**翻车形状是漏一条且无人发现。** 和[类一](class1TextStream.md)的错位不同,
这里漏掉的是**一整条**, 界面上看起来完全正常, 只是少了一行。

## 1. 什么时候选它

选型三问的第一问答"是" + 载体是一条条自带全序 id 的条目。

**和类一的分界**: 载体是连续字节流就是类一, 是离散条目就是类二。
两者的 id 都是内生的, 差别在"缺口怎么判" —— 字节长度天然连续, 离散 id 不连续,
所以类二**必须带左端点**(第 2 节)。

## 2. 帧字段

    段: {BaseMsgId: string, NewMsgs: []Msg}
    roomEnter 申报: {我的 LastMsgId}

* **左端点 `BaseMsgId` 必须带。**
  > 违反后果: 客户端停在 m3 收到 [m5,m6] 时**根本判断不出 m4 存不存在** ——
  > 离散 id 之间没有"下一个"的概念, 光看 id 发现不了空洞, 漏的那条会永久漏掉且无人发现。
* `BaseMsgId` 是空串是**合法值**(本批从最早一条开始), 判"有没有这一段"要看 `len(NewMsgs)`。
* 消息 id 必须**全序、不复用、不回收**。
  > 违反后果: 拿"第几条"当 id, 条数会因为去重 / 补拉窗口而两边对不上。
  >
  > 全序**不只是为了排序**, 客户端的缺口判断直接建立在"能比大小"上面(第 5 节)。
* **光"全序"不够: id 的顺序必须和"对读者可见的顺序"一致, 而这条不会自己成立。**
  自增 / 雪花的 id 是**分配那一刻**定的, 可见是**提交那一刻**的事, 并发插入下两者会反过来:
  A 拿到 100、B 拿到 101, B 先提交; worker 这时读库看见的最大 id 是 101, 游标推到 101;
  A 随后才提交, 它那条 100 落在游标后面 —— 区间查询**永远不会再包含它**。
  > 违反后果: 那一条**永久漏掉且完全静默**。它一次都没进过任何一帧, 所以客户端这边
  > `BaseMsgId` 和游标一路都接得上, **两条回退路径一条都不会触发** —— 这就是这一类
  > "漏一条且无人发现"那个翻车形状最真实的来源。
  >
  > 三条落地办法, 选一条并**写下来选了哪条**(手册 D26):
  > ① **同一房间的插入串行化**(单写者的库如 sqlite, 或一把房间级插入锁), 于是分配顺序 = 提交顺序;
  > ② **游标不用主键**, 改用"在那个串行插入点上分配的房间内序号";
  > ③ worker 取 `LastMsgId` 时**留安全滞后**(只认已经不可能有更小 id 未提交的那一条), 代价是多一档延时。

## 3. 服务端: 进房时怎么算这一份

在进房三步的**第三步**(无锁, 有 DB IO):

    类二: 查区间 (客户端的 LastMsgId, 快照的 LastMsgId], **两端都放进帧**

* 这个区间要有**条数上限**(参数表里那个 `MsgCatchUpMaxNum`)。超了就走 `NeedFullReload`,
  见第 6 节 —— 这是**四类里唯一一个可以走它的桶**。
* 条数上限是"体积太大"的一个**便宜的前置判断**: 不查库就能判, 省掉一次注定要作废的大查询。
  它和"应答太大"是**同一件事的两个测法**, 不是两种不同的降级。

## 4. 客户端: 怎么应用

**按序比较, 不是集合成员判定:**

    BaseMsgId == 我的游标   -> 追加, 游标推到帧里最后一条
    BaseMsgId <  我的游标   -> 按 id 去重后追加(重复是安全的那一边)
    BaseMsgId >  我的游标   -> 中间缺了 -> 重新进房

> 违反后果(写成"在不在我已有的消息里"): 客户端只保留一个窗口(进房补拉有条数上限, 整页拉取也分页),
> 于是 `BaseMsgId` 比我窗口里最早那条还老时, 会被判成"没见过 → 重新进房" —— 而它明明 <= 我的游标,
> 中间一条都没缺。进房那一步又明确允许客户端游标比服务端快照新,
> 所以这是**会稳定复现的一次白进房**。
> **id 全序就是用来做这个比较的**, 别退回集合判定。

去重**按 id, 不按位置**。

## 5. 为什么这一类是幂等的

同一条消息应用两遍, 按 id 去重之后等于应用一遍。
这份宽容度是"重复是安全的那一边"这条规则的全部依据 —— 拿不准的时候**宁可重复不可漏**。

对照: [类一](class1TextStream.md)的应用**不幂等**(靠字节偏移),
所以它必须精确裁剪; 类二只要 id 对得上, 多给几条不要紧。

## 6. 这一类的降级路径

| 触发 | 动作 | 再来一次哪里不一样 | 有效? |
| --- | --- | --- | --- |
| 缺的消息太多(> 条数上限) | 应答里 `NeedFullReload=true` | **重拉把游标推到最新, 下次要补的条数变少** | ✅ |
| `BaseMsgId` 有洞 | **重新进房** | 进房带的是客户端**当前**的游标, 服务端据此重算 | ✅ |

> 第一行为什么合法, 而[类一](class1TextStream.md)那条同样形状的路不合法:
> 判据是[协议篇第 5 节](protocol.md#5-needfullreload-唯一用途--有效判据)那句 ——
> **"这次应答有多大"必须是客户端申报游标的函数**。
> 消息条数是(拉完游标推进, 要补的就少了); 正文的全文长度不是(拉完还是那么长)。
>
> 客户端侧配套的两条: **整页重拉要设最小间隔并合并**, 但**限速期间要排队, 不许丢弃**;
> **进房应答自己接不上时不能原样再进一次房**(基准没变, 答案也不会变), 只能整页重拉换新基准。

## 7. 测试: 这一类必须有的场景

* **缺的消息太多** → 走 `NeedFullReload` → 整页重拉 → 收敛。
  断言**整页重拉恰好 1 次**(它是一次就收敛的, 不是"有界"就行)。
* **`BaseMsgId` 比客户端窗口里最早那条还老** —— 断言这里**不**触发重新进房
  (这就是第 4 节那条"别写成集合判定"的钉子)。
* **迟到的小 id**(手册 D26): 两个事务并发往同一房间插消息, 让**拿到小 id 的那个后提交**, 两个都 fire。
  断言客户端**最后两条都有**。
  > 选了办法 ① 的话这个场景天然过(插入本来就串行), **仍然要写** —— 它钉的是
  > "以后有人把插入改成并发"。
* **进房窗口的 A 段 / B 段**各压一遍, **这一桶单独压一次**(手册 §8.1)。
* 每加一个场景**做一次变异验证**。
