# 推送的正确性: 三条规则 + 常见形式的分类分析

本文要解决的问题: 拿到一个"服务端数据变了, 客户端要看到"的需求, 怎么判断你的做法**对不对**,
以及在常见的十种做法里怎么选。目标是让人(或 AI)拿着本文看几遍代码、写几个测试,
就能把某一种推送方案做对。

范围: **只讨论下行**(服务端变化 → 客户端获取)。
上行(客户端 → 服务端, 网络长期坏、忽然好一下)是另一个问题, 本文不讨论。

## 三个指标

**正确性** —— 网络好的时候, **人工不干预**, 最终能收到最新消息。

> "人工不干预"是关键门槛: 很多线上系统的真实正确性是"用户按 F5", 它**不满足**这个定义。
> 整个第一部分就是在把"人"换成"机器"。

**实时性** —— 服务端发生这件事 → 客户端看见的**理论延时**。用 RTT 为单位, 与具体网络无关。

**性能** —— 分四项看, 不拆开就是一团糊:

| 项 | 含义 |
| --- | --- |
| 变更时的服务端成本 | 一次变更要做多少次动作 × 每次多大 |
| 拉取放大 | 一次变更引发多少次回源读(打在 DB / API 上的那部分) |
| 带宽 | 总字节 |
| 常驻成本 | 每连接/每客户端服务端要存什么; 重连成本 O(1) 还是 O(订阅数) |

三者的关系: **正确性是门槛, 不是维度。** 实时性和性能可以取舍, 正确性只有"满足"和"不满足"。
不允许为了后两者削弱前者 —— 需要更好的实时性/性能时, 加的是第二部分列的加速手段,
而加速手段一律不得成为可靠性的来源。

## 第一部分: 正确性的三条规则

### 规则一: 必须存在一条"全量对齐"的路

任何时刻, 都能把客户端拉回到一个和服务端一致、业务上可接受的状态。
**这条路是可靠性的唯一来源。** 推过去的任何东西(戳、版本号、增量、全量值)都是加速, 都可以丢。

"对齐"的目标**由业务定义**, 必须写下来:

* 小状态量(配置 / 未读数 / 在线状态) → 对齐 = 取回整个当前值
* 累积日志(聊天消息) → 对齐 = 取回**最近 N 条 + 把更早的标记为未加载**

第二条要特别说清: 对齐**不等于"什么都不缺"**。离线半年的客户端一样要走全量对齐,
不可能把半年消息全拉回来。对齐的定义是"该有的都对, 没有的标记清楚"。

凡是号称"不需要全量对齐"的方案(日志从创世保存、永不 GC), 只有比特币那类在做, 性能不可接受;
一切实用系统都有对齐这条路, 区别只在代价和边界画在哪。

### 规则二: 必须能触发规则一

* **a)** 每次(重)连接都触发一次全量对齐。无条件, 不能"等下一个通知再说"。
* **b)** 必须有独立的活性探测(应用层心跳 + 读超时)。

两条正交, 缺一不可:

* 缺 a —— 连上了也不对齐 → 断线期间的变更永久丢失。
* 缺 b —— 永远发现不了该重连 → 静默死链(中间盒丢包 / IP 变了, TCP 仍是 ESTABLISHED,
  两端都没有任何报错)上, 客户端可以永远卡着。

### 规则三: 顺序 —— 通知窗口必须覆盖快照点

抽象形式: 任何一次拉取读到的状态, 不得早于在此之前已发出的通知所对应的状态;
且拉取之后发生的任何变更, 都必须有通知能送达。

三个可执行的检查点:

* **服务端**: 变更**对拉取路径可见之后**才发通知。不能在事务提交前发。
* **客户端**: **订阅生效之后**才取快照。不能先拉后订。
* **拉取路径**: 读到的版本必须能校验 >= 通知所声明的版本。
  (读写分离时打到滞后副本就栽在这条; 没有版本号的形式根本没法校验。)

违反规则三的症状是**永久卡在旧值**, 不是暂时不一致 —— 因为那次变更的通知已经发完了,
不会再有第二次。这是本文三条规则里最难发现的一条。

### 逐环、逐流各套用一遍

三条规则不是全局检查一次, 是**按单位重复检查**:

**逐环**: 业务写库 → 服务端感知变化 → 通知发出 → 客户端收到 → 客户端拉取 → 本地状态生效。
每一环都要满足规则二的 a 和 b。
反例: pg `LISTEN/NOTIFY` 默认**两条都不满足**(没有活性探测, 断连期间的通知不补发),
所以它只能当"通知源", 不能当"这一环已经对了"。

**逐流**: 有几条独立的序号流, 就检查几遍。每房间一条流 = 检查 N 遍; 每用户一条主流 = 检查 1 遍。

## 第二部分: 常见形式的分类分析

只收**真实被实现过**的形式。每一项固定四段: 做法 / 正确性 / 实时性 / 性能。

正确性那段不打分(同一形式可以做对也可以做错), 而写:
**它自动帮你满足了哪几条、把哪几条留给你、它特有的最容易漏的那条。**

### 0. 什么都不做, 靠用户手动刷新

* **做法**: 没有推送。用户觉得不对就刷新页面。
* **正确性**: **不成立。** 规则一有(刷新就是全量对齐), 但规则二没有 —— 触发器是人。
  列在这里是给规则二一个反面对照: 规则二的全部意义就是把"人"换成"机器"。
  注意这是线上最常见的形式, 而且常常是无意识的 —— 只要你的方案漏了规则二, 它就退化成这一项,
  表现是"用户抱怨要刷新才更新"。
* **实时性**: ∞ (由人决定)。
* **性能**: 变更时的服务端成本 0; 拉取放大 取决于用户按刷新的频率; 带宽 每次全量; 常驻成本 0。

### 1. 周期轮询

* **做法**: 客户端每 T 秒拉一次(可带版本号做条件拉取)。
* **正确性**: **三条全自动满足**, 是唯一一个不需要你额外做什么的形式。
  规则一 = 每次轮询就是一次全量对齐; 规则二 = 定时器就是触发器, 且不需要活性探测
  (没有长连接状态可以坏); 规则三 = 没有通知, 也就没有顺序问题。
  留给你的只有一条: 轮询失败要继续重试, 不能因为一次 5xx 把定时器停掉。
  天然免疫: 打到滞后副本时这一轮拿到旧值, 但**下一轮会修正** —— 轮询对一切滞后免疫,
  因为它总会再来一次。
* **实时性**: 平均 `T/2 + 0.5 RTT`, 最差 `T + 0.5 RTT`。
* **性能**:
  * 变更时的服务端成本 —— 0(服务端不需要知道变了)
  * 拉取放大 —— **O(客户端数 / T), 恒定**, 与变更频率无关: 变更少时纯浪费, 变更多时反而最省
  * 带宽 —— 每次全量(条件拉取可省掉未变更的)
  * 常驻成本 —— 0, 没有重连这个概念
* **关键性质**: 负载恒定且可预测, 运维上最省心。低频、实时性不敏感的场景它是**最优主线选择**。
  但**不要把它当成叠加在其它形式之上的兜底层**, 理由见第三部分。

### 2. 长轮询 / hanging GET

* **做法**: 客户端发请求, 服务端挂住直到有变化或超时, 返回后客户端立刻再发一个。
* **正确性**: 规则一二自动满足(每次响应都是一次对齐机会; 请求超时天然就是活性探测,
  **不需要自己做心跳**)。
  留给你: **响应返回到下一个请求发出之间的空窗**。请求必须带上"我上次看到的版本",
  服务端据此判断这段空窗里有没有变更。
  最容易漏: 就是这条。只问"有变化吗"而不带版本号的长轮询, 会丢掉空窗期的变更。
* **实时性**: `0.5 RTT` + 服务端感知延迟。**和推送一样好。**
* **性能**:
  * 变更时的服务端成本 —— 唤醒挂起的请求, O(在线数)
  * 拉取放大 —— O(在线数), 且是同步尖峰
  * 带宽 —— 每次全量或增量
  * 常驻成本 —— 每客户端占一个挂起的 HTTP 请求, 比 ws 贵, 要占中间层的连接/线程/超时配额
* **注**: 正确性比长连接推送**更简单**, 实时性一样好, 被淘汰纯粹是因为常驻成本。
  需要快速做对时是好选择。

### 3. 纯戳 + 拉取 (通知里无版本号)

* **做法**: 长连接推一个"变了", 客户端收到就去拉全量。
* **正确性**: 规则一有(拉全量)。
  留给你: 规则二 a 和 b **全部**, 规则三前两点。
  规则三第三点(校验拉取结果不早于通知版本)**这个形式根本没法满足** —— 没有版本号可校验。
  最容易漏: 规则二 b。典型表现是一切正常直到某个中间盒开始静默丢包, TCP 还是 ESTABLISHED,
  客户端永远收不到戳、也永远不知道自己聋了。
* **实时性**: `1.5 RTT` + 服务端查询时间(0.5 戳 + 0.5 请求 + 查询 + 0.5 响应)。
* **性能**:
  * 变更时的服务端成本 —— O(在线数), 每次极小
  * 拉取放大 —— **O(在线数 × 通知数), 且是时间上完全对齐的同步尖峰**: 所有在线端被同一个戳
    同时唤醒同时打 DB。这是本形式唯一的硬伤, 也是"ajax 泛滥"的来源
  * 带宽 —— 戳 + N 份全量
  * 常驻成本 —— 每连接的订阅集合
* **注**: **被 4 严格支配, 不该选。** 加版本号的代价只是服务端存一个当前版本,
  换回来的是"版本没变就不拉"和"拉取结果可校验"两件事。

### 4. 戳 + 版本号 + 拉取

* **做法**: 通知带上"当前版本是 v7"。客户端本地已是 v7 就不拉; 比 v7 旧才拉; 拉回来校验 >= v7。
  例: hgmRoomNotify(`ChangeSeq` + `CVersionId`)、HTTP ETag / If-None-Match、
  IMAP IDLE(EXISTS + UIDNEXT)。
* **正确性**: 留给你: 规则二 a 和 b, 规则三三点。
  规则三第三点**在这个形式里才第一次成为可能**。
  最容易漏两条:
  * 规则二 b, 同 3。
  * 把版本号当成可靠判据。通知会丢、会被合并、重启会清空, 版本号只是提示。
    **重连时必须无条件拉一次**, 不能因为"版本号看着没变"就跳过。
* **实时性**: `1.5 RTT` + 查询。但版本没变的那些通知实时性变成 0(本来也不需要看到新东西)。
* **性能**:
  * 变更时的服务端成本 —— 同 3
  * 拉取放大 —— 从 O(在线数 × 通知数) 降到 O(在线数 × 实际版本变化数), 这是加版本号的主要收益
  * 带宽 —— 戳 + 实际需要的那些全量
  * 常驻成本 —— 服务端要存每个单位的当前版本(hgmRoomNotify 是每房间一个单值)

### 5. 推全量当前值

* **做法**: 通知里直接带整个当前值。例: 配置下发、小状态量、hgmRoomNotify 的 `LiveData` 装全量。
* **正确性**: **正确性条款最少的推送形式。** 规则一在稳态下几乎自动满足: 下一帧就是一次全量对齐,
  所以**丢帧免费**, 不需要跳号检测, 不需要补拉逻辑。
  留给你: 规则二 a 和 b(长连接固有, 躲不掉), 规则三。
  最容易漏: 值超过帧/写缓冲上限时的退路。必须有一条"太大了, 你自己去拉"的路径,
  否则大值场景静默失败 —— 而且往往是上线后数据长大了才出现。
* **实时性**: **`0.5 RTT`。** 最优。
* **性能**:
  * 变更时的服务端成本 —— O(在线数 × 值大小)
  * 拉取放大 —— 0(命中时)
  * 带宽 —— O(值大小 × 在线数), 值一大就爆
  * 常驻成本 —— 服务端要存当前值
* **适用边界**: 值小, 且中间态塌缩了无所谓。值变大就退到 4 或 6。

### 6. 推增量 + 序号, 缺口补拉

* **做法**: 每次变更推一个带序号的增量。序号连续就直接 apply; 跳号或重连就走补拉。
  例: Telegram、Discord、Matrix、Linear。聊天消息正文的主流做法。
* **正确性**: **条款最多的形式**, 也是唯一需要客户端维护持久游标的形式。
  留给你: 规则二 a 和 b, 规则三, 再加四条本形式特有的 ——
  * 跳号检测(序号不连续必须触发补拉)
  * 补拉**必须分页**(离线一天可能缺几千条, 一次返回会撑爆写缓冲 → 断连 → 重连 → 再撑爆)
  * 补拉超出保留期时的**降级路径**(退到"最近 N 条 + 更早标记未加载")
  * 把"对齐目标"的业务定义写下来(见规则一)

  最容易漏: **降级路径**。它平时跑不到、出事才跑, 是最容易写错又最难发现的一段。
  次容易漏: 把推来的增量当可靠来源。它永远是加速, 规则一才是唯一来源。
* **实时性**: **`0.5 RTT`。** 最优。
* **性能**:
  * 变更时的服务端成本 —— O(在线数 × 增量大小)
  * 拉取放大 —— 稳态接近 0, 只在跳号/重连时发生, 相比 3/4 消掉了同步尖峰
  * 带宽 —— 最省(只传 delta)
  * 常驻成本 —— 服务端存序号(+可选的有界 replay buffer);
    **重连成本 = O(独立流数)**, 这是本形式最容易低估的一项, 见下
* **关于重连成本**: 序号按什么单位单调, 决定了客户端存几个游标、重连要发几次补拉。
  每房间一条流 → 加了 200 个会话的用户重连要发 200 次补拉, 而重连最频繁的时候正是弱网。
  每用户一条主流 → 重连一次往返搞定, 客户端只持久化一个数字。
  代价是队头耦合(一个刷屏房间拖慢同一条流上的其他房间), 所以实践中是混合:
  Telegram 把私聊和普通群合并进**一个公共 message box(共享一个 `pts`)**,
  而每个 channel / supergroup 有自己独立的 message box 和 `pts`;
  补拉相应分成 `updates.getDifference`(公共) 和 `updates.getChannelDifference`(单个 channel)。
  另有一个账号级的 `seq` 和一个次级的 `qts`(密聊、部分 bot 事件)。
  即: 长尾的 1:1 会话被折叠成 O(1), 只有大房间才单独付一条流的成本。
* **变体**:
  * 服务端有界 replay buffer(Discord 的 `RESUME` → 满了 `INVALID_SESSION` → 全量 `IDENTIFY`):
    **纯性能优化, 规则一那条全量对齐的路始终在**, 不改变任何正确性条款。
  * 相对"该客户端已 ack 的版本"做 diff(游戏 netcode): 服务端要存每客户端的已 ack 版本,
    常驻成本变成 O(客户端数 × 状态大小)。大状态、慢变化、高帧率时才划算。
  * 多节点扇出时增量可能乱序到达, 此时跳号里混进"其实马上就到"的假缺口。
    Telegram 的做法是检测到跳号先等约 0.5 秒再决定补拉。单节点单连接不会乱序, 可以先不做。

### 7. 推可交换增量 (CRDT)

* **做法**: 把增量设计成可交换、幂等的 op, 到达顺序无关。例: Yjs、Automerge、协同编辑。
* **正确性**: **唯一一个能删掉规则的形式** —— 规则三的顺序部分不再需要。
  但换来两条新的:
  * op 必须能幂等去重(靠 op id)
  * 必须有压缩 / 快照路径, 否则 op 无限增长

  规则一照旧(压缩后的快照就是对齐目标), 规则二照旧。
  最容易漏: 压缩/快照路径。不做的话前期一切正常, 半年后客户端首次加载要几十秒。
* **实时性**: `0.5 RTT`。
* **性能**: 带宽和 6 相当; 常驻成本上状态单调增长, 靠压缩控制。
  独有好处: 多个写入方不需要中心排序, 服务端可以只做转发。
* **适用**: 多方并发编辑同一份东西。聊天消息**不需要** —— 消息是 append-only, 本来就不冲突,
  为它引入 CRDT 是纯粹的复杂度浪费。

### 8. 快照 + 增量日志跟随

* **做法**: 消费者先取一个带版本的快照, 然后从该版本开始跟随日志。
  例: mysql binlog 复制、Kafka consumer、CDC。**服务端之间**用。
* **正确性**: 规则一 = 那个快照; 规则二 = 消费者自己持久化游标, 断了重连从游标继续。
  留给你: **日志保留期是硬边界。** 消费者落后超过保留期时, 必须能退回"重取快照",
  这条路不做就是静默的数据不一致。
  最容易漏: 就是这条。平时游标都在保留期内, 一次长时间停机才出事。
  重要认识: 它**不是"更可靠的形式"**, 它就是规则一 + 规则二的一个具体实现。
  日志会 GC, 所以它一样有对齐这条路, 只是那一步藏在日志系统外面。
  (Kafka 的 log compaction 更直白: 压缩后的 topic = 快照 + 尾巴, 就是本形式本身。)
* **实时性**: 取决于日志管道延迟(复制延迟 / 端到端延迟), 通常毫秒到秒级, **不由 RTT 决定**。
* **性能**:
  * 变更时的服务端成本 —— O(1), 只写日志, 扇出由日志系统承担
  * 拉取放大 —— 0
  * 带宽 —— 日志量
  * 常驻成本 —— 每消费者一个持久游标
* **适用边界**: **消费者少、可控、有运维。** 面向浏览器不适用: 消费者数量大、随时消失、
  游标没法持久化在不可信的一端。把它接到浏览器面前时, 浏览器那一段一定会退化成 4 或 6,
  日志系统的真实位置是服务端内部的扇出总线。

### 9. 离线唤醒 (APNs / FCM) + 回前台补拉

* **做法**: 移动端进后台, ws 被系统杀掉, 靠平台推送唤醒, 回前台后补拉。
* **正确性**: 规则一在"回前台补拉"这一步。
  **规则二 b 你做不了** —— 你无法在 APNs / FCM 通道上做心跳和读超时, 只能依赖 OS。
  留给你: 因为上面这条, **必须有第二个独立触发器: 回前台无条件补拉。**
  最容易漏: 只在收到推送时才拉。平台推送是明确的尽力而为(会丢、会延迟、会合并、
  会被用户在系统设置里关掉), 只依赖它就会永久漏消息。
* **实时性**: **不保证。** 秒级到分钟级, 系统可能延迟、合并或直接丢弃。
* **性能**: 变更时的服务端成本极低(扇出由平台承担); 拉取放大 = 回前台的用户数;
  带宽极低; 常驻成本 = 存 device token。
* **注**: **只要有移动端, 这一环就躲不掉。** 所以"戳一下 + 拉取"这个形状在任何 IM 里都存在,
  只是它的位置在离线通道上, 而不是在主通道上。

## 第三部分: 形式的叠加, 以及为什么不要做"兜底"

### 会叠加的只有两层

真实系统通常是两层, 而不是从上面挑一个:

* **主线** —— 形式 6(消息正文) 或 形式 4/5(状态量) 或 形式 1(低频不敏感的东西)。决定稳态实时性。
* **离线** —— 形式 9。有移动端就必须有, 因为后台的 ws 会被系统杀掉, 这是物理约束不是选择。

一个具体的例子(聊天类产品的典型形状):

| 数据 | 形式 |
| --- | --- |
| 消息正文 | 6, 每用户主流 + 大房间独立流 |
| 未读数 / 在线状态 | 4 或 5(可塌缩, 用不着序号) |
| 移动端后台 | 9 |
| 大文件 | 不走推送通道, 独立 HTTP |

叠加时的纪律只有一条: **每一层都要独立满足第一部分的三条规则。**
不能出现"这一层不做活性探测, 反正另一层会兜住"这种想法 —— 那就是把规则二从"机器"退回到"运气"。

### 不要额外加一层"兜底"

一个很自然的想法: 主线做好了, 再叠一层低频轮询, 用来兜住"主线出了没预料到的问题"。**不建议。**

三条理由, 一条比一条硬:

1. **它和正确性无关。** 三条规则满足了, 兜底层永远救不到什么;
   三条规则没满足, 兜底层做的是**掩盖**问题而不是解决它 —— 症状从"永久卡死"变成"慢半分钟",
   于是这个 bug 再也不会被发现和修掉。
2. **它反过来会侵蚀正确性。** 有了"反正有轮询兜着"这个念头, 规则二 b 就容易被省掉,
   设计实际退化成"轮询 + 一个不可靠的加速通道", 但没人会这么写在设计文档里。
3. **它是平时跑不到、出事才跑的代码, 必然测试不足。**
   而它真被触发的那一刻, 主线正处于异常状态 —— 此时**两条路径并发写同一份本地状态**,
   重复 apply / 乱序覆盖 / 游标回退这类 bug 就出在这里,
   而且全是开发时想不到、线上才第一次跑到的那种。付出的复杂度换回来一个更难查的故障。

**要区分开**: 形式 6 里"补拉超出保留期 → 退到最近 N 条"**不是兜底**,
它是规则一要求的对齐路径本身, 必须有、必须测。
被否掉的是**在一个已经正确的设计之上再叠一层冗余**。

替代做法: 与其加兜底, 不如把三条规则测到位(第四部分), 并且**让重连变便宜** ——
出问题就干净地断开、重连、走规则一。这比多养一条平时不跑的路径可靠得多,
因为重连路径每天都在跑, 有问题当天就会暴露。

## 第四部分: 怎么验证

### 终极断言(与选了哪种形式无关, 所有形式都要过)

> 停止一切变更, 等待 N 秒, 断言: **每个客户端的本地状态 == 服务端权威状态**。
>
> 累积日志型(形式 6 / 7)再加一条: 本地日志无空洞, 且与服务端序列逐条一致。
> 已显式标记为"未加载"的区间不算空洞。

这条断言的价值在于它把三条规则全部覆盖了, 而且不需要知道实现细节。
N 取"心跳间隔 + 读超时 + 重连最大间隔"之和再留余量。

### 故障注入清单

每注入一项之后, 终极断言仍须成立:

* 断网重连
* 半开连接(静默丢包, 无 RST 无 FIN)
* 服务端重启(纪元变化)
* 房间/对象被重建
* 通知乱序到达
* 通知重复到达
* 服务端写缓冲打满
* 拉取请求超时
* 只读副本滞后
* 通知与事务提交乱序
* 浏览器 tab 冻结与恢复
* 补拉请求超出保留期
* 同一用户多标签页/多设备同时连

### 三个最值得单独测的

* **半开连接** —— 唯一"TCP 说没事、实际全丢"的场景, 也是规则二 b 存在的唯一理由。
  测法: 用防火墙静默丢包(不发 RST), 断言客户端在读超时时间内察觉并重连。
* **顺序类**(先拉后订 / 提交前通知 / 副本滞后) —— 症状是**永久卡在旧值**而非暂时不一致,
  最难发现。测法: 在两个窗口之间人为插入一次变更, 断言最终收敛。
* **补拉超出保留期**(仅形式 6) —— 降级路径平时跑不到、出事才跑, 最容易写错。
  测法: 直接把客户端游标改成一个远古值。
