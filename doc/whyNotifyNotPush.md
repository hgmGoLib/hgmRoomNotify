# 为什么 ws 只"戳一下" + DB 拉取, 而不是直接用 ws 推内容当可靠

本文解释本库的核心设计取舍: 为什么不把聊天消息这类内容直接用 WebSocket 推送并当作可靠送达,
而是让 ws 只传一个可丢的小信号("戳一下"), 真实数据走数据库 + ajax 拉取。

结论先放这里: **在本库的约束下(数据库为唯一真相源、不引额外基础设施、对接尽量简单),
"ws 戳一下 + DB 拉取" 是已知最优的结构。** 没有"换个架构就更好"的方案;
能优化的只有参数(见末尾「能调的参数」)。下面给出推理和方案对比。

---

## 一句常见的错误说法

> "这个库的 WebSocket LiveData 本身已经可靠传每条聊天消息。"

两层都错:

1. **事实层**: 本库的 `LiveData` 明确是 best-effort —— 重连、写缓冲满、超 1024 字节、
   服务器重启(`RoomEpoch` 变)都会丢。它从设计上就**不保证**送达每一条。

2. **概念层(更要害)**: 就算某个 ws 库**真去尝试**"可靠送达每条", 这也不是 ws 这个传输层
   能提供的属性。要让 ws 投递变"可靠", 你**必须**去解决下面那一整套积压 / 持久化问题 ——
   而一旦解决, 可靠性其实来自你新加的持久层, **不来自 WebSocket**。
   所以"ws 可靠送达"是把传输层和持久层混为一谈。选不选本库, 跟"ws 能不能可靠"无关;
   本库是**故意不做这个承诺**, 改用"戳一下 + 拉取"。

---

## 直接用 ws 推内容的致命点: 连接变成了队列

ws 跑在 TCP 上。慢消费者(弱网手机、客户端处理慢)→ 接收窗口缩小 →
服务端内核 send buffer 填满 → 应用层 `write` 阻塞或 `EWOULDBLOCK`。
这一刻 ws 库**只有三条路, 全是坏的**:

- **阻塞写线程** → 占内存 + 队头阻塞(HoL), 一个慢客户端能拖住整个房间的扇出;
- **应用层排队** → 内存无上限增长, 这就是"队列积压";撑不住时再退回下面两条;
- **丢 / 断开** → 直接不可靠, 漏消息。

而"积压满了存硬盘"—— 这一步等于**给每条连接挂了一个持久化消息队列**, 也就是手搓了一个
per-connection 的 Kafka, 而且更烂: 每连接一份队列状态、落盘 IO、积压清理、
重连后从哪个 offset 续传, 全得自己管。

**问题的根在于: 连接变成了队列。** 而连接是存队列最差的地方 ——
它按客户端复制 N 份、生命周期跟着网络抖动走、背压无处可去(你没法让别的用户别说话)。

本库面对同样的积压, 选的是**第四条: 让连接根本不背内容**。它丢掉 best-effort 的
`LiveData`(`serverLiveDataDropped`)、把连发合并成最新一个, 既不阻塞也不无限涨 ——
因为这个信号丢了能从 DB 补回来。

---

## 多方案对比

| 方案 | 连接里放什么 | 慢消费者 / 积压 | 重连后 | 可靠性来源 | 优化手段 |
|---|---|---|---|---|---|
| **A 纯 ws 推内容当可靠** | 每条消息内容 | 内存无限涨 → 阻塞 / 丢 / 断, 三选一 | 连接内队列丢光, 漏消息 | 无 | 几乎没有, 瓶颈在每条连接 |
| **B ws 推 + 每连接持久队列** | 内容 + 落盘 / offset | 解决了丢, 但要自管 per-conn broker | 靠 offset 续传(自己实现) | 你新加的持久层 | 极复杂; 且队列数据还要和业务 DB 对齐 = 两套真相源 |
| **B' 现成 broker(Kafka/NATS)做投递** | 内容 | broker 扛积压 | consumer offset | broker | 引入重组件; 历史 / 已读 / 搜索仍在 DB, 真相源还是两套 |
| **C 本库: ws 戳一下 + DB 真相源 + ajax 拉** | 一个可合并可丢的小信号(version) | 只收到个"你落后了"的旧戳, 追上后拉 DB, **无 per-conn 积压** | 自动下发当前 version → 触发 ajax 对齐 | DB 里业务 `MsgIndex` 单调 | 全落在 DB: 分片 / 索引 / 缓存 / 归档 / 分页 |
| **D 纯轮询** | 无 ws | DB 扛 | 下次轮询自愈 | DB | 简单可靠, 但延迟 = 周期 + 空轮询浪费 |

C 本质就是"事件驱动的 D" —— 把 D 的空轮询去掉, 用一个戳来触发拉取。

---

## 当前方案(C)的优势

1. **连接不再是队列**: 信号大小恒定 O(1), 与消息吞吐量完全解耦 →
   积压 / 落盘 / 队头阻塞**这一整类问题直接不存在**。这是和 A / B 的根本分野。
2. **单一真相源 = DB**: 历史、回放、已读、搜索、断线补发全在一个地方,
   不用像 B / B' 那样维护"ws 队列 + 业务 DB"两套并对齐它们。
3. **丢失安全所以能做到极简极快**: 信号可丢、可合并, 靠 version 收敛 + DB 兜底,
   ws 层因此可以做得很薄; 反过来 A 要快就得丢、要不丢就得重, 本库没这个两难。
4. **优化落在数据库, 而数据库正为此而生**: 水平分片、读副本、缓存、冷热分离都是成熟手段;
   per-connection 队列没有任何一种。"存储就是数据库, 该怎么搞怎么搞, 更容易优化"。
5. **故障恢复是天然的, 不是特例**: 重连 / 服务器重启 / `RoomEpoch` 变,
   统一走"下发当前 version → ajax 全量对齐", 不需要单独写"断线补发"逻辑。
6. **对接简单**: 客户端只有两条路径 —— 戳到且连续 → 快路径直接用 `LiveData`;
   缺失或跳号 → ajax 补。详见 [`../example/ReliableChat/`](../example/ReliableChat/)。

诚实的代价:

- `LiveData` 不够用时(超限、重连、积压被丢)**多一个 RTT**;
- 快路径仍是 best-effort, 它是**延迟优化, 不是可靠性来源** —— 可靠性永远在 DB 的 `MsgIndex`;
- DB 成为读放大热点, 需要为此设计 —— 但这是**好事**: 问题集中在一个可控、可水平扩展的点,
  而不是散在 N 条连接的缓冲区里。

---

## 这是已知最优吗?

**是, 在本库的约束下。** 约束 = 数据库为唯一真相源、不引额外基础设施、对接尽量简单。
在这组约束下没有"换个架构就更好"的方案:

- A / B / B' 相对 C 要么**严格更差**(把队列塞回连接, 重新踩积压三选一),
  要么是**更重但不更好**(外挂 broker, 还多出一套真相源要对齐)。
- 唯一真正不同的设计点是: 拿**日志型 broker(Kafka)当投递 + 持久层**, 不再用 DB + ajax。
  在极端规模下日志结构可能比"从 DB ajax 拉"更省, 但那是**另一组约束下的不同权衡**
  (你接受引入 Kafka、接受 broker 与 DB 两套真相源), 在本库"DB 即真相、不引基础设施"的
  约束下**不算更优**。

所以剩下能动的不是"换方案", 而是**调参数**。

### 能调的参数

| 参数 | 当前值 | 在哪 | 调大/调小的影响 |
|---|---|---|---|
| 单连接写缓冲上限 `WriteBufMaxBytes` | 默认 64KB(可配) | `02server.go` `ServerConfig` | 调大 = 慢消费者积压更晚触发丢弃 / 断开, 但占更多内存; 调小 = 省内存但更早丢 `LiveData`。这是背压安全阀, 不是可靠性来源 |
| `LiveData` 单条上限 | 1024 字节(应用层硬上限) | `02server.go` 校验; 线协议本身支持到 65535(`03libProtocol.go`) | 调大可让更多增量走快路径(少一个 RTT), 但每条更大 → 写缓冲更快填满, 削弱背压安全。1024 是"快路径覆盖率"与"背压安全"的折中 |
| `CVersionId` 上限 | 100 字节(应用层) | `02server.go` | 放状态编码 / 版本号通常够; 不够就当版本号用 + ajax 取完整状态 |
| 增量合并窗口 | 由调用方控制 `FireChange` 节奏 | 调用方 | 窗口大 = 更多连发合并成一次戳, 省带宽但延迟高; 窗口小 = 实时但戳更密 |

调这些参数是在"快路径覆盖率 / 内存占用 / 背压安全 / 延迟"之间移动工作点,
**不会改变上面的结构性结论**。要更高吞吐, 正确的方向是优化 DB 那一侧(分片 / 缓存 / 归档),
而不是把更多内容塞回 ws 连接。
