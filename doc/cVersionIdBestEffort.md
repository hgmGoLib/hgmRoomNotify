# CVersionId 是尽力而为的"当前值"提示, 不是可靠单调版本通道

本文回应一个具体误区(对接策略下发 / 版本号场景时容易犯):

> "`FireChange` 时让 `CVersionId = 全局单调版本号`(server 现成有的 `policy_version_seq`)。
> 端点 `onChange` 拿到 `CVersionId` 跟本地 `highestVersion` 比: `CVersionId <= 本地` →
> 直接 no-op, **连 snapshot 都不请求**; `CVersionId > 本地` → 才拉全量。
> 安全上没问题: 伪造更高版本号顶多让你白拉一次(snapshot 有签名); 伪造相等/更低让你跳过 ——
> 但你本来就已经 ≥ 那个版本, 跳过无害。"

一句话结论: **这把 `CVersionId` 误当成了"总是存在、连续、单调、可比"的可靠版本通道。它不是。
`CVersionId` 和 `LiveData` 一个性质 —— 尽力而为, 不保证总是有(只是"有的概率高一些")。可靠锚点永远是
那次全量请求(snapshot / ajax), `CVersionId` 只能当一个机会主义的"省一次请求"提示, 不能当跳过的唯一判据。**

与 [`liveDataNotReplayStream.md`](liveDataNotReplayStream.md) 同根: 那篇讲 `LiveData` 是机会主义快路径、
背后永远有 ajax 兜底; 本篇讲 `CVersionId` 同样是机会主义提示, 背后永远有全量兜底。两者都**不是**可靠性来源,
把任何一个当成"可以据此跳过兜底"都是同一类错误。

---

## 它到底有多"不保证总是有" —— 看代码

`CVersionId` 存在房间结构里, 内存、单值、可选。下面四件事都会让 `onChange` 收到一个**空的 / 旧的 /
不可比的** `CVersionId`:

1. **每次 FireChange 无条件覆盖, 没带就清空。**
   `FireChange` 里是 `room.CVersionId = ev.CVersionId`(`02server.go`)。它不是"取最大", 也不是"没传就保留旧值",
   而是直接赋值。**只要有一次 `FireChange` 没带 `CVersionId`, 存的值就被重置成空串。**
   所以除非你保证*每一次* `FireChange` 都带, 否则它既不连续也不单调; 而框架并不强制你每次都带。

2. **服务器重启全丢。** `roomMap` 在内存。重启后房间表是空的, 在下一次 `FireChange` 回填之前,
   该房间的 `CVersionId` 就是空串(且 `RoomEpoch` 换新)。

3. **首次进房就是空。** 进一个还没被 `FireChange` 过的房间时, 房间按需创建,
   下发的就是 `ChangeSeq=0`、`CVersionId=""`(`02server_auth.go` 的 `doRoomEnter`)。

4. **框架不解释它的内容。** `CVersionId` 是 ≤100 字节的 opaque 字符串。框架既不校验它是数字,
   也不保证它单调。"`CVersionId = policy_version_seq` 全局单调号"完全是你 app 层自己的约定 ——
   框架不提供、不维护这个保证。即使你这样约定了, 上面 1/2/3 仍会让它缺失 / 被重置 / 不可比。

另外, 客户端去重的锚点是 `(RoomEpoch, ChangeSeq)`, **不是** `CVersionId`(`client_room.go` 的 `onRoomValue`)。
`CVersionId` 只是跟着这条 `roomValue` 搭车下发的字段。`RoomEpoch` 变(重建/重启)会无条件触发一次 `onChange`,
此时完全可能带着一个空的 `CVersionId`。

## 为什么"`CVersionId <= 本地` 就跳过"会漏数据

误区方案默认"真实更新一定带着一个 `> 本地` 的 `CVersionId`"。但由上一节, 一次真实更新完全可能带着:

- **空串**(生产者那次没带 / 重启后还没回填) —— 你若把空串按版本比较当成 `<= 本地`, 就把真实更新跳过了;
- **被重置后的旧值 / 不可比的值** —— 同样可能被误判成"已有, 跳过"。

它的"安全性论证"也错在这: "伪造相等/更低让你跳过, 但你本来就 ≥ 那个版本, 跳过无害" ——
这个推理只在"真实更新必然 `> 本地`"成立时才对。而真实更新可能根本不带可比的 `CVersionId`,
于是"跳过无害"不成立: 你会漏掉一次真正的新策略。问题不在攻击者, 在于**把一个会缺失的字段当成了跳过的唯一闸门**。

## 正确的对接契约: 跳过是机会主义优化, 全量是可靠兜底

和 `LiveData` 完全对称。`CVersionId` 命中省一次请求, 没命中就回源 —— 回源永远是安全默认。

| `onChange` 收到时 | 动作 |
|---|---|
| `CVersionId` 非空 **且** 可比 **且** `RoomEpoch` 没变 **且** `<= 本地` | 跳过这次全量(机会主义去重: 重连回放 / 重复戳) |
| 其它一切(空 / 不可比 / `RoomEpoch` 变了 / `> 本地`) | 拉全量(ajax / snapshot) |

要点:

- **任何疑点都回源**: 空、不可比、`RoomEpoch` 变了, 一律当"必须拉全量", 绝不当"`<= 本地` 跳过"。
- **跳过只是省一次冗余请求**(去掉重连回放 / 重复戳带来的白拉), 不是可靠机制。可靠性永远在那次全量 + 它自带的
  校验(如签名), 不在 `CVersionId`。
- **如果你依赖它做去重, 就别在真实 `FireChange` 上漏带 `CVersionId`** —— 漏带会把存的值清空(见上节第 1 点),
  反而让后续都被迫回源。要么每次都带, 要么干脆不依赖它跳过、纯靠全量。

这样 `CVersionId` 就回到它该在的位置: 一个"当前状态量"的尽力下发提示(在线/typing、未读数、版本号),
命中省一个 RTT, 丢一次自动收敛(下一次 `FireChange` / 进房 / 重连会再带最新值), 而正确性始终由全量兜底。

---

## 总结

`CVersionId` 不是"总是有、连续、单调、可比"的可靠版本通道, 它是和 `LiveData` 同级别的尽力而为提示 ——
可选、内存单值、没带会被清空、重启丢失、进新房为空、内容框架不解释。可以拿它做"省一次全量"的机会主义优化,
但跳过的判据必须是"非空 + 可比 + 同纪元 + `<= 本地`", 其余一律回源。把"`CVersionId <= 本地`"当成
唯一跳过闸门会漏掉真实更新。可靠锚点永远是那次带校验的全量请求。
