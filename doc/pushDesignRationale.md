# 实时推送方案的由来: 每条规则为什么是那样

这是 [`pushDesignAndReview.md`](pushDesignAndReview.md)(执行手册)的配套文档。

**执行手册回答"怎么做";这一篇回答"为什么"。**
想删掉、放宽、或者换一种写法之前, 先在这里找到对应的那一节 —— 每一条规则都有由来,
**没有一条是凭感觉加的**。

**这一篇不是执行必需的。** 只在下面三种情况下需要读:

1. 你想改动执行手册里的某条规则;
2. 你在 review 别人的推送系统, 需要论证"这样为什么不行";
3. 你要给一桶**新形状**的数据设计推送, 而 §2 那四类都套不上。

**数据来源**: 本篇所有数字来自一个真实系统的实测 —— 生产单元测试, 加上一个独立重写的模拟器
(跑真 TCP、能注入网络故障、参数按生产等比缩小 32 倍)。是估算的地方明写"模型"。

## R1. 为什么目标必须写成可证伪的句子

"更快""更省""放大常数尽可能接近 1"这类目标, **没有任何一行代码能违反它们**。

后果是具体的: 从这种目标派生出来的检查点永远只能挂在"建议"档上。
而"建议"是个陷阱 —— 它让"没做"看起来像一种合法状态, 于是那几条永远不会被做掉,
检查表本身也不再能回答"现在到底满不满足目标"这个问题。

**真实经过**: 带宽目标最早写的就是"放大常数尽可能接近 1"。五条检查点(执行手册的 D2/D6/D7/D8/D9)
因此一直挂在建议档, 一挂就是很久。把目标改写成"**每帧信封开销 <= 64 字节**"这一个数字之后,
那五条当天就升到了"必须" —— 因为它们终于有了一个会变红的判据。

**64 这个数不是拍脑袋**: 一帧变更的信封当时是三十几个字节(帧类型 + 房间句柄 + 字节偏移 +
命名空间代号 + map 头 + ws 帧头), 留一倍余量给以后加的字段。
**真要超, 先回来把这段账重算一遍, 别顺手改大数字。**

**结论: 一个目标如果你写不出"什么情况下它会当场变红", 那它还不是目标。**

## R2. 为什么是 正确性 > 延时 > 并发 > 带宽 > 简单性 这个顺序

**正确性排第一, 而且它不是维度是门槛。**
理由不是"正确性当然重要"这种空话, 而是它的**失效模式**:
推送系统的正确性 bug 几乎全是**静默且不可恢复**的 —— 界面停在旧数据, 连接健康, 心跳照跑,
日志干净, 用户不会报障(他们会按 F5)。这类 bug 没有"发现 → 修复"的自然循环,
所以不能用"先上线看看"来兜。

**延时排第二**, 因为它的下界是**形状**决定的, 不是实现决定的。
"服务端戳一下, 你自己来拉"这个形状, 客户端就必然多付一个完整 RTT ——
缓存 / 压缩 / 合并 / 换机房都补不回来。**选错形状之后没有调参空间**, 这是它排在前面的全部理由。

RTT 数是常数, 乘上真实网络的 RTT 才是体感, 而乘数你改不了:

| | 额外 RTT | RTT=1ms | RTT=350ms |
| --- | --- | --- | --- |
| 戳一下 + 回查全量 | 1 | +1ms | +350ms, **每批变更都要再付一遍** |
| 推内容 + 内生 id | 0 | — | — |

**并发排第三, 在带宽前面**, 三条理由:

1. **在单机部署下它是"能承载多少用户"的唯一上限。** 加机器这条路一旦被排除,
   天花板就完全由"服务端有没有一段被所有人排队等的临界区"决定 —— 别的都是常数因子。
2. **退化方式不同。** 带宽退化是线性的、局部的(某个用户多花点流量);
   并发退化是**超线性且全局**的 —— 一把共用锁里有 DB IO 就是 O(排队人数) 串行,
   而且一个正在读大正文的房间会把**所有别的房间**的进房请求一起卡住。
3. **补救代价不同。** 带宽事后能补: 换个编码就行, 协议形状一行不用改
   (真做过一次, 每帧 171 → 16 字节)。并发事后补不了: 它要求换掉**版本号的定义**,
   而版本号是整个协议的地基(见 R3)。**能事后补的排后面, 补不了的排前面。**

**带宽排第四不等于可以不管**: 单机单网卡, 上行带宽同样是全局共享资源;
放大倍数从 1.7 涨到 150 就等于把能同时看流式输出的人数**除以 88**。
它排在并发后面只是因为它事后能补。

**简单性排最后, 但在左边四项打平时它说了算。**
执行手册 §10 那张"明确不做"的清单每一条都是简单性赢来的 —— 它不是弱势指标, 是**平局的裁判**。

## R3. 核心: 为什么版本号必须内生于数据

**这是整套设计的地基, 别的都是它的推论。**

给整个房间发**一个**共用版本号(每广播一次 +1)是最容易想到的做法。
它有一条隐藏的硬性要求: **"版本 N 的那份数据"必须是一个明确的东西**, 否则客户端拿它比大小会比错。

于是只能写成: **读 DB / 算增量 / 号 +1 / 序列化, 四件事在同一个临界区里完成。**

—— **锁不是为了保护数据, 是为了给这个号赋予意义。**
号是外面发的(外生), 临界区就是它的定义域。一旦这么定, DB IO 进锁就成了必然。
**这是形状问题, 不是实现问题**(这条路真走过一版)。

所以正确的做法是: **不发号, 去数据自己身上找号。**

| | 定义 | 代价 |
| --- | --- | --- |
| **外生版本号** | 它本身不是数据的一部分, 只有在临界区里被"发"出来才有意义 | **一把锁** |
| **内生版本号** | 它就是数据自己的某个属性, 谁读到数据就顺带读到了号 | **0** |

例: 一段**只会往后追加**的字节流, "当前长度"就是它的版本号 —— 不需要任何人去发这个号, 长度就在那儿。
两个人并发读, 读到的必然是互为前缀的两份, 长度大的那份就是新的。
**"谁先谁后"这个问题在这里根本不存在, 所以也就不需要一个临界区去定义它。**

于是问题从"怎么把锁做得更细"变成了"**这一桶数据的内生版本号是什么**"。
不同的数据形状答案不同 —— **所以必须一桶一桶单独设计, 不能统一**(这就是 R4)。

### R3.1 为什么"每房间一把小锁"这个后门必须堵死

有人会说: 那我不用全局锁, 给每个房间一把小锁, DB IO 放小锁里不就行了。

这个后门在**同一个房间有多个观众**时立刻漏水: 两个人同时进同一个房间,
第二个人要排队等第一个人把几十 KB 正文从 sqlite 里读完。
**sqlite 开着 WAL 本来允许多个读者并发, 一把每房间的小锁照样能把这个能力抹掉。**

更根本的一条:

> **一把锁里出现 DB IO, 就等于把"这把锁的持有时间"交给了磁盘。**
> 磁盘慢一次, 所有排在这把锁上的人一起慢。
> **锁拆得再细也只是缩小受害范围, 没有改变形状。**

所以执行手册里的并发目标写了更强的第二句(**任何一把锁里都不许有 DB IO, 一把也不行**):
它堵死了"再拆一层锁"这条退路, 逼你回答真正的问题 ——
**这段代码为什么非得在锁里跑?** 答案永远是"为了让某个号有意义", 修法也永远是"换一个内生的号"。

### R3.2 为什么并发目标不许用压测判

"现在只有个位数用户, 压不出来"不是理由, "我给你举个跑得挺快的例子"也不是反驳。

一把锁里放着 DB IO, 逻辑上就是 O(排队人数) 串行 —— 这是**形状**, 和当下测出几毫秒无关。
更具体地说: **串行段在人少时排队长度是 0 或 1, 被完全掩盖; 人一多是断崖不是斜坡。**
压测反映的只有"当前这几个人", 它对"再多十倍会怎样"**没有任何预测能力**。

而等到压得出来的时候, 要改的是版本号的定义, 也就是整个协议。
**这条检查点的全部价值在于它超前。**

## R4. 为什么一共只有三种 id 数据结构

不是"想到几种算几种", 是从客户端那一侧**穷举**出来的。

客户端收到一帧, 能做的动作只有三种, 每种需要 id 回答的问题不一样:

| 客户端动作 | id 要回答的问题 | id 数据结构 |
| --- | --- | --- |
| 接在已有数据后 | "接在哪一位?" | **A**: (区间起点, 区间终点] ← 内生 |
| 覆盖已有数据 | "该不该覆盖?" | **B**: (纪元, 单调计数) ← 外生 |
| 执行一个动作 | (不需要问) | **C**: 没有 id |

**三种动作穷尽了"客户端能拿这一帧干什么", 所以三种 id 也就穷尽了。**

执行手册里的"四类"是同一件事按**数据长什么样**分的:
类一 = A 的连续版(字节流), 类二 = A 的离散版(条目流), 类三 = B, 类四 = C。

### R4.1 方案 A: 为什么两端都要在帧里

版本号 = 序列的终点; 一帧增量 = 左开右闭区间 (上一次的终点, 这一次的终点]。

**起点用来对齐(接在哪), 终点用来推进(下次从哪接)。**
两端都在帧里, 于是**任何一个"停在这段中间某个位置"的客户端都能消费同一帧** ——
这是服务端不必按人算增量、因而不必进锁的**直接原因**。

不带起点会怎样: 客户端只能靠"双方都记得上一次到哪"对齐。
而这份记忆随时会因为断线、重连、整页重拉而分叉;
**分叉之后每一次追加都会接到错误的位置上, 界面上是重复一截或者乱码, 而且 id 一路连续,
再没有任何东西会把它纠正回来。** 这是最坏的一类 bug: 静默且不可恢复。

**离散载体上这条更硬**: 连续载体上"缺没缺"能靠减法看出来, 离散不能 ——
客户端停在 m3 收到 [m5, m6] 时, 光看 id **根本判断不出 m4 存不存在**,
因为离散 id 之间没有"下一个"的概念。漏的那条会永久漏掉且无人发现。

**而客户端那三条规则必须写成按 id 比大小, 不能写成"在不在我已有的那些消息里"。**
两者看着等价, 但客户端手上**只有一个窗口**(进房补拉有条数上限, 整页拉取也分页)。
于是起点比窗口里最早那条还老时, 集合判定会答"没见过 → 重新进房",
而它明明 <= 我的游标、中间一条都没缺 —— **一次白进房**。
而且进房路径本来就允许客户端游标比服务端快照新(R5), 所以这个情形会**稳定复现**。

> **"id 必须全序"这条要求不只是为了排序, 客户端的缺口判断直接建立在能比大小上面。**
> 正确的三条是: 起点 == 我的游标 → 追加; **起点 < 我的游标 → 去重后追加**; 起点 > 我的游标 → 有洞。

### R4.2 方案 A 的前提必须有一个显式的守卫

"序列真的只追加, 从不重写中间"这条前提**不会自己成立**, 必须有东西守着。

本项目里守卫是一个命名空间 id(`CallId`): 正文会变短的所有情况(一次调用结束 / 换一条调用)
它一定跟着变, 变了就是**另一套字节空间**, 只能整份换。

**所以 `CallId` 不是版本号, 是字节空间的命名空间。** 这个区分很重要:
版本号可以比大小, 命名空间只能比相等; 拿命名空间去比大小, 或者拿版本号去当命名空间, 都会错。

#### 守卫必须**每帧都判**, 不是"换的时候带一下"

这是最容易写漏的一格, 而漏了的症状正好是最坏那一类。

`BaseLen` **只在同一个命名空间内有意义**。所以客户端收到任何一帧追加,
第一件事必须是"帧的命名空间和我手上这份是同一个吗", 不同就重新进房 —— **在判 `BaseLen` 之前**。

漏掉它会怎样: 拿旧命名空间的 `BaseLen` 去和新命名空间的长度比大小, 然后把旧的那截字节
**接到新的那份屁股上**。界面上是乱码, 而 `BaseLen` 一路连续, **没有任何东西会纠正它**。

> **典型的写法错误是"只在整份替换那一格判命名空间"** ——
> 因为换命名空间时服务端确实会发一帧整份替换, 看起来判那一格就够了。
> 不够: 那一帧一旦没被应用(重放顺序 / 客户端刚整页拉过还不知道命名空间),
> 后面每一帧追加都会硬接。

#### 帧里带的是"代号", 不是那个字符串

`CallId` 本身是二十来字节。而这是**每帧都要判**的东西 —— 带字符串等于每批变更白扔二十字节,
而一批正文才二十几字节(R11 那笔账里这是很大一块)。

所以帧里带的是一个**进程内递增的小整数代号**, 和 `CallId` 是同一件事的两个字节版本:

* `CallId` 字符串只出现在 `roomEnter` 申报里 —— 客户端是从**普通拉取**那条路知道它的,
  而那条路给不出房间内部的代号;
* 服务端在进房应答里把代号回给客户端, **从此每帧只比代号**。

**客户端"还不知道代号"要有一个表示法(用 0)。** 刚整页拉过、还没进房时就是这个状态,
这时**判不了命名空间, 也就不判**, 由随后那次进房把代号对齐过来。

#### 跨命名空间的回退是故意不防的

客户端**只比相等, 不比大小** —— 光看代号它分不出"更老"还是"更新"。
于是重放缓冲时, 一帧属于旧命名空间的整份替换**会把新的那份盖回去**。

**这是可以接受的, 但它依赖一条别的规矩:**

> 让快照前进到新命名空间的那一次 `Store`, 后面**必然紧跟一帧广播**(R6: Store 和广播是绑定的,
> "没有可见变化"是在 Store 之前就返回了)。
> 而这条连接在第一步就订阅好了, 同连接 FIFO ⇒ 那一帧必然排在旧帧后面、必然被应用。
> **重放按到达顺序走, 最后落地的一定是最新那一帧。**

所以中间态会在屏幕上闪一下, 那是体验不是正确性。

> **反过来说: 一旦有人在 R6 那里加了"Store 了但这次不广播"的分支, 这条论证就断了。**
> 记在这里, 因为这两处代码离得很远, 改的人不会想到它们咬合着。

### R4.3 方案 B: seqlock 的不变式, 和两个顺序为什么不能换

那一桶(几个库若干张表拼出来的一组标量)**找不到内生版本号** —— 没有哪个字段能代表"整桶的版本"。
所以只能外生, 但**只锁那个整数, 不锁数据**:

    写侧: 1) 写库(提交)  ->  2) Seq++       ->  3) 广播(内容 + 这个 Seq)
    读侧: 1) 读 Seq       ->  2) 读数据, 发出 (数据, 刚才读到的 Seq)

**不变式**:

> 发出去的每一对 (数据 d, 标签 v), 都满足"**d 至少包含了所有 <= v 的写入**"。

**推导**: 写入 k 落库 早于 bump 到 k; bump 到 k 早于 bump 到 v(同一个计数器, k <= v);
而读数据晚于读到 v。传递下来, d 一定含写入 k。

**关键性质: 标签只会低估数据的新鲜度, 绝不会高估。**
低估是安全的(最多客户端多收一帧重复的), 高估是致命的。

**两个顺序各自对应一个真实 bug:**

* 写侧"先 Seq++ 再写库": 中间有个窗口, 号涨了库还是旧的。这时有人读,
  就发出一份**贴着新号却缺了那次写入**的数据。
* 读侧"先读数据再读 Seq": 同样是旧数据配新号。

**高估的后果不是"晚一帧", 是永久静默错误**: 客户端把自己顶到那个号,
之后真正属于这个号的那一帧会被判成"不比我新"而扔掉, 界面停在这里, 看不出任何异常。

而且**两条路的可恢复性不一样**: 广播那条路还能被下一次 fire 纠正;
**进房那条路纠正不了** —— 进房应答不是被某次写入触发的, 它后面没有"下一次 fire"排着队。
**所以这两个顺序是进房路径正确性的唯一支点。**

### R4.4 方案 B 的两个"啥事没有"(为什么它够用)

* **锁住顺序是没有意义的, 只要锁住"变没变"。**
  两个并发的读者谁的号大, 客户端看到谁, 另一个被扔掉 ——
  而被扔掉的那份数据一定是"某个真实存在过的版本", **不是拼出来的**。
  收敛只需要最后一条: 最后一次写之后发出的那一帧, 标签严格大于此前所有帧。
* **客户端多收敛一次, 什么事都没有。**
  状态桶的应用是**幂等的整份覆盖**, 多盖一遍等于没盖。

第二条正是"整份覆盖"这个形状换来的宽容度, **也正是它必须整份而不能是字段级差量的原因**:
差量的应用不幂等, 一旦允许乱序就会错; 要求不乱序就要求号严格连续; 要求号严格连续就又要一把锁。
**一路回到 R3。**

### R4.5 为什么用不可变快照 + 原子指针, 而不是裸 seqlock

    房间里存 atomic.Pointer[RoomState_t], 快照结构体里自带 Seq。
    写侧 Store 一个全新的指针, 读侧 Load 一次同时拿到数据和号。

这么写之后, **读侧那两条"顺序不许换"的纪律自动成立** —— 一次 Load 同时拿到数据和它的号,
"先读哪个"这个问题根本不存在。只剩写侧要人守。

**前提**: 同一个房间同时只有一个 worker 在改它(脏房间 id 去重 + 等一轮做完才进下一轮),
是单写者多读者。
裸 seqlock 是给"数据大到没法一次原子换指针"的场合准备的, 这里不需要。

**初值用 CAS 而不是锁**: 谁先到谁 `CompareAndSwap(nil, 新的)`, 输了的那次读库白读。
**那是锁外的白读, 不阻塞任何人** —— 比"所有人排队等一次读"好。

### R4.6 为什么纪元是命名空间而不是 id

(进程纪元, 房间句柄) 在三个方案之外, 它是**所有 id 的作用域**:
纪元一变, 下面所有的号(长度 / 消息 id 链 / Seq)全部作废, 客户端无条件重新对齐。

**为什么必须有**: 没有任何东西能保证跨进程 / 跨重启单调 —— 时钟会回拨, 数据库会回档。
没有纪元, 重启后的新变更会被当成旧消息忽略。

**为什么房间句柄可以兼任房间纪元, 不需要另一个字符串**:
房间只在**最后一条连接离开时**销毁, 所以"客户端还在房里期间号不会变"是**结构性成立**的。
省下每帧三十来字节。

**作用域这件事要当真**: 命名空间 id 只在一个房间句柄里有意义 ——
换了句柄就必须重新对齐, 拿旧句柄下的号去比新句柄下的号会撞。**这是一个真 bug。**

**一个白捡的好处**: 有了纪元, "跨重启单调的 id"这个不可能的需求就消失了。
这也是"房间不存在期间发生的变更"不需要任何补偿逻辑的原因。

### R4.7 为什么不做方案 D(无序集合按 key 版本 + 墓碑)

判据: **集合整份的字节数, 和"每个 key 的版本表 + 墓碑管理"比, 哪个便宜就用哪个。**

本项目里那些集合都是几百字节的小集合, 整份丢进类三远比给每个 key 发版本便宜,
而且省掉了**"删除怎么表示"这一整类问题**。

以后真出现了大集合再说。这是简单性赢的一局 —— 它赢在"前四项打平"上, 不是赢在"代码少"上。

## R5. 为什么"订阅先于快照 + 客户端缓冲重放"等价于"锁里原子完成"

常见写法是让进房在同一把锁里原子完成(登记连接和取快照之间不许有广播插进来)。
本方案把它拆成了两步, 中间**故意留了一个空隙**。

**证明两者给出的保证一样:**

> 订阅(第一步)完成之后的每一次广播都会发给这条连接;
> 登记之前发生的变更, 一定已经反映在第二步 Load 到的那份快照里(因为 Store 早于广播, 见 R6)。
> 两者重叠的部分 = "已经在快照里、又被广播了一遍"的帧, 按各桶自己的 id 精确剔除。
> **没有任何一个变更会同时落在两边之外。**

而拆开之后, **锁里不需要做任何按用户的活** —— 这就是它比"锁里原子"好的全部理由。

代价是客户端多了一个状态(pending + 缓冲), 这个代价由 R7 那条规矩兜住。

### R5.1 为什么缓冲溢出不能"丢最旧那几帧"

丢最旧 = 制造一个**静默空洞**: 客户端不知道自己少了一段, 后面的帧照样接上去, 内容就错了。

**现在的做法是关掉连接**, 由重连重进所有房间收敛。理由见 R9。

> 曾经的做法是"整个缓冲作废 + 记标记, 应用完快照立刻重新进一次房"。
> 它本身是收敛的(输入严格改变了: 基准变成刚拿到的那份), **被删掉不是因为它错**,
> 而是因为它是一条**只在灾难时才走、因而永远测不到**的路。见 R9。

### R5.2 客户端怎么知道一帧广播属于哪个房间

这一步比看上去要紧, 因为 R5 那个"故意留的空隙"就在这里兑现:
**第一步订阅之后广播就开始发了, 而应答要等第二、三步。**

广播帧上只有整数句柄(为了省那三十来字节, R11), 而客户端是**按房间**缓冲的 ——
所以它必须在收到第一帧广播之前就知道句柄。**应答来得太晚。**

修法是一帧十几字节的 `roomHandle`, 而且它必须**在订阅的那把锁里就入队**:

    第一步(锁内): 登记连接进房间 -> 同一把锁里 pushFrame(roomHandle)
    // "roomHandle 排在本房间任何一帧广播之前"于是由 FIFO 结构性保证, 不靠时序运气

**不做这一帧的后果不是"慢一点", 是首次进房窗口内的广播全部被当成"认不出的句柄"扔掉** ——
而这正是 R13.4 那组 A/B 段场景要压的东西, 于是那组场景会**全绿, 但什么都没验**。

> 替代方案是"按连接缓冲所有未知句柄的帧, 拿到应答再按句柄捞出来"。
> 它要多一个连接级缓冲和它自己的上限 —— **多一个状态, 换十几个字节**, 按 R2 的裁判规则输了。

**重新进房时句柄不要清。** 房间只在最后一条连接离开时销毁(R4.6), 重进一次不换号;
清掉反而会让这次应答回来之前的广播全被当成"不认识的号"扔掉。要清的是"我和服务端对齐着"那个标记。

### R5.3 为什么快照不需要"一个事务读出来"

数据分在三个 sqlite 文件里, **跨库事务不存在**, 一个事务包不住它们。
所以快照相对写库方可能读到"半新半旧"。

**这不影响收敛**: 每次写库后面都跟着一次 fire, 下一版重读时会把上一版读串的地方纠正过来。
而且这正是普通拉取路径一直以来的行为(用的是同一个函数)。

**结论: 不要为了"快照要原子"去发明跨库事务 / 全局版本表 / 每条数据加版本列。**
要保证的是"**下一次重读一定会来**"(那是上游 fire 点的事), 不是"这一次读得完美"。

## R6. 广播写侧的几条设计取舍

### R6.1 为什么 Seq++ 挂在 worker 的 Store 上, 而不是业务侧自己 bump

两条理由:

1. 业务侧是主流程。让它同步去读库 + 扇出全房间, 等于**把推送的 IO 挂到业务关键路径上**。
2. 更重要的一条: 挂在 Store 上之后, **"忘了 bump"退化成"忘了 fire"**。
   后者是本来就存在、已经审过、而且漏了会立刻表现成"界面不动"这种**显性**故障的纪律 ——
   **不会变成一种新的静默 bug。**

第 2 条是这个取舍的真正价值: 它把一类可能的静默错误换成了一类已知的显性错误。

### R6.2 为什么合并不影响正确性

一次爆发里的 N 次 fire 攒成一帧, 那一帧读到的是最新数据、标的是最新 Seq,
**中间那些版本本来就没人需要看见**(这正是"中间态可塌缩"的定义)。

### R6.3 为什么 worker 不加定时器

ws 的合并是**机会主义**的: 没有任何定时器, 只有在 worker 正忙着处理上一轮时,
新来的 fire 才会被攒到下一轮。

* **系统不忙时零延迟**(来一个发一个);
* **系统忙时自动省帧**, 省的正是那些"反正马上要被下一帧覆盖"的中间态。

**这是免费的。** 加了定时器就变成拿延时换带宽 —— 那是另一个取舍, 而且是一个需要调的旋钮。
反过来把合并去掉("为了更实时")也不行, 理由同上。

### R6.4 白捡的一件事

"要不要发这一帧"的判断**就是这个快照指针本身** —— 旧 state 就在指针里, Load 一下就能比。
不需要额外在内存里留一份状态拷贝去做比对。

### R6.5 机会主义合并有一个没写出来的前提: 脏标记什么时候清

R6.3 那句"只有 worker 正忙时新来的 fire 才攒到下一轮"听起来只是描述,
但它**依赖一个具体的实现细节**, 而这个细节漏写过:

> **脏标记必须在读库之前就取走并清空, 不能等这一轮做完再清。**

    正确:  roomIds := takeDirty()          // 锁内把整张表换走, 就地清空
           for _, id := range roomIds { rebuildAndBroadcast(id) }   // 读库发生在清之后

    错误:  for id := range dirty { rebuild(id) }
           clearDirty()                    // 读完再清

**错的那种会吞掉一次 fire**: 读库之后、清标记之前到达的那次 fire, 它的标记被这一轮清掉了,
而它带来的变更**并没有进这一轮读到的数据里**。界面停在旧数据上, 直到下一次别的 fire 把它带出来。

**这条比"忘了 fire"危险**, 尽管症状一样:

* "忘了 fire"是**显性**的 —— 那条路一次都不动, 一测就出来(这正是 R6.1 那个取舍的全部价值);
* 吞 fire 是**竞争窗口** —— 平时全绿, 只在"读库刚好慢一点 + fire 刚好落在那个窗口里"时丢一帧。

所以它值得单独进检查清单(执行手册 D24), 查法就一句: **看"清脏"和"读库"两句谁在前。**

## R7. 为什么需要"条件四": 连接活着 != 房间活着

这条**不在** [`deliveryGuarantee.md`](deliveryGuarantee.md) 上, 因为它**只在"推内容"的形状里存在**,
是优化自己制造出来的。

客户端在等进房应答期间不能直接应用广播(那些帧的基准还没确定), 于是协议里多了一个**冻结点**:

> 只要那份应答永远不到, 房间就永远停在旧数据上 —— 而**连接是健康的, 心跳照跑**,
> 连接级探活(心跳 + 读超时)**完全看不见它**。

推广成通用规矩:

> **凡是"我在等 X, 在等到之前收到的东西不能直接用"的状态, 都必须有:**
> **(a) 一个独立于连接的超时把它踢回去重来;**
> **(b) 一个内存上限 + 溢出时的有效降级。**

### R7.1 这条真的漏过一次, 而且漏在最不像的地方

漏网的不是 ws 上的等待, 是**"等一个 ajax"**:
整页重拉在飞期间, 该房间的推送和进房应答一律丢弃, 而那几个 POST 请求**没传超时**。

于是: 连接是健康的; ws 那边的进房超时**也不会响**(每次都收到了应答, 只是被丢掉);
房间就永远停在旧数据上。

**修法**: 给那类请求加统一超时, 并把规矩写进注释 ——
凡是在"重拉计数 ++ 和 --"之间 await 的请求都必须带上它。

**教训**: 找冻结点时, **不要只找"等一个 ws 帧"的地方**。任何一个"在等 X 期间丢弃/缓冲"的分支都算。

### R7.2 有了缓冲之后为什么还要留房间级超时

缓冲只是让**等待期间的帧不丢**。
一个刚打开页面、手上什么都没有的新客户端, **没有快照就是白屏** —— 缓冲再多也渲染不出来。

超时值直接**复用连接读超时, 不新增配置项**: 正常应答是毫秒级的,
真慢到读超时那个量级, 读超时那条路本来也已经把连接判死了。

## R8. 为什么每条降级路径必须写出"再来一次哪里不一样"

优化必然带来上限(单帧上限、缓冲上限、补拉条数上限、客户端缓冲上限),
有上限就必然有降级路径("这次我给不了, 你退回去用笨办法")。

**降级路径的唯一正确性要求:**

> **触发降级之后, 下一次尝试的输入必须严格改变(游标前进 / 队列排空 / 基准更新)。**
> **否则就是活锁 —— 不是"慢一点", 是永远不收敛。**

### R8.1 一条"无效降级"长什么样

**"正文太长 → 让你整页重拉"** 就是无效的:
全文有多大, 和你重拉过几次**没有任何关系**。重拉完还是那么长, 于是再降级, 于是无限重拉。

**有效的对照**: "缺的消息太多 → 整页重拉"是有效的, 因为**重拉真的把游标推到最新了**,
下次要补的条数变少。

**两者看起来是同一个动作, 有效性完全相反** —— 这就是必须逐条写出第三列的原因。
类一的"太大"只能靠"客户端申报基准 + 服务端只回差值"解决。

### R8.2 进房应答接不上时为什么不能原样再进一次房

基准没变, 答案也不会变 —— 死循环。只能整页重拉换一份新基准。
这是同一条规矩在客户端的落点。

### R8.3 "让你整页重拉"这条路的完整判据

R8.1 那两个例子(正文太长 vs 消息缺太多)看着是同一个动作、有效性却相反。
把它们分开的判据只有一句:

> **"你去整页重拉"有效, 当且仅当"这次应答有多大"是客户端申报游标的函数。**

它的全部作用是让客户端**换一份新游标再来问**。拉完再来问, 如果答案还是一样大,
那这条路什么都没改变 —— **那不叫降级, 那叫定时白拉一次的死循环。**

由此推出一条**协议层面**的硬规矩, 而不只是"降级路径要收敛":

> **进房应答里的每一样东西, 要么它的大小被某个客户端游标管着(拉完就变小), 要么它就不该在应答里。**
> **没有第三种情况。**

### R8.4 这条硬规矩是真踩出来的: 一个大小由用户决定的字段

**用户输入框里还没发出去的草稿**, 跟着会话状态整份进了进房应答。
粘一段几百 KB 的日志进输入框, 应答就超上限, 于是回一句"你整页重拉"——
拉完再进房, 草稿还是那么大, **永久循环**。

它同时犯了两条:

* **(a) 推送这一侧根本没有消费者。** 前端确实把它收下了(赋值给了变量),
  但只有普通拉取那条路会去读它, 推送这两条路一次都没读过。
* **(b) 它的大小由用户决定, 而且不属于任何一个客户端游标。**

**最坏的是症状完全静默**: 普通拉取那条路**没有体积上限**, 所以界面一切正常、内容照常显示,
只是每隔几秒白烧一次全量拉取, **没有人会发现**。

**修法不是给它做降级, 是把它从推送这条路上摘掉**(组装应答时清空一下, 普通拉取那条路照常给全)。

这是同一个形状的第三次犯病, 前两次只犯了 (a) —— 一个"最后活跃时间"字段和一个版本字符串,
每批变更都在动、推送侧没人读, 前者一度占了 **77% 的推送量**。
**只犯 (a) 是白烧带宽; (a)(b) 一起犯是永不收敛。**

于是有了一条逐字段的检查(执行手册 D23), 两句话:

> **(1) 推送这一侧谁读它?** 找不到就别放进来。
> 注意"前端把它赋值给了某个变量"**不算读** —— 要找的是用它渲染或做判断的地方。
> **(2) 它的大小谁说了算?** 用户能决定大小的, 要么不进推送, 要么必须落在某个游标里。

这条和"信封 64 字节"(R11)是一对: **一个管信封, 一个管负载。**
类三那一桶尤其要盯 —— 它是整份覆盖, 所以桶里任何一个字段变胖,
代价都要乘上"这一桶发了多少帧"。

## R9. 为什么"缓冲装不下"只许断线

**这一章的结论推翻了它自己的前一版。** 前一版是"丢帧但留着连接, 事后补一帧告诉你重新对齐",
连带三笔写缓冲账、兜底帧、按房间去重。**全部删掉了。**
删掉的过程比结论有价值, 所以 R9.2 把它完整留着 —— **想加回来的人先读那一节。**

### R9.1 结论和三个理由

> **凡是"缓冲装不下"引起的异常, 唯一允许的处理是断开这条连接。**
> 服务端写队列装不下一帧 → 关连接; 客户端等待缓冲装不下一帧 → 关连接。
> **不丢帧、不记账、不事后补发。**

**1. 测不到的概率极高 —— 这是最重要的一条。**
"丢帧然后补救"那条路只在灾难时才走, 真实环境几个月碰不上一次, 只能靠模拟器人造。
而断线重连是**天天都在走**的路(网络抖动 / 切 WiFi / 服务重启 / 合盖), 被反复验证过。

> **与其给兜底另修一条只在灾难时走的路, 不如让灾难走那条天天都在走的路。**

**2. 状态组合爆炸。**
"丢帧但留着连接"要求两端同时维护一堆跨帧的状态: 哪个房间丢过、补救帧有没有在队列里排着、
缓冲作废了没有。这些状态的 bug **只在特定到达顺序下出现**, 正确性无法论证。
断线只有一个状态转移: 连着 → 断了 → 重连 → 全部房间重进。

**3. 在这个架构里断线是安全的** —— 这条是前提, 不成立的话前两条都白说。
"我抄到第几页"存在**客户端**手上(进房时申报的那些游标), 服务端不为任何客户端保存进度(R14)。
**补齐由重连流程负责, 不由推送路径负责。**

**这也是业界的统一做法**, 没有一家在长连接上做"丢这一帧但留着连接":

| | 上限 | 超了怎么办 |
| --- | --- | --- |
| Redis pub/sub | `client-output-buffer-limit pubsub 32mb 8mb 60` | **关闭连接** |
| NATS | `max_pending` 默认 64MB | 标记 Slow Consumer → **服务端断开** |
| gorilla/websocket 官方 chat 示例 | 发送 channel 满 | 认为客户端已死 → **注销并关闭** |

补齐方式也一样: 重连之后把错过的从主库读回来 —— 就是"重新进房带游标"。

### R9.2 被删掉的那一版: 一条修补链是怎么长出四个设计的

**这一节是反面教材, 完整保留。** 它是"降级路径要收敛"这条规矩最贵的一次学费。

起点是一个看起来很合理的决定: **队列满了就丢这一帧, 但别断连接**(丢的只是一帧广播, 便宜)。
然后每一步都是上一步逼出来的:

    1. 丢了帧, 客户端不知道自己少了一段
       -> 得事后补一帧"我丢过东西, 你重新进房"(resync)

    2. 那一帧 resync 自己也在同一个满了的队列里, 也会被丢
       -> 得给它单开一笔预算, 保证它在别的账满了的时候还发得出去    ← 三笔账的由来

    3. 那笔预算的容量算不出来 (见下面那个"重试轮数"的坑)
       -> 只好按房间去重: 队列里已经有一帧就算作已发                ← 去重的由来

    4. 去重会漏 (去掉的那一帧和留下的那一帧配对 Id 不同)
       -> 客户端处理这类帧时**不许看配对 Id**                       ← R10 那条的由来

**四个互相咬合的设计, 服务的是一个"关掉连接"就不存在的问题。**

第 3 步那个算不出来的账值得单独记, 因为它是**降级路径普遍长这样**的一个标本:

    第一版按"房间数 × 每帧大小"算容量, 穿了, 症状是某个场景十次红一次。
    漏掉的因子是**重试轮数**:
        发兜底帧 -> 客户端整页重拉 -> 重拉完再进一次房 -> 那时账多半还满着 -> 又要一帧兜底 -> ...

> **降级路径基本都是环。只算第一轮就会少一个因子,**
> **而这个因子在一条连接的写超时窗口里没有上界。**

当时的修法是"让那个上界真的成立"(去重), 而不是"把数字调大"——
**方向是对的, 但整条链的存在本身才是问题。**

### R9.3 由此少掉的东西, 以及为什么分账不是目的

* **写队列不再分账。** 分账的**唯一**理由是"补救帧必须在别的账满了的时候还发得出去"。
  没有单独发的补救帧, 这个理由就不存在了。
  **分账从来不是目的, 它是那条修补链的第 2 环。**
* **没有 resync 帧, 没有空的兜底帧, 没有按房间去重。**
* **R10 那条结论(指令帧不许按 id 丢)仍然成立**, 但它的理由换了 —— 见 R10。

**唯一一处不占账的帧是 `deny`**(终态信号, 发完连接就没了):
让它绕过上限直接排进队列是一个三行的特例, **不是一笔账**。

### R9.4 断线和"扇出不阻塞"不冲突

**扇出时绝不同步阻塞在慢连接的 write 上** —— 否则一个弱网页面能拖住整个房间(队头阻塞)。
**关连接是 O(1) 的内存操作**, 广播循环照样不等任何人。

### R9.5 "帧不丢"和"id 对齐"是两件事

> **同一条连接上"帧不丢"由传输层保证(FIFO + 装不下就断线), 不由 id 保证。**
> **id 只负责"跨来源"(快照 vs 广播)的对齐和剔重。**

**想清楚这条分工能省掉一堆假想的连续性检查。**

两个直接推论:

* **类三的 Seq 会跳号, 不许拿它判连续** —— 一个没有客户端可见变化的版本压根不发帧,
  所以"号不连续"是正常现象, 不是丢帧。
* **传输上的缺口不存在了。** 队列装不下的那一刻连接就断了,
  **没有"连接还在但中间少了一段"这种状态。**
  内容上的缺口仍然由各桶自己的 id 发现(混沌测试里真的观测到触发过)。

> 注意这条比上一版**强**: 上一版是"传输缺口由 resync 发现", 两条路都得是活的、都得有场景压。
> 现在只剩一条路。

### R9.6 容量账的性质变了

容量账从"正确性前提"降级成了"调参": 算错的后果是"没事就断一次线", 不再是活锁。
**账还是要算, 但它现在只回答一个问题: 这个数够不够大, 让正常操作碰不到断线?**

**不过这里有一个容易写错的论证, 单独记一下。**
"断线为什么是有效降级"不能答成"重连时客户端会申报当前基准" ——
断线**可能发生在应答写出去之前**, 那时基准根本没变, 下一次的输入和这一次完全一样。

> **真正严格改变的输入是"队列/缓冲被整个清空了"**, 这一条无条件成立, 和基准变没变无关。

**这个区分不是抠字眼**: 按 R8 那条规矩, 第三列填错了就等于没验证过收敛性。
填"基准变了"的话, 恰恰是在最需要论证的那个情形(应答还没发出去就断了)上论证失败。

**顺带: 那个"单条连接同时进几个房间"的因子, 按一个页面真的会进几个算就行,
不用按系统强制的进房上限算。** 那个上限是防 bug 导致的无限进房用的, 不是会被正常用满的数;
而且**同时进的房间不等于同时有流量**, 按上限乘出来的是一个不会发生的最坏值。

## R10. 为什么指令帧绝不许按 id 丢弃

快照会过期, "你去重拉"不会 —— **它什么时候执行都是对的。**
按 id 丢掉它, 白白多绕一轮。

**推广**: 按"处理状态"的那套规则(比大小、剔重、配对)去处理**指令**, 就是这个错误。
指令没有状态, 也就没有新旧。

### R10.1 这条规矩的理由换过一次, 但结论没变

**这一节是提醒: 别因为老理由没了就顺手把 Id 判断加回来。**

老理由**更硬**, 是活锁级别的: 当时 `needFullReload` 是**单独一帧**,
而它**偏偏总是在队列积压时才发出** —— 到达客户端时对方多半已经超时重发过,
**配对 Id 必然对不上**。按 Id 丢掉它, 整条降级链上唯一能收敛的一环就断了。
(它同时也是 R9.2 第 4 环, 那个去重能不漏的唯一支点。)

那个形状已经删了(R9): 现在 `needFullReload` 不是一帧, 是搭在进房应答上的一个布尔字段,
和快照同一帧, **结构上丢不掉**。

**于是老理由消失了, 但结论仍然成立** —— 现在它的理由是纯粹的"指令没有新旧"。
从"活锁"降级成了"白绕一轮", **规矩本身一个字不改。**

## R11. 带宽: 帧信封那 64 字节是怎么省出来的

实测: 每帧信封从 **171 字节降到 16 字节**(模拟器口径; 生产一帧变更约 36 字节)。
换编码之前**一批正文才 24 字节 —— 89% 的带宽花在信封上**。

**逐个记下来, 免得有人顺手加回去:**

| 拿掉的 | 省了多少 |
| --- | --- |
| 房间名字符串("房间类型:" + 20 位 id) → 整数句柄 | 每帧 30+ 字节 |
| 房间纪元字符串 → **删掉**, 句柄兼任纪元(R4.6) | 每帧十几字节 |
| 可读字段名 → **整数键**(**这一步是大头**) | 164 → 37 字节。只换二进制不换键: 164 → 136 |
| 一个每批变更都换新值的版本字符串 → **删掉**(那一侧只写不读) | 它是"491 字节的状态桶每帧都重发"的**唯一原因** |
| 状态桶整份带 → 字段级 diff(缺席 = 没变) | 每帧几百字节 |
| 只带正文/消息的帧不再带 Seq(它们的应用幂等) | 每帧几字节 |
| 一整屏 TUI 黑框(每帧 1KB+)→ 移出推送, 改成前端 1 秒一轮轮询 + 版本号短路 | 每帧 **1183 → 37 字节** |

### R11.1 为什么不是 protobuf

同样裁剪下约 33 字节, **和整数键 msgpack 打平** —— 两者本质同构(整数标签 + varint + 长度前缀)。

体积既然打平, 就选**不需要 schema / 代码生成 / 前端 runtime** 的那个。
这是简单性在"前四项打平"时行使裁判权的一个标准例子。

### R11.2 为什么不改成定长数组(还能再省 5 字节)

那就把"**未知键忽略**"这条唯一的可升级性卖掉了。5 字节买不到这个。

### R11.3 那个 TUI 黑框: 一次完整的选型弯路

它曾经放在类三那一桶里。判据"整份小"看着是满足的(1KB 出头)。

**错在"小"要按每帧算, 不是按"一次看着不大"算**: 它**每帧都在变**,
于是每帧背着它的全量, 而且服务端算每一帧增量时还要多查它一次。

拆回"前端 1 秒一轮拉 + 版本号短路"之后, 帧从 1183 字节回到 37 字节,
换来的代价只是把 0 秒变回 1 秒 —— 而那一桶本来就是"差一秒没人在乎"的东西。

### R11.3.1 但真正的结论不是"改成轮询", 而是"别占每一帧的信封"

这个案例很容易被总结成"这种东西改轮询就对了"。**那是一个过度概括, 执行手册里已经改掉了。**

真正被证明的只有一件事: **一桶"变得很勤 + 每次都得整份带"的数据不能进类三** ——
它的成本是 `变更次数 × 整份大小`, 而它把两个因子都顶满了。

把它从每帧信封里拿出去有两条路, 而**当时的记录里没有写为什么选了后一条**:

* **(a) 退到类四(戳一下) + 客户端合并连续的戳。**
  成本随"真的在看的人"走, 没人看就一次查询都不发生, 合并间隔就是延时旋钮。
* **(b) 前端定时轮询。**

**(b) 是一次优先级倒挂**: 它是整套设计里**唯一一个 O(在线人数) 的常驻负载**,
顶在**并发**(第 3 优先级)上, 换来的只是省**带宽**(第 4 优先级)。
按 R2 的取舍规则, 这本来是不允许的。

所以执行手册把顺序写成了"先试 (a), (a) 不行才 (b)", 并给 (b) 定了四个准入条件
(纯内存查询 / 只有打开面板的人才拉 / 版本号短路 / 串行循环)。
**(b) 唯一站得住的场合是: 上游根本没有可靠的 fire 点 —— 说不清它什么时候变了, 所以戳不出来。**
一旦那一桶的查询变成一次真查库, 它就是性能炸弹。

**这条和 R14 "不要轮询兜底"不冲突**, 两者是不同的东西:
兜底轮询是**并行的第二条**可靠性路径(专门用来掩盖第一条的 bug, 而且永远没人测);
2b(b) 那个轮询是这一桶**唯一的一条**路径 —— 走通走不通都在明面上。

### R11.4 还有一件事: 别让零值上线

计数从 0 起算、编码器跳过零值 —— 否则"戳一下"那几类帧会白背一个恒为 0 的 `Seq`。
**这是真踩过的。**

> **守这条的东西换过一次。** 当时的理由是"兜底帧那笔账只有 64KB(模拟器里 2KB),
> 每帧多九个字节就能把它的容量削掉一成"。那笔账已经没了(R9)。
> **现在守它的是"每帧信封 <= 64 字节"那条硬断言** —— 加字段之前先看它还剩多少。
> 规矩没变, 但记账的地方变了。

同理: **只有"重放会出错"的帧才带 Seq。**
判据是"重放会不会出错", **不是"带没带状态桶"** ——
后者会漏掉"同一条命名空间下的第一截正文也是整份替换"那一格(也是真踩过的)。

## R12. 压缩: 为什么它不许进任何一条带宽账

**压缩是唯一一处"配错了也完全不报错"的优化。**
没谈成 / 模式选错 / 阈值调过头 —— 三种情况下功能全都正常, 别的用例全绿, 只是线上字节多几倍。
而且应用层永远看到明文, 一个字节都不会变, **所以只能到 TCP 那一层去数字节**。

### R12.1 第一版的检查点写错了, 记在这里免得再犯

第一版只有一条 "每帧线上字节 <= 64", 并声称它能抓阈值退化。

**它抓不到**: 阈值调到 1 时每帧是 54 字节, 照样 <= 64, 一路绿着过去。
(顺带还把大帧从 0.080 倍拖到 0.101 倍, 而"小于明文 1/5"那一关也拦不住 0.101。)
也就是说"阈值被调小"这件事当时**三关全都不会红**。

**根子在判据的形状:**

> **"压缩配错了没有"只能拿线上和明文比, 不能拿一个绝对数字比** ——
> 绝对数字同时受编码和压缩两件事影响, 于是哪一件都判不准。

反过来那条绝对数字也不能被比值替代: 信封加了字段时明文和线上一起涨, 比值照样绿, 只有绝对数字会红。
**所以必须是两条。**

**"新场景必须做变异验证"这条纪律就是防这个的, 而第一版偏偏只对第 1 关做了变异验证。**
现在两条都变异验证过(阈值改 1 → 当场红: 线上 10874 vs 明文 7274)。

### R12.2 反直觉的实测: 小帧压不了, 而且越想压越亏

真 TCP 字节:

| 压缩阈值 | 最热的小帧 | 一条 5100 字节的消息 |
| --- | --- | --- |
| 1 | 每帧 **54** 字节 | 514 字节(0.101x) |
| 128 | 每帧 **40** 字节 | 406 字节(0.080x) |

把阈值从 128 调到 1(= "让最热的那类帧也进压缩器"), **小帧变大 35%, 连大帧都跟着变差**。

**原因在 Go 标准库, 不在 ws 库**: 两个 ws 库都把压缩级别写死成 `BestSpeed`,
而级别 1 的 `encSpeed` 对**一次 flush 不足 128 字节**的块直接放弃 LZ77、只做 Huffman
(16 字节以下干脆 stored), 并且顺手 `bestSpeed.Reset()` 把匹配表清掉。

于是小帧进压缩器**两头亏**: 自己压不动反而多个块头, 还把后面大帧赖以生存的滑动窗口给清了。

### R12.3 那条纪律

> **任何一条带宽账都不许把压缩算进去。**

理由: 那 64 字节必须靠编码本身站住, 因为**压缩一旦顶在前面, 编码退回 JSON 也测不出来** ——
重复几百遍的字段名恰恰是 deflate 最擅长压的东西, 压完看着一点都不大。

**这也是"压缩必须排在编码之后做"的全部理由。顺序反了, 那条检查点就再也没有牙齿。**

### R12.4 换 ws 库的账

要的就是**保留压缩上下文**这一项。
有的库把 `client_no_context_takeover` 写死在握手串里、没有开关,
而不保留上下文时每条消息都从空字典开始, 大块 JSON 差一个数量级。

代价是没有读写 deadline, 超时要改成 ctx(读写各一处), 语义一样。

## R13. 测试方法论的由来

### R13.1 为什么"打印"不算覆盖证据

场景里打印出来的"这条路走到了 N 次", 如果它是覆盖证据, **就必须是断言而不是打印** ——
光打印的话它悄悄变成 0 也没人会发现。

> **一个从来没红过的分支, 和没写的分支一样可靠。**

### R13.2 为什么覆盖证据要两头都断

结尾那句"于是走到了 Y"要断言, **开头那句"我已经把环境弄成 X 了"同样要断言**。
只断结尾的话, 环境没弄成的那些轮次会**安安静静地绿着过去**。

**这个形状踩过两次**: 一次漏的是前者, 一次漏的是后者。

### R13.3 为什么每个新场景必须做变异验证

把被测逻辑改坏, 看着它当场变红, 再改回来。**没红过的场景不算数。**

真实例子: 把客户端的进房缓冲改回"直接丢", 三条断言各自当场变红 ——
正文停在 90/150 字节 / 消息 3/7 / 状态停在旧值。
**三个都是"已对齐=true 连着=true 序号连续"的静默症状** —— 正好是最坏那一类,
说明这三条断言是有效的。

### R13.4 为什么进房窗口的三桶要各压一遍

只灌正文的话, **消息和状态那两段判断根本不会被执行到**。
一桶的 id 写错不会被另一桶掩盖 —— 反过来说, 也就抓不到。

**两个陷阱:**

**(1)** 压状态桶那一半只能改**一次**状态。
改两次(A → B → A)会被 worker 合并成"和快照相比没变", 一帧都不发, 窗口就白开了。
**机会主义合并在写场景时是个陷阱。**

**(2) 这组场景本身依赖 R5.2 那一帧 `roomHandle`。**
窗口撑开期间客户端还没收到进房应答, 认不出句柄就整帧扔掉 —— 于是 A 段"剔掉了"、B 段"没重复",
**两段都绿, 而实际上一帧都没进过缓冲。**
这是 R13.2("覆盖证据要两头都断")最该被用上的地方:
先断言"这个窗口里客户端确实缓冲到了 N 帧", 再断言"重放之后收敛到了 X"。

### R13.5 为什么值得独立重写第二遍

模拟器是把同一套协议**独立重写的第二遍实现**, 跑真 TCP、能注入网络故障、
参数按生产等比缩小 32 倍(为了让 stall 几毫秒就顶满缓冲)。

**它的价值不在"多一份测试", 在于它会用不同的方式把同一个形状实现一遍 —— 形状错了两边对不上。**

### R13.6 一个值得记住的观察

**至今被压出来的正确性洞, 全部来自随机压测和故障注入, 没有一个是看代码看出来的。**

这条和 R3.2("并发不许用压测判")不冲突, 两者是分工:
**正确性靠压测和故障注入发现, 并发靠读代码判定。**

## R14. "明确不做"清单里几条的完整理由

执行手册 §10 那张表给了结论, 这里补理由。

**不要轮询兜底。**
指的是"推送之外再挂一层定期拉取, 防止漏"。
它掩盖问题(真正的 bug 被兜底遮住, 变成"偶尔慢一下"), 制造**没人测过的代码路径**,
而且是常驻开销换一个概率性的好处。
**正确的替代是把失效场景写成能自动跑的测试** —— 这条在 R13.6 那个观察下尤其成立。

**这条不禁止 R11.3.1 那种"某一桶就是靠轮询取数"的做法**, 两者的区别是:
兜底轮询是**并行的第二条**路径(它的存在就是为了遮住第一条的失败);
2b(b) 那个轮询是那一桶**唯一的一条**路径, 坏了当场就看得见。
不过 2b(b) 有它自己的准入条件和优先级倒挂问题, 见 R11.3.1。

**不要服务端为每条连接存正文游标。**
客户端本来就免费知道自己的偏移。服务端存一份反而要处理"这份游标什么时候过期"的一整类新问题,
外加 O(连接数) 的常驻内存。

**不要反馈式窗口 / 阻塞流控。**
一个弱网页面就能拖住整个房间(队头阻塞)。
断开那一条连接的代价只落在**那一个**客户端身上(它重连、重新对齐一次), 而阻塞的代价是**所有人**一起等。

**不要把"装不下就断线"改回"丢帧但留着连接"。**
这正是 R9 删掉的东西。想加回来之前先回答一句:
**那一帧"我丢过东西"自己被丢掉时, 谁来收敛?** —— 答不上来就是活锁。

**不要无界队列("那就别让它装不下")。**
内存有硬上界这件事是设计的一部分, 不是缺陷。代价只是让那一条连接重连一次。

**不要给"你整页重拉"加第二种含义。**
它就是"这次应答太大, 你换条路去拿", 到此为止(R8.3)。
想表达别的(我出错了 / 我丢过东西 / 你重连一下), 每一件都有自己的路:
接不上走重新进房, 缓冲装不下走断线, 终态走 `deny`。
**一个字段一个含义, 客户端才只需要一个动作** —— 多出来的每个动作都要自己的收敛证明。

**不要往进房应答里加"大小由用户决定、又不在任何游标里"的字段。**
见 R8.4。症状是完全静默的死循环。

**不要把各桶的 id 合并回一个。**
两个后果: 必然要一把包住 DB IO 的锁(R3); 一桶判错会表现成"整个房间不收敛", **分不出是哪一桶**。

**不要"统一形状"。**
这是唯一一条反直觉的: "所有数据走同一套 id 机制"看起来更简单,
但它换来的是一把包住 DB IO 的锁, 以及不可诊断性。
**那不是简单, 那是把复杂度藏进了一个更糟的位置。**

**统一形状本身没有价值, 省下来的字节和 RTT 才有。**
