# 多节点分布式通知 — 理论分析

> **注意:本文仅理论分析,未实践,未跑过真实多机。**
> 没有性能 / 可靠性需求时,**尽量用单体(单进程房间表)**,正确性风险最小。
> 本文只回答两个问题:这类问题看起来有没有办法解决?要不要改库本身?
> 结论:有办法,且全广播那一档**不用改库**。真要上生产请自己验证。

约束(讨论的前提):

- **不引入 pub/sub 总线**(不用 Redis / NATS / Kafka 当消息总线)。
- 分布式 = **数据库分布式**(默认多个 mysql,也可能拿 Kafka 当库)+ **本库的多个进程**。
- **不轮询**数据来找变化;节点之间宁可直接交互,也不靠定时拉。

---

## 核心:只有一个真问题

ws 层一个客户端只连**一个**节点,`RoomEnter` 发生在那个节点上。
房间 R 变了(某节点 `FireChange`),唯一的难点是:

> **R 的订阅者坐在哪些节点上?怎么把"戳一下"送到那些节点?**

其余都是这个问题的派生。把它拆成**两个正交的旋钮**,所有场景都能归位:

### 旋钮 1:连接落点(ws 连到哪个节点)

跟"房间"无关,只跟"用户"有关。LB 按 `userId` 一致性哈希 → 一个用户永远落同一个节点,
**一条 ws 连接搞定他订阅的所有房间**,无论他在几个房间里。

- "用户多 / 每个用户房间多" → 按用户分节点。对。
- **不要按房间分连接落点**。否则一个用户在 N 个房间就要连 N 个节点,退化成灾难。
  所以"按房间分"在连接层基本不出现。

### 旋钮 2:FireChange 怎么扩散到有订阅者的节点

- **2a 全广播**(mesh,发给所有 peer):零路由表,最简单。
  适合**小集群**,或**几乎人人都订阅那几个房间**(用户多 + 房间少 + 每个用户都注册)——
  这时订阅节点集合 ≈ 全部节点,维护路由表纯属浪费,直接广播。
- **2b 按房间的"订阅节点表"裁剪**:每个节点在本地有人进 / 退房时,往共享 DB upsert 一行
  `(roomId, nodeId)`(或经 mesh 通知 peer)。**这张表只在进 / 退房时变,不是每条消息变,所以不是轮询**,
  完全符合"DB 分布式 + 多进程 + 不轮询 + 不上 pub/sub 总线"。
  `FireChange` 时查这张表,只发给真正有订阅者的节点。适合**大集群 + 稀疏订阅**。

### 常见场景如何映射

| 场景 | 落点 | 扩散 |
| --- | --- | --- |
| 小集群 / 大多数房间人人订阅 | 按 user | 2a 全广播 |
| 大集群 + 稀疏订阅(用户分散在很多房间) | 按 user | 2b 订阅节点表 |
| 单个超热房间(直播弹幕 / 名人房,百万观众散落全节点) | 按 user | 折叠回 2a:这个房间天生活在所有节点,订阅节点表 = 全部节点,等价广播 |

所以"按用户分"和"全广播"不是并列的两类,而是 **落点(永远按 user)× 扩散(广播 or 路由表)** 的两种组合。
超热房不是新模式,折叠进广播。其余类型出现概率很低。

## 成员发现:走 DB,别单独开机器

节点之间互相发现用**共享 mysql 一张表**:

```
nodes(nodeId, addr, heartbeatAt)
```

每个节点每几秒 upsert 自己的心跳、读一遍表知道有哪些 peer;死了就是心跳过期被别人发现。
零额外组件、零单点。

**不要为成员发现单独开一台 / 两台机器**——那是在重新发明 Consul/etcd 式注册中心:
一台 = 单点;两台互备 = 又要处理 2 节点脑裂 / 一致性,把想躲开的 HA 问题请了回来。
既然约束就是"DB 分布式",成员发现走 DB 表是最省的。
(读这张表很低频,只在节点上下线时才有意义,不算"轮询数据找变化"。)

## 节点互联:mesh 转发 + 两个坑

用的就是本库已有的两半:每个节点照常跑它的 ws/https server(`ServerManager`),
同时作为 `Client`(或一个内部 http endpoint)去连别的节点。
`FireChange` 跨节点 = 收到本地业务事件时,本地 `FireChange` 一次 + 把同一事件转给(广播档的)所有 peer
或(路由档的)订阅节点,peer 收到后各自做**本地** `FireChange`。

不"trivial"的就两处:

1. **防回环**:A 把事件转给 B 时,B 只能做**本地 fire**,绝不能再转给所有 peer,否则广播风暴。
   做法:区分"本地业务产生的事件"(要转发)和"从 peer 收到的事件"(只本地 fire,不再转)。one-hop。
   忘了就炸。

2. **别依赖跨节点的 `ChangeSeq` 对齐**:`ChangeSeq` 是每节点每房间各自单调的,跨节点对不上——
   但这**正好不用管**。可靠性锚点是 DB 里的**业务消息序号**(见 [`../example/ReliableChat/`](../example/ReliableChat/)),
   ws 只负责"戳一下"。客户端只跟自己那个节点说话,看到的是那个节点单调的 `ChangeSeq`;
   只要戳到了,它就按业务序号 ajax 补齐。**这套架构天生吸收了跨节点 `ChangeSeq` 不一致**——
   这也正是它能"开个 server 写写就行"的根本原因。

连接重连、节点上下线,`Client` 那半本来就自带。

## 要不要改库本身?

- **2a 全广播:不用改库。**
  `FireChange(RoomEvent_t)` 已是公开方法。转发完全在应用层:本地 `FireChange` + RPC 给 peer,
  peer 收到调自己的 `FireChange`。防回环也是应用层(按事件来源区分),库无感知。

- **2b 订阅节点表:可能要给库加一点点只读能力。**
  维护 `(roomId, nodeId)` 表需要节点知道"本地哪些房间有订阅者 / 进退房事件"。
  目前 `GetSnapshot()` 只给计数,没有"枚举本地房间 / 某房间本地是否有订阅者 / 服务端进退房回调"。
  所以 2b 真要做,大概率要给 `ServerManager` 加一个**只读查询**(列出本地房间,或查某 room 本地有无订阅者)
  或一个**服务端进 / 退房事件回调**。是小改动,且只在上大集群时才需要。**用之前请确认当前 API 是否已够用。**

一句话:**全广播档现在就能搭(不改库);路由裁剪档要等真有大集群需求时,给库补一个只读的本地房间查询。**

整体难度不大,但本文未经真实多机验证,生产前请自行实测。
