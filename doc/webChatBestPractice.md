web + app 聊天室 实时消息通道: 方案选择判据 与 最优做法
======================================================

本文回答两个问题:
    1. "戳一下 + 拉取"(hgmRoomNotify 模型) 和 "推内容 + 序号" 之间, 按什么判据选?
    2. 具体到 web + app 的聊天消息实时通道, 最优方案的协议长什么样?

写这篇的起因: 拿 hgmRoomNotify 做聊天正文, 实测出现 "ajax 泛滥"(一个客户端一分钟十几个 ajax)
和 "1.5 RTT 才看到内容". 追下去发现不是调参问题, 是模型和场景的匹配问题.

结论速查:
    * 聊天正文 / AI 流式吐字 -> 推内容 + 序号, 缺口补拉. 不要用纯戳.
    * 配置更新 / 软件自动更新 / 未读数 / 在线状态 / 会话列表排序 -> 纯戳最优, 用 hgmRoomNotify.
    * 例外: 弹幕型刷屏房间(速率快到用户只看得了最后 N 条) -> 纯戳重新变得有效,
      见第一部分"判据一的例外". 判定门槛: 消息速率 × 拉取间隔 > 可视窗口条数.
    * deliveryGuarantee.md 那 8 条正确性必须, **两种模型都要满足**, 一条都不能少.
      那篇文档是本方案的验收清单, 本文是它在聊天场景下的具体落地.


第一部分: 决策判据 (本文最有用的部分)
====================================

先纠正一个容易得出的错误结论: **不是 "纯戳过时了 / 不流行"**.
纯戳(业界叫 invalidation-and-refetch)在很多领域是主流甚至最优, 只是**聊天正文不在其中**.

纯戳的成熟应用: 缓存失效 / CDN purge、数据库 CDC -> 应用层缓存失效、
IMAP IDLE(用了三十年的 "有新邮件了, 你来 FETCH")、APNs / FCM silent push、
Figma LiveGraph(复杂查询结果订阅).

**Figma 的案例尤其重要, 因为他们是从"增量推送"主动退回到纯戳的.**
Figma 原文给出了纯戳成立的前提, 引用两句:

    "the larger part of client data is delivered due to **initial reads** rather than live updates"
    "we get a stateless invalidator and fast invalidations at the expense of over-invalidating
     hard queries ... **invalidations on active queries are infrequent**"

即: 数据主要来自首次读、变更稀疏. 还有一句对做单库项目的人特别有用 ——
他们早年在单 Postgres 上**不敢**用 invalidation, 因为
"the database was extremely sensitive to any spikes. **Issuing too many queries at once could
topple the database**", 是先把读端扩展了才敢切纯戳的.
这正是 "ajax 泛滥" 的根因, 而且说明纯戳有准入门槛, 不是无条件更简单.


判据一: 戳省的是"塌缩省", 中间态不可塌缩时收益为零
--------------------------------------------------
这是最本质的一条.

                          v1 v2 v3 的关系   客户端最终需要   戳的收益
    配置 / 未读数 / 状态量     替代           只要 v3         省掉 v1 v2 的传输
    query result             替代           只要最新结果     省掉中间几次重算
    聊天消息 / 流式 token      **累加**       **全部三条**     **0**

聊天里戳 3 次、客户端拉 1 次, 拉回来的**还是那 3 条完整内容**.
带宽一个字节没省(只省了 2 个帧头), 却多了 1 个 RTT + 1 次 DB 查询.

    纯戳的收益 = 塌缩率 × 内容大小
    聊天的塌缩率 ≈ 0, 所以收益 ≈ 0, 成本全留下.

这条同时解释了一个常见的错误直觉: "怕中间状态太多, 推过去客户端也没读, 全浪费了".
这个担心**只对可塌缩的状态成立** —— 那正好是 hgmRoomNotify 的设计前提,
也正好是聊天消息没有的性质.


判据一的例外: 消息速率远超阅读速率时, 塌缩率又回来了
--------------------------------------------------
上面那句"聊天的塌缩率 ≈ 0", 隐含前提是**用户最终要看全部消息**. 有一类场景不成立:
房间刷得极快, 而用户看的时候**只需要最后 N 条**(弹幕 / 直播评论 / 万人群刷屏 / 日志流面板).
被跳过的中间消息**根本不需要送达**, 塌缩率立刻就回来了 —— 只是塌缩发生在
"当前可见尾部窗口"这个单位上, 而不是单条消息上. 而"当前尾部窗口"是个**可替换的当前值**,
正好是 hgmRoomNotify 的模型.

    塌缩率 = 1 - 客户端实际需要的条数 / 服务端产生的条数

    普通聊天    用户要看全部, 比值 = 1                        -> 塌缩率 0    -> 纯戳收益 0
    弹幕房间    每次只要最后 20 条, 服务端一秒产 100 条        -> 塌缩率 90%+ -> 纯戳有效

发生条件可以算. 设可视窗口 N 条、客户端拉取间隔 T 秒、房间消息速率 R 条/秒:

    只有 R × T > N 时才真的发生塌缩.

N=20 / T=0.5s 需要 R > 40 条/秒. 门槛相当高, 所以这类场景**存在但不常见** ——
低于门槛时一条也没省下, 直接退回判据一的原结论.

越过门槛后, 另外三条判据也跟着翻转:
* 判据三(延迟): 内容被刷新的速度快过用户阅读速度, 单条晚 1 个 RTT 到已经没有意义.
* 判据四(扇出尖峰): **方向反过来**. "本房间最新 N 条"对房间内所有人是**同一个查询结果**,
  服务端算一次缓存起来供所有人拉 —— N 个并发读打在一个热缓存项上, 不是 N 个不同的 DB 查询.
  这恰好命中 Figma 的前提(拉取结果是共享的、可以只算一次).
  反过来推内容在这里是 O(速率 × 在线数) 的带宽, 速率越高越吃不消.
* 判据六(UI 即时性): 刷屏场景本来就没有"这一条必须立刻单独渲染"的诉求.

代价要认清: **接受历史空洞**. 客户端不再有"MsgIndex 连续就直接 apply"这条快路径,
只能整体替换尾部窗口, 中间那些消息本地就是没有. 若产品要求上滑能看完整历史,
仍然得留一条分页拉历史的路 —— 不过那条路本来就在(3.4).

所以它**不是另一套协议**: 就是 3.4 里"缺口过大 -> 只取最近 N 条 + 标记上方有空洞"
那条降级分支**被当成常态**跑. 同一个设计覆盖两端, 只是默认档位不同.

最后一个提醒: 到达这个门槛时, 先试**服务端批量推**(把 200ms 内的若干条合成一帧下发).
不改协议、不引入空洞, 就能消掉"每条一帧"的帧数开销. 只有当**内容带宽本身**成为瓶颈
(而不只是帧数)时, 才值得上纯戳 + 尾部窗口缓存.


判据二: 戳划算 iff "变更的描述" << "重算后的内容"
------------------------------------------------
    Figma      invalidation = 一个 query id(几十字节); 重算结果 = join 出的对象图(几十 KB);
               且大部分 write 不影响大部分 query          -> 大赚
    IMAP       通知 = 一个 EXISTS; 邮件带附件几 MB, 客户端可能只要 header -> 赚
    APNs/FCM   平台强制限制 payload 大小 + 隐私要求        -> 被迫用
    聊天       一条消息 200 字节, 戳 50 字节, 拉回来还是那 200 字节 -> **纯亏**

聊天消息的特殊之处: **变更本身就是一个小的、自包含的、完整的 delta**, 没有"重算"这回事.
戳和内容几乎一样大, 那戳就是纯粹多余的一个往返.


判据三: 延迟差距是结构性的, 且在最差网络下放大最厉害
--------------------------------------------------
    推内容  = 0.5 RTT
    纯戳    = 0.5(戳) + 0.5(请求) + DB 查询 + 0.5(响应) = 1.5 RTT + 查询时间

    网络             单程 RTT    推内容      纯戳
    好 wifi / 5G     20-40ms     10-20ms     40-80ms
    4G               50-150ms    25-75ms     100-300ms
    弱网 / 跨国      200-400ms   100-200ms   400-900ms

聊天"实时感"的心理阈值大约 100-200ms. **4G 上纯戳就已经跨过那条线, 弱网下差一个数量级.**
关键在于这个差距**不能靠优化消掉** —— 它是多了一个完整往返, 是结构性的;
而且它在最差的网络下放大最厉害, 那恰恰是移动聊天最常见的场景.


判据四: 扇出下的同步尖峰 (比"读放大"更精确的说法)
-------------------------------------------------
纯戳把"一次写"变成"N 个**时间上完全对齐**的并发读". 不是平滑的 N 次查询, 是**同步尖峰** ——
所有在线端被同一个戳同时唤醒, 同时打 DB. 这就是 thundering herd.
参考量级: Facebook memcached 一个 hot key 失效, DB QPS 从 1300 尖到 17000.

推内容则是服务端**自己控制节奏**的 N 次 socket 写, 节奏在自己手里.

缓解手段是给客户端拉取加随机抖动, 但那又给判据三的延迟雪上加霜 ——
**这两个目标在纯戳里直接冲突**, 没有同时满足的调参点.


判据五: 移动端耗电 (app 侧独有的硬伤, web 上不存在)
--------------------------------------------------
蜂窝 radio 的 RRC 状态机: connected 态约 200-400mA, 中间态约 40-100mA, idle 最低.
每次网络活动都可能触发一次 radio promotion, 并在之后保持 connected 一段 tail time 才降档.

    推内容: radio 唤醒一次, 数据已到手.
    纯戳:   戳唤醒一次 -> 客户端立刻又发一个请求 -> radio 被拖着多亮一会儿.

聊天是高频场景, 乘以每天几百次.


判据六: UI 反馈的即时性
----------------------
戳里没有"是谁发的、说了什么", 所以**收到戳的那一刻什么 UI 都做不了**, 必须等拉回来.
推内容可以立刻把气泡渲染出来. 这影响的正是聊天体验最核心的那一瞬间.


判据小结
-------
    纯戳适合: 变更稀疏、内容远大于变更描述、中间态可塌缩、扇出比低、延迟不敏感.
    推内容适合: 变更密集、变更本身就是小而完整的 delta、中间态不可塌缩、扇出比高、延迟敏感.
    纯戳还有第二个入口(判据一的例外): 变更**密到用户根本读不完**, 只需要尾部窗口 ——
      此时塌缩率重新变高, 且拉取结果全房间共享可缓存. 门槛是 R × T > N.

普通聊天正文六条判据全部落在"推内容"一侧. **这不是行业惯性, 是六条判据同时指向同一边.**
只有速率越过上面那个门槛的刷屏型房间会翻到另一侧.


第二部分: 一个被推翻的假设 (幽灵连接)
====================================

whyNotifyNotPush.md 优势第 7 条给纯戳记了一笔额外收益:

    "不给'在不在都不一定'的客户端白付内容传输代价 —— 对链路不稳、或连上了但其实不活跃的客户端,
     服务端只发了个极小的'戳一下'... 换成直接推内容, 这些'可能根本不会再读'的连接也得照付完整
     内容的传输成本."

那条自己就标注了"不确定、估计不大". 现在可以下判断了: **这个假设是错的, 这条收益基本为 0.**

原因很自洽, 甚至有点反讽 ——
**正是因为本库把 deliveryGuarantee.md 的条件二(主动心跳 + 读超时)做对了, 幽灵连接才极少.**
默认心跳 4.5s、读超时 10s, 意味着一条静默死链最多存活 10 秒就会被两端清掉.
所以"服务端在线连接集合"其实相当准确, 里面"实际已断"的比例并不高,
不存在一大批"白付了内容传输代价"的连接.

剩下的真"幽灵"只有一类: **连接活着, 但用户没在看**(后台标签页).
但移动端后台时 ws 早被系统杀掉、走 APNs / FCM 了, 根本不在这个集合里;
web 端后台标签占比不高, 且聊天正文很小.

结论: 做方案选择时**不要把这条算进纯戳的收益**. 判据一到六才是决定性的.


第三部分: 最优方案 (具体协议)
============================

形状 = 一条 WebSocket 承载双向 JSON 帧, 推内容 + 序号, 缺口在同一条连接上补拉,
媒体走独立 HTTP. 主流一致选择, 不是本文发明的(核对见第六部分).


3.1 传输层选择
-------------
* 一条 ws 就够. 浏览器一条 ws 已经天然多路复用所有房间, 不需要额外的 stream 抽象.
* **不要 jsonl**: ws 自带帧边界, 一帧一个 JSON 对象即可.
  jsonl 只在裸 TCP / HTTP chunked 这类没有帧边界的传输上才需要.
* **不要 JSON-RPC 2.0 全套**: batch / error object / notification 语义对 IM 是负担.
  取它 "用 Id 配对请求和响应" 的思想即可.
* 原则: **小消息 + 小 RPC 走 ws, 一切大东西走 HTTP**.
  用结构消掉"不做流控"的风险, 而不是靠调用者守纪律.
  (背景: 多路复用协议里若不做流控, 无窗口 -> 阻塞一路传到 TCP ->
   一条大流阻塞整条 conn 上所有 stream.)


3.2 帧类型
---------
通用信封(字段名 / 类型名 / JSON 名 ascii 一致, 首字母大写驼峰):

    type Frame_t struct {
        Type FrameType_t
        Id   string  // 可选. 请求/响应配对用. 单向推送帧不带.
        ...  // 按 Type 展开的字段
    }

    const FrameType_ping            FrameType_t = "ping"
    const FrameType_pong            FrameType_t = "pong"
    const FrameType_roomEnter       FrameType_t = "roomEnter"
    const FrameType_roomEntered     FrameType_t = "roomEntered"
    const FrameType_roomLeave       FrameType_t = "roomLeave"
    const FrameType_msgPush         FrameType_t = "msgPush"
    const FrameType_pullRange       FrameType_t = "pullRange"
    const FrameType_pullRangeResult FrameType_t = "pullRangeResult"
    const FrameType_sendMsg         FrameType_t = "sendMsg"
    const FrameType_sendMsgAck      FrameType_t = "sendMsgAck"
    const FrameType_streamDelta     FrameType_t = "streamDelta"
    const FrameType_deny            FrameType_t = "deny"
    const FrameType_closeConn       FrameType_t = "closeConn"


3.3 下行: 推内容 + 序号
----------------------
    MsgPush{RoomId, RoomEpoch, MsgIndex, Body}

* `MsgIndex`: **每房间单调递增**, 服务端落库时分配 —— 就是业务消息表里那一列,
  **不是第二套 offset**. (这正是 whyNotifyNotPush.md 批 Kafka offset 时说对的那点:
  位置锚点应该复用业务序号, 不该另起一套.)
* `RoomEpoch`: 房间重建 / 服务端重启导致 MsgIndex 语义变化时换值.
  没有它, 重启后的新消息会被当成旧消息忽略.

客户端收到后**只有两条路径**:
    a) MsgIndex == LocalMsgIndex + 1 且 RoomEpoch 相同  -> 直接 apply, 0 额外 RTT
    b) 其余一切情况(跳号 / 纪元变 / 刚重连)             -> 发 PullRange 补拉

推的内容永远是"机会主义加速", **可靠性唯一来源是 b) 这条补拉路径**.
这条纪律和 accelFieldsNotReliable.md 完全一致, 只是加速字段从"一个可丢的戳"
换成了"带序号的完整消息".


3.4 补拉: 走同一条 ws, 必须分页
------------------------------
    PullRange{Id, RoomId, FromMsgIndex, Limit}
    PullRangeResult{Id, RoomId, RoomEpoch, MsgList, HasMore, NextFromMsgIndex}

* 走 ws 而不是 ajax: 省掉 HTTP 建连 / 鉴权 / 中间层, 且和推送共用一条连接的生死状态.
* **分页是必须的, 不是加分项**: 断了一天再上线, 一个房间可能缺几千条.
  没有分页会出现一次巨大的响应把写缓冲撑爆 -> 断连 -> 重连 -> 再撑爆的死循环.
* Limit 由服务端封顶, 客户端请求值只作为建议.
* 缺口过大时(缺了几万条)允许服务端回"太旧了", 客户端退化成"只取最近 N 条 + 标记上方有空洞",
  用户滚动时再拉. Discord 的 ChannelDifferenceTooLong 是同一思路.

**乱序容忍窗口(Telegram 的做法, deliveryGuarantee.md 里没有这条)**:
检测到跳号时先等 ~0.5 秒再决定要不要补拉 —— 缺的那条可能只是被乱序了, 马上会到.
单服务端单连接不会乱序, 所以小规模下可以先不做; 但一旦做多节点扇出 / 多路径,
跳号里会混进一批"其实马上就到"的假缺口, 无脑立即补拉会造成拉取风暴.


3.5 上行: ClientMsgId + Ack (和下行正交的第二个命题)
--------------------------------------------------
    SendMsg{Id, RoomId, ClientMsgId, Body}
    SendMsgAck{Id, RoomId, ClientMsgId, MsgIndex}

**先说清它和 deliveryGuarantee.md 的关系**: 那篇文档的保障命题是
"客户端最终收敛到房间的最新状态" —— 主语是客户端, **方向是下行**.
上行是另一句独立命题: "用户按下发送后, 这条消息最终恰好出现一次".
两句话正交, 做对下行不会自动做对上行.

问题场景: 客户端发出 SendMsg 后连接断了, 客户端**不知道服务端有没有落库**.
不重发可能丢, 重发可能重复.

做法:
* `ClientMsgId`: 客户端生成的幂等键. 服务端落库时对 (发送者, ClientMsgId) 去重,
  重复的直接返回已分配的 MsgIndex, 不新建.
* 客户端把未 ack 的消息留在本地发送队列, 重连后全部重发. 靠幂等键去重, 重发是安全的.
* UI 上未 ack 的显示"发送中", ack 回来后换成 MsgIndex 对应的正式位置.

注意: 这个洞在"戳 + ajax POST"方案里**同样存在**(ajax 超时了也不知道成没成),
不是选了 ws 才引入的, 也和选哪种下行模型无关.


3.6 重连: 不需要服务端 replay buffer
-----------------------------------
* 重连后对每个活跃房间发 RoomEnter, 收到 RoomEntered{RoomEpoch, LatestMsgIndex} 后,
  若 LatestMsgIndex > LocalMsgIndex 就发 PullRange 补齐.
* **顺序不能反**: 必须 RoomEnter(订阅生效) 在前, PullRange(取快照) 在后.
  反了就是 deliveryGuarantee.md 里那个经典空洞: 拉到 v3 -> 发生 v4(还没订上, 不送达)
  -> 订阅生效 -> 此后无新变更 -> 永远卡在 v3.
* 服务端**不需要**为每条连接存 replay buffer. 重连补齐就是一次普通的 PullRange,
  和首次进房走同一条代码路径 —— 故障恢复是天然的, 不是特例.

**可选的中间档(Discord 的做法)**: 若实测"短断线重连补拉"很频繁、想省 DB,
可以在服务端加一层**有限**的近期消息内存 buffer, 命中直接回, **满了/太旧就降级查 DB**.
关键是它**纯属优化, 全量兜底始终在**, 所以不会背上"在通知层重建可靠事件流"的包袱.
deliveryGuarantee.md 把选择写成了二分(要么重建可靠事件流, 要么全量对齐),
这是被漏掉的第三档.


3.7 媒体: 走 HTTP, 不进 ws
-------------------------
* 图片 / 视频 / 文件: 独立 HTTP 上传下载, 或直传对象存储(预签名 URL).
  ws 帧里只放 URL + 尺寸 / 时长 / 缩略图元数据.
* 用 **HTTP/1.1 独立连接**, 不要塞进 API 的 HTTP/2 连接:
  h2 多路复用共享一条 TCP, 大文件会造成 HoL —— 正是 blocking_and_solutions.txt 批的那套
  (延时带宽积 / 窗口太小背压无效 / 窗口太大等于没写 / connection-level 依然互相阻塞).
* 浏览器里控制不了连接复用的话, 至少让媒体走**不同的 host 名**, 逼浏览器开独立连接.


3.8 AI 流式吐字
--------------
    StreamDelta{StreamId, ChunkIndex, TextDelta, IsEnd}

和聊天消息同构: ChunkIndex 连续就直接追加, 跳号就补拉该 StreamId 的区间.
**推 delta 不推全文**, 否则累计流量 O(n^2) —— 这是纯戳在吐字场景最致命的地方:
每个 token 一次戳, 客户端每次拉的都是**当前全文**.
主流(SSE / ws 流式 token)清一色是推 delta, 没有一家用"内容变了你来拉".


第四部分: 背压 / 过载 (服务端)
=============================

"不做任何流控"的准确含义
----------------------
指**不做 per-stream 滑动窗口**(理由见 blocking_and_solutions.txt),
**不是**指写缓冲无上限. 后者就是 whyNotifyNotPush.md 说的"连接变成了队列",
必然走向 内存无限涨 / 阻塞 / 丢 三选一.

具体做法
-------
* 每连接一个写缓冲, 有**硬上限**(参考 hgmRoomNotify 的 WriteBufMaxBytes 默认 64KB).
* 超上限 -> **断连**, 不是丢帧.
  和 hgmRoomNotify 不同: 那边帧是可丢的戳, 丢了靠下一个戳收敛; 这边帧里有内容,
  丢帧会造成跳号 —— 虽然客户端能靠 PullRange 拉回来, 但不如直接断干净, 少一条状态分支.
* 扇出时**绝不能同步阻塞在慢连接的 write 上**. 必须 nonblocking push, 满了标记断连,
  否则一个弱网手机能拖住整个房间的扇出(队头阻塞).
* 客户端 reader **只读不阻塞**: 收到就落本地队列 / IndexedDB, 渲染和 RPC 在别的任务里做.
  (blocking_and_solutions.txt 的 s1, 那边是 dirty flag 合并, 这边是入队.)

关于"要有可统计性, 好动态调这个参数"
----------------------------------
建议统计:
    * 写缓冲高水位分布(p50 / p95 / max), 按房间、按客户端类型分组
    * bufFull 断连率(次数 / 连接数 / 时间), 按同样维度分组
    * 单次扇出耗时 与 房间在线数 的关系

但**不建议做自动动态调**: 调大 buffer 只是把崩溃推迟, 代价是内存, 还掩盖真实原因.
更有效的方向是**让断连变便宜** —— 断了重连 + PullRange 补齐, 用户无感.
断连一便宜, buffer 就可以设得很小, 回归成纯粹的安全阀, 而不是一个需要调优的旋钮.
这也正是本方案的红利: 内容丢了能补拉, 所以背压策略可以粗暴.


第五部分: deliveryGuarantee.md 的清单在本方案里怎么落
==================================================

那 8 条正确性必须逐条对应(**一条都不能省**):

    1. 每次(重)连接重新拉全量        -> 重连后每个活跃房间 PullRange{From: LocalMsgIndex}
    2. 先订阅、再拉快照              -> RoomEnter 在前, PullRange 在后 (3.6)
    3. 服务端保存当前状态可全量下发  -> 服务端有 LatestMsgIndex, 真源是业务消息表
    4. 应用层心跳 + 读超时           -> FrameType_ping / pong + 两端读超时(参数见 pingTime.md)
    5. 重连无限重试                  -> 同 hgmRoomNotify, 且要加随机抖动防惊群
    6. 能识别服务器重启(epoch)       -> RoomEpoch 字段
    7. 加速数据缺失时回退全量拉取    -> MsgIndex 跳号 -> PullRange (3.3 路径 b)
    8. 通知级联逐环自检              -> 若上游是 pg NOTIFY, 那一环也要满足条件一 + 条件二

三条建议同样照抄: 心跳间隔 << 读超时; 重连最小间隔 + 随机抖动; 两端都能发终态信号
(FrameType_deny / closeConn, 带 Reason, 且必须用户可见).

**本文新增两条(聊天特有, 原清单没有)**:
    9.  上行幂等: ClientMsgId + Ack + 服务端去重 (3.5)
    10. 补拉必须分页, 缺口过大时能降级 (3.4)

顺带记两条实现细节, 原清单没有但实践中会撞上:
    * 乱序容忍窗口 ~0.5s (3.4), 多节点时必须有
    * 服务端近期消息 buffer 是可选第三档 (3.6), 纯优化, 不改变契约


第六部分: 主流核对 (2025-2026)
=============================

**没有一家主流聊天产品用纯戳传正文.** 形状高度一致 ——
推内容 + 序号, 缺口走增量拉, 大文件独立 HTTP.

    Telegram  update 带 pts/seq; 检测到 gap 先等 ~0.5s(可能只是乱序), 仍不齐才
              updates.getDifference(pts) 分页补齐. 冷启动只调 getDifference.
    Discord   ws 推事件带 s 序号; 断线 RESUME(session_id, s) 由服务端 replay buffer 补;
              **buffer 满就 INVALID_SESSION -> 全量 IDENTIFY**. 短期回放 + 全量兜底.
    Matrix    /sync?since=<token>
    Linear    /sync/delta?lastSyncId=
    Slack     Gateway Server(有状态, 多地域) + Channel Server(一致性哈希分房间)
              + Flannel(边缘元数据缓存); 重连后拉 history 对齐.

反过来, 纯戳阵营(见第一部分)里没有一个是聊天正文场景. 两边的分界线就是那六条判据.

两个常见误解顺手澄清:
* **Kafka 的真实位置是服务端内部的扇出总线**, 不是让浏览器消费 offset.
  whyNotifyNotPush.md 批"Kafka 当浏览器投递层"结论没错, 但那个靶子本来就没人立.
* **移动端后台 ws 必被系统杀**, 必须接 APNs / FCM 唤醒 + 回前台补拉.
  所以"戳一下 + 拉取"这条链**躲不掉**, 它会以推送通道的形式存在.
  即: 两种模型最终都要有, 只是各管各的场景.


第七部分: hgmRoomNotify 的正确战场
=================================

它在这些场景不是"凑合能用", 是**最优**:

    * 配置更新 / 软件自动更新("有新版本了")
    * 未读数、在线状态、正在输入
    * 会话列表排序 / 徽标
    * 任何"只关心当前值是什么, 中间态塌缩了无所谓"的东西
    * 超大广播房间的"该刷新了"信号(推戳 O(1), 比推内容省一个量级)
    * **弹幕 / 刷屏型房间**: 消息速率快到用户只看得了最后 N 条, 中间的不需要送达.
      这是判据一的例外(见第一部分), 也是"聊天类"里唯一该用本库的一档.
      注意它要求业务接受历史空洞, 且服务端应把"最新 N 条"缓存成全房间共享的一份.

判据一到六在这些场景**全部反向成立**: 中间态可塌缩、变更相对稀疏、
延迟不敏感(用户不盯着未读数的毫秒)、内容可能远大于戳.
于是 whyNotifyNotPush.md 列的那些优势 —— 连接不背内容、单一真相源、丢失安全所以极简、
故障恢复天然 —— 在这里全部成立.

**只有第 7 条(幽灵连接省带宽)要划掉**, 理由见第二部分.

一句话收尾:
    hgmRoomNotify 是一把好锤子, 但聊天正文不是钉子.
    对聊天场景, 这个项目最有价值的产出是 deliveryGuarantee.md 这份清单, 而不是那个库 ——
    因为库帮你付的那 7 条固定成本(心跳 / 重连 / epoch / 先订阅后快照 / 回退全量 /
    终态信号 / 每次重连对齐)是**长连接的固有成本**, 自己写 ws 时照样要付一遍,
    清单能保证你付对. 而聊天真正的复杂度(序号 / 分页 / 本地库合并 / 发送态 / 上行去重)
    库一点没碰, 所以"用性能换简单性"这笔交易在聊天场景换不到东西.
