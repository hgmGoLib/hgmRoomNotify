## 1. 第 1 步: 把五个指标写成五句可证伪的话

### 1.1 顺序和取舍规则

    正确性  >  延时  >  并发  >  带宽  >  简单性

**取舍规则只有三句:**

1. **正确性不是维度, 是门槛。** 只有"满足 / 不满足", **不参与任何取舍**。
2. **左边没打平之前, 右边一句话都不许说。** 例如: "这样写简单一点"在并发还没达标时是无效论据。
3. **简单性排最后, 但在左边四项打平时它说了算**, 选状态更少的那个。

> 违反后果: 顺序反过来最常见的两种结果 —— 为了"统一形状"把可追加的数据做成整份重推(带宽 O(n²)),
> 或者为了"先跑起来"在锁里放 DB IO(并发天花板被钉死, 后面要动整个协议才能拆)。

### 1.2 五句话(照抄, 把方括号里的数换成你自己的)

**在正确性成立的前提下:**

| 指标 | 目标(必须可证伪) | 怎么验 |
| --- | --- | --- |
| **正确性** | 只要两端最终都在线、网络最终双向连通并维持足够久, 客户端**最终**收敛到房间最新状态。中间态允许塌缩 | 故障注入场景 + `-race` 连跑 5 次 |
| **延时** | 一次业务变更从落库到出现在屏幕上, 客户端付出的**额外往返次数 = 0**, 上行 **0 字节** | 抓整条连接的帧, **数 RTT 个数和上行字节** |
| **并发** | (a) 没有任何一把**被多个用户共用的锁**里做过"按用户"的活;<br>(b) 更强的一条: **任何一把锁的临界区里都不许有 DB IO**, 一把也不行 | **只读代码, 不许用压测判**(§9 D17/D19) |
| **带宽** | 一次会话的累计下行字节与本次真正产生的新内容字节**同阶**(O(n) 而非 O(n²)), 且**每帧信封开销 <= [64] 字节** | 真 TCP 上量放大倍数 + **硬断言**信封字节 |
| **简单性** | 每一个"客户端在等 X"的状态、每一条降级路径, 都**有名字、有超时、有上限、有自动化测试**; 没有任何一条路径只在生产上才会被走到 | 数状态; 数"只有出事才跑的代码"有没有场景 |

### 1.3 三条量法纪律(写测试之前先接受)

**(a) 延时量"额外 RTT 数", 不量毫秒。**
开发机 RTT ≈ 0, 量毫秒只能量到自己机器有多快。RTT 个数是形状决定的常数,
乘上真实网络的 RTT 才是用户体感 —— 乘数改不了, 只能改常数。

    戳一下 + 回查全量: 服务端戳 0.5 RTT -> 客户端发请求 -> 响应回来 1 RTT = 1.5 RTT
    推内容 + 内生 id:  服务端直接推 = 0.5 RTT, 上行 0 次

| | 额外 RTT | RTT=1ms(开发机) | RTT=350ms(公网) |
| --- | --- | --- | --- |
| 戳一下 + 回查 | 1 个 | +1ms, 看不出来 | **+350ms, 每批变更都卡一下** |
| 本方案 | 0 个 | — | — |

> 违反后果: 在开发机上量毫秒, 会得出"这两种形状没区别"的结论, 于是选错形状 —— 而形状选错之后没有调参空间。

**(b) 带宽量"放大倍数"(累计下行 / 真正的新内容字节), 不量绝对字节。**
绝对字节和"这次内容多长"绑死, 没法横向比。**对比双方的合并程度必须一致**, 否则量出来的是合并率不是形状。

**(c) 并发这两条不许用实测判, 只读代码。**
一把锁里放着 DB IO, 逻辑上就是 O(排队人数) 串行 —— 这是**形状**, 和当下测出几毫秒无关。
串行段在人少时排队长度 0-1、被完全掩盖, 人一多是**断崖不是斜坡**, 压测对"再多十倍会怎样"没有预测能力。

> 违反后果: 等到压得出来的时候, 要改的是版本号的定义, 也就是整个协议。


## 2. 第 2 步: 把数据切成桶, 每桶单独选一种方案

**这是整套设计里最重要的一步, 后面所有章节都是它的下游。**
输出物是一张表, 照下面的格式填, 填完再往下走:

| 桶 | 装什么 | 选哪类 | id 字段 | 客户端动作 |
| --- | --- | --- | --- | --- |
| (你的桶 1) | | | | |

**一个房间里混用多类是常态, 不是妥协。** 不要试图让整个房间共用一套 id。

> 违反后果: 合成一套 id 就必然要一把包住 DB IO 的锁; 而且一桶判错会表现成"整个房间不收敛", 分不出是哪一桶。

### 2.1 选型: 三句话, 按顺序问, 第一个"是"就定了

**顺序不能换。**

**问题 1: 这一桶只在尾部追加, 从不重写中间, 也从不变短吗?**
* 是 + 载体是**连续字节流** → **类一 正文流**
* 是 + 载体是**一条条自带全序 id 的条目** → **类二 消息流**

**问题 2: 整份推下去也不心疼吗?**(经验红线: 单份几 KB 以内, **且按"每帧"算不是按"一次"算**)
* 是 → **类三 全量推内容**
* **问题 2b(问题 2 答"是"之前, 先插一句): 这一桶是不是"变得很勤 + 只关心最新值 + 差一两秒没人在乎"?**
  典型长相: **每秒都在变、每次都得整份带、而且用户根本分不清 0 秒和 1 秒的区别** ——
  动画式的进度、光标闪烁、会整屏重绘的终端输出、跑马灯式的计数器。
  它答"是"就**不能进类三** —— 类三的成本是 `变更次数 × 整份大小`, 这两个因子它都顶满了,
  于是它会**霸占每一帧的信封**, 把真正高频的那一桶(类一)的带宽账吃掉。
  **正确的动作是"把它从每帧的信封里拿出去", 而不是"改成轮询"。** 两条出路, 按这个顺序选:

  **(a) 首选: 退到类四(戳一下), 并靠客户端合并连续的戳(§5.4)。**
  成本随"**真的在看的人**"走 —— 没人打开那个面板就一次查询都不发生, 而且合并间隔就是延时旋钮。

  **(b) 只有在"上游根本没有可靠的 fire 点"时(说不清它什么时候变了, 所以戳不出来),
  才退到前端定时轮询**: 串行循环(**不是 `setInterval`**, 否则慢查询会叠罗汉)+ 版本号短路"没变就别重传"。

  > **(b) 是一次优先级倒挂, 必须当场写下理由才允许走。**
  > 它是整套设计里**唯一一个 O(在线人数) 的常驻负载** —— 顶在**并发**(第 3 优先级)上,
  > 换来的只是省**带宽**(第 4 优先级)。§1.1 的取舍规则本来不允许这么做。
  > 走 (b) 的四个条件, 缺一条就回 (a): ①查询是纯内存或极便宜; ②只有打开那个面板的人才拉;
  > ③有版本号短路; ④串行循环。一旦它变成一次真查库, **它就是性能炸弹**, 必须回 (a)。
  > (这和 §10 "不要轮询兜底"不冲突, 两者是不同的东西: 兜底轮询是**并行的第二条**可靠性路径,
  > 掩盖问题且没人测; 这里的轮询是这一桶**唯一的一条**路径, 走通走不通都看得见。)

**问题 3: 都不是 → 类四 仅戳一下**, 客户端自己去拉全量。

> 违反顺序的后果: 能追加的东西用类三 = 每次把全文重推一遍 = O(n²);
> 整份才几百字节的东西硬做追加 = 发明一套 id 和一堆缺口判断, 换来省几十字节。

完整判据(两句都为是才值得推内容): **变更描述的大小 << 重算全量的大小**,
且**客户端能原地应用这个描述**。类一类二是"远小于", 类三是"描述就是全量, 但全量本来就小",
类四是"描述比全量还贵, 或者根本说不清"。

### 2.2 四类横向对照(贴墙用)

| 维度 | 类一 正文流 | 类二 消息流 | 类三 全量推 | 类四 戳一下 |
| --- | --- | --- | --- | --- |
| **id 从哪来** | 数据自己(字节长度) | 数据自己(id 区间) | 外生计数 + 纪元 | 没有 id |
| **服务端要锁吗** | 不要 | 不要 | 只锁那一个整数 | 不要 |
| **客户端动作** | 裁剪后追加 | 去重后追加 | 整份覆盖 | 去发一个拉取请求 |
| **应用幂等吗** | 不幂等(靠偏移) | 幂等(靠 id 去重) | 幂等 | 幂等 |
| **丢一帧的后果** | 接不上 → 重新进房 | 接不上 → 重新进房 | 下一帧盖回来(自愈) | 停在旧数据(等下次戳) |
| **溢出/太大时** | 申报基准 + 回差值<br>**不许整页重拉** | 分页 + 整页重拉<br>(重拉有效) | 退回类一或类四<br>重新走 §2.1 | (本来就没内容) |
| **带宽** | O(n), 常数近 1 | O(n) | O(变更次数 × 整份) | O(变更次数 × 全量) |
| **额外 RTT** | 0 | 0 | 0 | 1 |
| **典型翻车** | 错位且静默 | 漏一条且无人发现 | 旧数据贴新号 | 被按 id 丢掉 |

**一条贯穿四类的判据: 只有类三需要一个外生的号, 也就只有它需要一个受保护的整数。**
任何时候你发现类一 / 类二也想加锁, 那说明你在给它们发外生号 —— 回 §2.1 重新找它们的内生号。

### 2.3 一个填好的例子

一个 AI 编程助手的 web 前端, 一个页面同时进 5 个房间:

| 桶 | 装什么 | 类别 | id 字段 | 客户端动作 |
| --- | --- | --- | --- | --- |
| 会话详情·正文 | AI 流式吐字 / 工具调用交错正文 | 类一 | `CallId` + `BaseLen` + `Text` | 按偏移裁剪拼接 |
| 会话详情·消息 | 聊天消息列表 | 类二 | `BaseMsgId` + `NewMsgs` | 按 id 去重追加 |
| 会话详情·状态 | 会话/计划/任务列表等约 20 个标量(三个库拼出来的) | 类三 | `Seq` | 整份覆盖 |
| 全局状态 | "运行中 / 排队中"两个数字 | 类三 | `Seq` | 整份覆盖 |
| 会话列表 / 任务列表 / 建任务 | 分页查询结果 | 类四 | 无 | 去拉一次全量 |
| (终端输出黑框) | TUI 尾部十几行, 会整屏上滚, 光标一直在闪 | **不进推送**(2b) | 版本号短路 | 前端 1 秒一轮拉 |

**最后一行是 2b 的实例, 但它走的是 (b) 那条退路, 不是首选的 (a)。**
它曾经放在类三里, 每帧从 37 字节涨到 1183 字节 —— 一桶"看着才 1KB"的东西, 因为**每帧都在变**,
把整条链路的带宽账吃掉了; 拆出推送之后帧回到 37 字节。
**但记录里没写当时为什么选轮询而不是 (a) 的戳一下**, 所以别把这一行当成"轮询是推荐做法"的依据 ——
新的一桶数据碰到同样的形状, 按 2b 的顺序先试 (a)。

顺带: **"统一形状"本身没有价值, 省下来的字节和 RTT 才有。**


## 3. 第 3 步: 写协议帧

### 3.1 帧信封: 只放每帧真的会变的东西

**信封预算: <= 64 字节。这是硬断言, 不是目标。**

一帧的信封只允许有: 帧类型 / **房间句柄** / 该桶的 id 字段 / map 头 / ws 帧头。

必须做的三件事:

1. **房间用整数句柄, 不用房间名字符串。** 句柄 = 进程内递增的小整数, 房间销毁重建时换号。
   > 违反后果: `"房间类型:20 位 id"` 这种字符串每帧要 30+ 字节, 而一帧正文才 24 字节。
2. **不要单独的房间纪元字段 —— 句柄兼任纪元。**
   房间只在最后一条连接离开时销毁, 所以"客户端还在房里期间号不会变"是**结构性成立**的。
3. **用整数键的二进制编码**(msgpack 整数键或等价物), 不用可读字段名。
   > 违反后果: 可读字段名 164 字节 → 整数键 37 字节。只换二进制不换键只能到 136 字节, **换键才是大头**。

再加两条纪律:

* **别让零值上线。** 每帧多九个字节就能把兜底帧预算的容量削掉一成(§6.3(c))。
  具体做法: 计数从 0 起算, 编码器跳过零值。
* **只有"重放会出错"的帧才带 Seq。** 判据是"重放会不会出错", **不是"带没带状态桶"**。
  幂等的追加帧不带。
  > 违反后果: 用"带没带状态桶"当判据, 会漏掉"同一条 CallId 的第一截正文也是整份替换"那一格。

### 3.2 帧类型清单(可直接抄)

    // 连接级
    ping / pong
    hello                      // 客户端第一帧, 带协议版本
    deny{Reason}               // 服务端拒绝, Reason 必须让用户看得见

    // 进房
    roomEnter{RoomKey, 客户端申报的基准...}    // 基准: 见 3.3
    roomEntered{RoomHandle, ServerEpoch, 快照 + 差值 + Seq}
    roomLeave{RoomHandle}

    // 推送
    roomChange{RoomHandle, [各桶的段, 每段可缺席], Seq?}

    // 指令(没有 id, 见类四)
    needFullReload{RoomKey}    // "你整页重拉一次"
    roomResync{RoomHandle}     // "我丢过帧, 你重新进房"

**纪元 = 所有 id 的作用域, 它本身不是 id。** 两级:

* `ServerEpoch`: 进程纪元, 进程重启换值。
* `RoomHandle`: 房间句柄, 房间销毁重建换号。

纪元一变, 下面所有的号(字节长度 / 消息 id 链 / Seq)全部作废, 客户端无条件重新对齐。

> 违反后果: 没有纪元, 重启后的新变更会被当成旧消息忽略; 或者拿旧句柄下的号去比新句柄下的号, 撞上。
> 有了纪元, "跨重启单调的 id"这个不可能的需求就消失了, "房间不存在期间的变更"也不需要任何补偿逻辑。

### 3.3 各类的帧字段

**类一 正文流:**

    段: {Mode: append|full, BaseLen: int, Text: string}
    外层帧带: CallId          // 命名空间, 一帧里多段正文共用一份
    roomEnter 申报: {CallId, 我手上有多少字节}

* **帧里必须同时有区间两端**: `BaseLen`(接在哪) + `Text` 的长度(接完到哪)。
  > 违反后果: 只有一端时, 客户端**只能靠"双方都记得上次到哪"**对齐,
  > 而这份记忆会因为丢帧/重连/整页重拉而分叉; 分叉后每次追加都接到错位置, 且 id 一路连续,
  > 没有任何东西会纠正它 —— **静默且不可恢复**。
* **别在每段正文里各带一份 `CallId`**, 放外层。
  > 违反后果: 每批变更白扔七八十字节, 而一批正文才 24 字节。
* **`CallId` 不是版本号, 是字节空间的命名空间。** 正文会变短的所有情况(一次调用结束 / 换一条调用)
  它必须跟着变, 变了就走 `full` 整份换。**这是"只追加"这条前提的唯一守卫。**

**类二 消息流:**

    段: {BaseMsgId: string, NewMsgs: []Msg}
    roomEnter 申报: {我的 LastMsgId}

* **左端点 `BaseMsgId` 必须带。**
  > 违反后果: 客户端停在 m3 收到 [m5,m6] 时**根本判断不出 m4 存不存在** ——
  > 离散 id 之间没有"下一个"的概念, 光看 id 发现不了空洞, 漏的那条会永久漏掉且无人发现。
* `BaseMsgId` 是空串是**合法值**(本批从最早一条开始), 判"有没有这一段"要看 `len(NewMsgs)`。
* 消息 id 必须**全序、不复用、不回收**。自增 / 雪花都行。
  > 违反后果: 拿"第几条"当 id, 条数会因为去重 / 补拉窗口而两边对不上。

**类三 全量推:**

    段: 整份字段(或字段级 diff: 缺席 = 没变)
    帧带: Seq

* **"没变"和"变成空"必须分得开** —— 用 `HasXxx` 布尔或 `*string` 指针。
  > 违反后果: "列表清空了"被当成"这次没带这个字段", 界面永远清不掉。
* 如果做字段级 diff(B 的变体): **这类帧必须带 Seq 才能剔重**, 因为它的应用不再幂等。

**类四 戳一下 / 指令:**

    只有 RoomKey (deny 多一个 Reason)。几十到两百字节。


## 4. 第 4 步: 写服务端

### 4.1 房间状态: 不可变快照 + 原子指针

**照这个写, 别自己发明:**

    type RoomState_t struct {   // 不可变。要改就整个换一个新的
        Seq        int64        // 类三那一桶的号, 从 0 起算
        LastMsgId  string       // 类二的游标
        Text       string       // 类一的当前全文
        CallId     string
        ... 类三那些标量
    }

    type Room_t struct {
        Handle int64
        state  atomic.Pointer[RoomState_t]
        conns  map[*Conn_t]struct{}    // 由全局锁保护
    }

    写侧(worker): 读库 -> 组装一份全新的 state(Seq = 旧 Seq + 1) -> Store 指针 -> 广播
    读侧(进房):   Load 一次指针, 数据和 Seq 一起拿到

* **单写者多读者**: 同一个房间同时只有一个 worker 在改(脏房间 id 去重 + 等一轮做完才进下一轮)。
* **初值谁装**: 谁先到谁 `CompareAndSwap(nil, 新的)`。CAS 失败就用别人那份, 自己那次读库白读 ——
  **那是锁外的白读, 不阻塞任何人**, 比"所有人排队等一次读"好。

> 为什么用不可变快照而不是裸 seqlock: 一次 `Load` 同时拿到数据和它的号,
> "读侧先读哪个"这条纪律**自动成立**, 只剩写侧要人守。

### 4.2 进房: 三步, 锁的边界画在第一步和第二步之间

    第一步 (全局锁内, 纯内存, O(1)): 订阅
        检查单连接进房数上限
        -> 取或建房间对象 (**只建壳, 不读 DB**)
        -> 把连接登记进房间
        // 这一步之后, 这条连接就已经是这个房间广播的收件人了

    第二步 (完全无锁): 取快照
        room.state.Load()   // nil 就读库 + CAS 装初值

    第三步 (完全无锁, 有 DB IO): 按客户端申报的基准算这次要给的东西
        类一: 快照里的正文 vs 客户端申报的长度, 只回那一截
        类二: 查区间 (客户端的 LastMsgId, 快照的 LastMsgId], **两端都放进帧**
        类三: 整份给, 标上快照里的 Seq

    第四步 (无锁): 编码, pushFrame 送进这条连接的写队列

**三条必须守的:**

* **建房间只建壳, 绝不在锁里读 DB。**
  > 违反后果: 一个正在读大正文的房间会把**所有别的房间**的进房请求一起卡住。
* **第一步和第二步之间有空隙, 广播会插进来。这是故意的, 由客户端缓冲兜(§5.2)。**
* **进房不许为了对齐把房间"拽到现在"**(再读一次库并给全房间推一帧)。只用房间手上那份快照算差值。
* **客户端申报的长度允许超过服务端房间那份**(它可能刚拉过全量, 而房间要等 worker 才前进)。
  这时服务端一个字都不补, 由随后那帧广播自带的偏移让客户端自己裁。

### 4.3 广播: 写侧顺序, 一步都不能换

    业务侧(每批变更一次):
        1) 写库(提交)
        2) fire(roomId)                    // 只标脏 + 唤醒 worker, 纯内存 O(1)

    worker(每个脏房间一个 goroutine, 同一房间同时只有一个):
        3) 无锁读库, 组装一份全新的 state
        4) 和 Load 到的旧 state 比出增量
           没有客户端看得见的变化 -> 到此为止, 不 Store 不广播
        5) 新 state 的 Seq = 旧 Seq + 1, **Store 指针**
        6) 序列化一帧, 扇出给房间里所有连接

**顺序约束: 3 → 5 → 6(数据先于号, 号先于广播)。**

> 违反后果: 顺序反了会发出**旧数据贴新号**(标签高估数据的新鲜度)。后果不是"晚一帧",
> 是**永久静默错误** —— 客户端把自己顶到那个号, 真正属于这个号的帧被判成"不比我新"扔掉,
> 界面停在这里, 看不出任何异常。广播那条路还能被下一次 fire 纠正, **进房那条路纠正不了**。

**三条配套的:**

* **Seq++ 挂在 worker 的 Store 上, 不要让业务侧自己 bump。**
  好处: 业务主流程不用同步读库+扇出; 而且"忘了 bump"退化成"忘了 fire",
  后者漏了会立刻表现成"界面不动"这种**显性**故障, 不会变成一种新的静默 bug。
* **合并是机会主义的: worker 不加任何定时器。** 只有在它正忙着处理上一轮时, 新来的 fire 才被攒到下一轮
  —— 不忙时零延迟, 忙时自动省掉那些"反正马上要被覆盖"的中间态。
  > 违反后果: 加了定时器就变成拿延时换带宽, 那是另一个取舍; 去掉合并则是拿带宽换一点点延时。两边都不做。
* **没有客户端可见的变化就一帧都不发**(和旧快照 DeepEqual)。

### 4.4 写缓冲: 三笔账 + 丢帧不阻塞

每条连接一条 **FIFO** 写队列(顺序不能乱: 同一个房间的帧必须按发出顺序到达),
但**准入分三笔独立的账**:

| 账 | 装什么 | 参考值 | 为什么必须单独一笔 |
| --- | --- | --- | --- |
| `broadcast` | 房间广播 | 256KB | 服务端自己一直在产生, 慢客户端身上会持续积压, 上限要小; 丢了让它重新对齐, 便宜 |
| `reply` | 客户端请求来的应答(`hello`/`pong`/带内容的 `roomEntered`) | 2MB | 一来一回就消掉; 丢一次要多绕一整轮, 贵 |
| `force` | 兜底帧(`needFullReload` / `deny`) | 64KB | **它出现的场合恰恰是 `reply` 那笔账已经满了** |

**`force` 这笔账额外两条, 咬合着的, 动一条之前先看另一条:**

* **同一个房间在队列里只留一帧**(入队时按房间去重, 已经有一帧就直接算作已发)。
* 去重之所以不漏, 靠的是**客户端处理 `needFullReload` 时不看配对 Id**(§5.3 类四)。

> 违反后果: 混在一起记账 = 活锁(要发的兜底帧被它要替代的那笔满账挡住)。
> 不去重 = 真实帧数是 房间数 × **重试轮数**, 而重试轮数在一条连接的写超时窗口里**没有上界**。

**扇出时绝不同步阻塞在慢连接的 write 上**: 满了就丢帧 + 记账 + 队列排空后补 `roomResync`。
**丢帧不是缺陷, 是设计的一部分。**

一条连接的服务端内存上界 = 三笔账之和 = **每连接最坏 2.31MB**(按上表)。
这个数只有"所有连接同时被卡满"时才达到(正常态几 KB), 但它必须是一个**你算过的数**。

**一条正交但关键的分工:**

> **"帧不丢"由传输层保证(同一条连接 FIFO + 丢帧必报 `roomResync`), 不由 id 保证。**
> id 只负责"跨来源"(快照 vs 广播)的对齐和剔重。

直接推论: **类三的 Seq 会跳号, 不许拿它判连续**(没有客户端可见变化的版本压根不发帧)。
内容缺口由各桶自己的 id 发现, 传输缺口由 `roomResync` 发现。**两条路都必须是活的, 都要有场景压。**

### 4.5 锁: 列一张清单, 定期逐个划掉

写完之后把服务端**所有**的锁列出来(全局的、每房间的、每连接的, 一个都不能漏), 逐个问:

1. 临界区里(含 `defer Unlock` 覆盖的整个函数体)有没有 **DB 查询**? 顺着调用往下追到底。
2. 有没有 `json.Marshal` / 序列化一份用户数据?
3. 有没有 O(某个用户的数据量) 的字符串比较 / 切片?

**有任何一个 = 不通过。修法不是再拆一层锁**(那只是缩小受害面), 而是回答:
这段代码为什么非得在锁里跑? 如果答案是"为了让某个版本号有意义", 就照 §2.1 换一个内生的号。

参考落点: 一个做对了的实现里只剩四把锁 —— 全局房间/连接表锁、脏标记锁、worker 句柄锁、每连接自己的锁,
**里面全是 O(1) 内存操作**。

### 4.6 goroutine: 每个 `go` 都要能停, 且停机要等它真的退出

把文件里所有 `go xxx()` 找出来, 逐个回答三句:

1. **谁能让它停?** 找不到答案的就是"起得来停不下来"。
2. 停它的那个函数, 是**通知完就返回**, 还是**等到它真的退出才返回**? **只通知不等待等于没停。**
3. 它读写的东西(全局服务 / db / 时钟 / 房间表)会不会在它退出之前就被别人换掉或关掉?

**一个必须注意的形状**: "等一个 goroutine 退出"这件事**必须在放开锁之后做** ——
拿着锁去等 goroutine 退出是标准的死锁形状。


## 5. 第 5 步: 写客户端

### 5.1 连接

* 应用层 **ping/pong + 两端读超时**。不要只依赖 socket 的关闭回调。
  > 违反后果: 中间盒丢包 / 客户端换 IP 时 TCP 仍是 ESTABLISHED, 你永远发现不了该重连(静默死链)。
* **无限重连**, 最小间隔 + 随机抖动。抖动是给服务端重启准备的(所有连接同时掉线同时重连)。
* 重连之后, 对**所有活跃房间**重发 `roomEnter`, 并**申报自己手上有什么**。

### 5.2 进房: pending 缓冲 + 重放

    发出 roomEnter 之后, 这个房间进入 pending:
        收到的 roomChange **缓冲**起来, 不直接应用
        (那些帧的基准还没确定)

    收到 roomEntered 之后:
        1) 先应用快照
        2) 把缓冲**按到达顺序**重放, **每一桶用自己的 id 判**:
               帧的纪元和应答的对不上 -> 整帧扔掉
               类一段: 按 §5.3 三选一
               类二段: 按 §5.3 三选一
               类三段: Seq <= 我的就扔, 大于就整份覆盖
        3) 清空缓冲, 房间恢复正常

* **缓冲必须有上限**(帧数 + 字节数)。
* **溢出时不是丢最旧那几帧** —— 那会造成静默空洞。
  正确做法: **整个缓冲作废 + 记一个标记**, 等应答到了先应用快照, **再立刻重新进一次房**。
  (输入严格改变了: 基准变成刚拿到的那份。)
* **房间级超时必须有, 而且独立于连接**: 记下"这次进房是什么时候发出去的",
  超过一个读超时还没等到应答就**重发 `roomEnter`**。
  > 违反后果: 应答永远不到时, 房间永远停在旧数据上, 而连接是健康的、心跳照跑,
  > **连接级探活完全看不见它**。这条规矩推广开就是: **连接活着 != 房间活着。**
  > 有了缓冲之后这条**仍然必须留着** —— 一个刚打开页面、手上什么都没有的客户端,
  > 没有快照就是白屏, 缓冲再多也渲染不出来。

### 5.3 应用增量: 每类的规则(没有第四条)

**类一 正文流**, `append` 模式:

    我 >= BaseLen + len(Text)   整帧我都有 -> 扔
    BaseLen <= 我               裁掉重叠的一截再接
    我 <  BaseLen               中间缺了   -> 重新进房(带上我现在的长度)

`full` 模式:

    同 CallId 且我不比它短   -> 保留我的(防回退)
    换了 CallId              -> 必须整份换掉(旧 CallId 的残留不能留在屏幕上)

**类二 消息流:**

    BaseMsgId == 我的游标        -> 追加, 游标推到帧里最后一条
    BaseMsgId 在我已有的消息里    -> 按 id 去重后追加(重复是安全的那一边)
    BaseMsgId 我根本没见过        -> 中间缺了 -> 重新进房

去重**按 id, 不按位置**。

**类三 全量推:**

    Seq <= 我的  -> 扔
    Seq >  我的  -> **整份覆盖** 并更新我的 Seq

> 违反后果: 改成"字段级差量地应用", 幂等就没了, 于是要求号严格连续, 于是服务端又要一把锁。
> 这一类的全部宽容度("多收敛一次啥事没有")都来自"整份覆盖是幂等的"。

**类四 指令: 绝不许按 id / 按新旧丢弃。**

> 违反后果: 快照会过期, "你去重拉"不会 —— 它什么时候执行都是对的。
> `needFullReload` **偏偏总是在队列积压时才发出**, 到达时客户端多半已经超时重发过, 配对 Id 必然对不上;
> 按 Id 丢掉它, 整条降级链上唯一能收敛的一环就断了。

### 5.4 客户端侧的两条降级纪律

* **自己合并连续的戳**(整页重拉设一个最小间隔, 如 5s), 否则一次爆发就是 N 次全量拉取。
* **进房应答里的增量接不上时, 不能原样再进一次房** —— 基准没变, 答案也不会变, 死循环。
  只能整页重拉换一份新基准。

### 5.5 客户端里所有"我在等 X"的状态, 逐个登记

把代码里所有 `if (还在等 X) { 丢掉 / 缓冲 }` 找出来, 每个填一行:

| 在等什么 | 等待期间收到的东西怎么处理 | 谁把它踢回去(超时) | 上限 | 溢出走哪条路 |
| --- | --- | --- | --- | --- |
| 进房应答 | 缓冲 | 房间级超时, 重发 roomEnter | 64 帧 / 1MB | 缓冲作废 + 应用快照后立刻重进房 |
| (整页重拉在飞) | 丢弃该房间的推送和应答 | **拉取请求自己的超时** | — | — |

**第二行是最容易漏的一格, 而且真的漏过**: "等一个 ajax"也算一个冻结点。
那几个 POST 原来没传超时 —— 连接健康、进房超时也不会响(每次都收到了应答, 只是被丢掉),
房间就永远停在旧数据上。**修法: 凡是在"重拉计数 ++ 和 --"之间 await 的请求, 一律带超时。**


## 6. 第 6 步: 参数表 + 三条不变式

### 6.1 参数表(参考值, 按自己的业务调, 但要重算 §6.3)

| 参数 | 参考值 |
| --- | --- |
| 广播账 / 应答账 / 兜底帧账上限 | 256KB / 2MB / 64KB |
| 单次进房应答上限 | 256KB |
| 一次补拉消息条数上限 | 50 |
| 单条连接最多进房数 | 256 |
| 客户端等待缓冲上限 | 64 帧 / 1MB |
| 整页重拉最小间隔 | 5s |
| 客户端心跳 / 读超时 | 4.5s / 10s |
| 服务端读超时 | 120s(客户端的 12 倍, 保证客户端先发现) |
| 单帧写超时 | 30s |
| 进房应答超时 | **= 客户端读超时**(不新增配置项) |
| 最小重连间隔 / 抖动 | 5s / 2.5s |

### 6.2 时间参数按**真实网络的 RTT** 选, 不按开发机选

* 心跳 4.5s / 读超时 10s: RTT 350ms 时一次 ping-pong 往返 0.7s, 六倍余量;
  读超时是心跳的两倍多, 所以**丢一个 pong 不会误杀健康连接**。
  > 违反后果: 按开发机 RTT 压缩这两个数, 在真实网络上变成周期性假断连 + 重连风暴。
* 进房应答超时复用读超时: 正常应答是"一个 RTT + 一次读库"。
* 服务端读超时必须**远大于**客户端读超时, 保证**客户端先发现**断连。

### 6.3 三条必须成立的参数不变式(改任何一个数之前先重算)

**(a) 单次进房应答上限 × 单条连接可能同时进的房间数 <= 应答账上限。**
例: 256KB × 5 = 1.25MB <= 2MB。**这条曾经不成立过。**

注意"每个房间同时只有一份应答在队列里"**不是天然成立的**(客户端整页重拉完会再进一次房,
上一份应答还没写出去时第二份就排进来了), 所以严格说右边还要乘一个重试轮数。
**这里故意不做 (c) 那样的去重**, 因为后果不同: 兜底帧被丢 = 降级链断了, 房间只能等进房超时;
而应答被丢 = 立刻补一帧兜底(那笔账是独立的), 客户端重拉一次就回来 —— **有下一层接着**。

**(b) 客户端等待缓冲上限 >= 一个读超时内正常能收到的广播量。**
例: 每批变更一帧、每帧一两百字节, 10 秒撑死几十帧 → 64 帧 / 1MB 有一个数量级余量。

**RTT 直接进这条账**: pending 窗口 ≈ 一个 RTT + 一次读库。
**必须按真实 RTT 复核, 不能按开发机复核** ——
> 违反后果: 按开发机算会得出"永远不会溢出"的结论, 于是 §9 的 D18(b) 那条溢出路径再也没人写场景。

**(c) 兜底帧大小 × 单连接进房数上限 <= 兜底账上限。**
例: 64KB / 每帧约 200 字节 = 三百多帧 > 256。
**这条的分母"一个房间同时只有一帧"是去重去出来的, 不是天然成立的**(§4.4)。
**这个账真的被穿过**, 症状是某个场景十次红一次。


## 7. 第 7 步: 登记每一条降级路径

优化必然带来上限, 有上限就必然有降级("这次我给不了, 你退回去用笨办法")。
**每一条都填进这张表, 填不出第三列的就是活锁 —— 不是"慢一点", 是永远不收敛。**

| 触发 | 动作 | **再来一次哪里不一样** | 有效? |
| --- | --- | --- | --- |
| 缺的消息太多(> 上限) | `needFullReload` | 重拉把游标推到最新, 下次要补的条数变少 | ✅ |
| 单次进房应答太大 | `needFullReload` | 重拉后客户端申报的长度 = 全文长度, 差值没了 | ✅ |
| **正文本身就长** | **不许 `needFullReload`** | 全文多大和重拉过几次**没有任何关系** | ❌ **无限重拉** |
| 广播账满 | 丢帧 + 记账, 队列排空后补 `roomResync` | 队列排空这件事本身就是输入的改变 | ✅ |
| 客户端等待缓冲溢出 | 缓冲作废 + 应用完快照立刻重新进房 | 带的是刚应用完那份快照的基准, 严格新于上一次 | ✅ |

**第三行是这张表存在的理由**: 类一的"太大"只能靠"申报基准 + 只回差值"解决, 绝不能用整页重拉。


## 8. 第 8 步: 搭测试

### 8.1 要覆盖什么(场景清单)

分两组, 两组都要有:

**网络类** —— 逐条验 §1.2 的正确性目标:
断线重连 / 换 IP / 静默死链(只丢包不 RST)/ 服务端重启 / 房间重建 /
两个客户端停在正文的**不同字节**上收同一帧 / 长时间离线后上线 / 随机混沌压测。

**缓冲类** —— 逐条验降级路径:
广播账压满(丢帧)/ 应答账压满 / 兜底帧账压满 / 慢客户端不影响快客户端 /
进房应答一直不来(房间级超时)/ 进房窗口 A 段与 B 段 / 客户端缓冲溢出。

**进房窗口那个场景要分两半压, 而且三桶各压一遍**(这是最容易漏的一组):

    用两个延时钩子把 §4.2 第一步和第二步之间的窗口撑开:
        A 段: 广播比快照旧 -> **必须剔掉**, 否则重复应用
        B 段: 广播比快照新 -> **必须重放**, 否则静默漏一段
    然后: 一个场景只灌类一, 另一个分两段只灌类二 / 只灌类三

> 为什么要每桶各压一遍: 只灌正文的话, 消息和状态那两段判断**根本不会被执行到**,
> 一桶的 id 写错不会被另一桶掩盖 —— 反过来说, 也就抓不到。

**一个陷阱**: 压类三那一半只能改**一次**状态。改两次(A→B→A)会被 worker 合并成"和快照相比没变",
一帧都不发, 窗口就白开了。**机会主义合并在写场景时是个陷阱。**

### 8.2 四条测试纪律

1. **真 TCP, 不靠 `if` 跳进降级分支。** 看丢帧计数器: **"丢帧 0 次"却绿了 = 这个测试在空转。**
2. **打印不算数, 断言才算数。** 场景里"这条路走到了 N 次"如果是覆盖证据, 就**必须是断言**。
   > 光打印的话它悄悄变成 0 也没人会发现 —— 一个从来没红过的分支和没写的分支一样可靠。
3. **覆盖证据要两头都断。** 结尾"于是走到了 Y"要断言, 开头"我已经把环境弄成 X 了"**同样要断言**。
   > 只断结尾的话, 环境没弄成的那些轮次会安安静静地绿着过去。这个形状踩过两次。
4. **新场景写完必须做一次变异验证**: 把被测逻辑改坏, 看着它当场变红, 再改回来。**没红过的场景不算数。**

另外两条: 断言尽量写成**可观测的代价**("这次进房花了几个来回""重拉了几次"), 而不是内部计数器;
`-race` 要**连跑 5 次全绿**, 单跑一次绿说明不了任何事。

### 8.3 值得做一遍的一件事: 独立重写第二遍

用一个独立重写的模拟器把同一套协议再实现一遍(跑真 TCP、能注入网络故障、参数按生产等比缩小,
让 stall 几毫秒就顶满缓冲)。
**它的价值不在"多一份测试", 在于它会用不同的方式把同一个形状实现一遍 —— 形状错了两边对不上。**


## 9. 验收清单: 22 条

**每一条都是"必须", 没有"建议"这一档。** 做不到就改代码, 或者把这条删掉/改写。

> 中间那档"建议"是个陷阱: 它让"没做"看着像一种合法状态, 于是那几条永远不会被做掉,
> 而清单本身也不再能回答"现在到底满不满足目标"。

| 编号 | 指标 | 检查点 | 怎么查 |
| --- | --- | --- | --- |
| **D1** | 延时 | 高频累加型内容, 变更帧是否**自带内容**而不是"你去拉"? | 抓一次完整变更的全部下行帧, 看客户端有没有为了渲染再发过任何请求 |
| **D2** | 带宽 | 变更描述比重算还贵的内容, 是否**没有**推内容? | 对每种房间问两句(§2.1): 描述比全量小吗? 客户端能原地应用吗? 一个否就别推 |
| **D3** | 带宽 | 累加型内容是否只传新增的那一截? | 累计下行 / 内容总字节 应是**常数倍**, 不随内容变长而涨 |
| **D4** | 正确性 | 每一帧增量是否**自带**"接在哪", 而不靠双方的记忆? | 让两个客户端**停在正文的不同字节上**, 广播同一帧, 看两边都能对 |
| **D5** | 带宽 | 进房应答是否是**差值**? 客户端是否申报了自己的基准? | 只差 300 字节时重连, 看整条连接的下行字节数 |
| **D6** | 延时 | 同一次爆发是否被合并, 且合并**不引入等待**? | 看合并逻辑里**有没有定时器**。有 = 拿延时换带宽 |
| **D7** | 并发 | 进房路径上是否**没有**为对齐而把房间拽到"现在"? | 读进房代码: 它只该用手上那份快照算差值 |
| **D8** | 带宽 | 帧信封开销 <= 64 字节(里面没有每帧重复的常量)? | (下行总字节 − 内容字节) / 帧数。**断言它, 不是打印一个数看看** |
| **D9** | 延时 | 这条优化是否**没有**增加任何上行字节? | 上行字节计数器减去心跳。**断言它和老形状不是一个数量级** |
| **D10** | 正确性 | 每个"等待期间不能直接用数据"的状态, 是否有**独立于连接**的超时? | §5.5 那张表填满。**注意"等一个 ajax"也算** |
| **D11** | 正确性 | 每条降级路径, "再来一次"的输入是否**严格改变**? | §7 那张表第三列。**写不出来的就是活锁** |
| **D12** | 正确性 | 会因"塞不下"而降级的帧, 是否和它要替代的大帧记在**不同**预算上? | 再问一句: 那笔预算的容量**把降级自己触发的下一轮算进去了吗**? |
| **D13** | 正确性 | 单次应答上限 × 同时进的房间数 <= 应答预算? | §6.3(a)。数一下一个页面上来会同时进几个房间, 乘一下 |
| **D14** | 并发 | 一个客户端的积压, 是否只影响它自己? | 两个客户端同房间, **只弄坏其中一台的网络**, 看另一个还能不能实时收到(**帧数是断言**) |
| **D15** | 正确性 | 优化之后, §1.2 那五句是否**逐条**还成立? | 网络类场景全组; 每条再问一遍"**这一步自己失败了, 谁来兜**" |
| **D16** | 正确性 | 压缓冲的测试是不是**真的**把缓冲压满了(真 TCP), 而不是靠 if? | 看丢帧计数器。丢帧 0 次却绿 = 空转 |
| **D17** | 并发 | **共用锁里是否没有按用户读写数据库**(及别的按用户的活)? | §4.5 的三问。**只读代码, 不许压测判** |
| **D18** | 正确性 | 进房期间的广播是否被缓冲并按各桶 id 正确重放/剔重? 缓冲有界吗? | (a) §8.1 那个 A/B 段场景, **三桶各压一遍**; (b) 溢出那条路**自己也要有场景** |
| **D19** | 并发 | **任何一把锁的临界区里, 是否都没有 DB IO?** | 列出**所有**锁(不管什么粒度), 顺着调用追到底。**只读代码** |
| **D20** | 简单性 | 每一桶数据, 是否都写清楚了"它是哪一类"? | 打开房间快照那个文件, 把每个字段分进 §2 那四类, **分不进去的就是设计漏了** |
| **D21** | 简单性 | 每个常驻 goroutine 是否**停得下来**, 且停机是"等它真的退出"? | §4.6 的三问 + `-race` 连跑 5 次全绿 |
| **D22** | 带宽 | 传输层压缩是否**真的开着**, 且**没有**被算进任何一条带宽账里? | §9.1 那四关 |

### 9.1 D22 展开: 压缩是唯一一处"配错了也完全不报错"的优化

没谈成 / 模式选错 / 阈值调过头 —— **三种情况下功能全都正常, 别的用例全绿, 只是线上字节多几倍**。
应用层永远看到明文, 所以**只能到 TCP 那一层去数字节**(在测试里包一层 `net.Conn`)。

**四关, 一关也不能少(它们互相抓不到对方):**

1. 握手响应头里有 `permessage-deflate`, 且**没有** `no_context_takeover` → 抓"模式配错 / 没开"
2. **(a)** 最热的小帧, **线上字节 <= 明文字节 + 每帧 8 字节的帧头** → 抓"阈值被调小了"
   **(b)** 同一批小帧, 每帧线上字节 <= 64(和 D8 同一个数) → 抓"帧信封长胖了"
3. 一条 5100 字节的大消息, 线上字节 < 明文的 1/5 → 抓"压缩其实没在干活"

**2a 和 2b 必须分成两条**(第一版只写了 2b, 抓不到阈值退化 —— 详见 pushDesignRationale.md R12.1)。

**连带的一条硬纪律:**

> **任何一条带宽账都不许把压缩算进去。D8 那 64 字节必须靠编码本身站住。**
> 压缩一旦顶在前面, 编码退回 JSON 也测不出来 —— 重复几百遍的字段名恰恰是 deflate 最擅长压的东西。
> **所以压缩必须排在编码之后做。顺序反了, D8 就再也没有牙齿。**

**选 ws 库时要确认的一件事**: 能不能**保留压缩上下文**。
有的库把 `client_no_context_takeover` 写死在握手串里、没有开关, 而不保留上下文时每条消息都从空字典开始,
大块 JSON 差一个数量级。


## 10. 明确不做的清单

**这些不是"暂时没做", 是"做了会更糟"。** 每条注明它省掉了哪一类状态。

| 不做 | 省掉了什么 |
| --- | --- |
| 反馈式窗口 / 阻塞流控 | 一整套窗口状态机 + 队头阻塞(一个弱网页面拖住整个房间)这一类故障 |
| 把丢帧改成不丢 | 无界队列 / OOM。内存有硬上界, 代价只是让那一个客户端重新对齐一次 |
| **轮询兜底**(在推送之外再挂一层"定期拉一次防止漏") | 一条**永远不会被测到**的并行路径 + 常驻开销换一个概率性的好处。正确的替代是把失效场景写成自动化测试。<br>**注意和 §2.1 的 2b(b) 不是一回事**: 那里轮询是某一桶**唯一的**取数路径(走通走不通都看得见), 这里是**并行的第二条**路径(它专门用来掩盖第一条的 bug) |
| 服务端为每条连接存正文游标 | "这份游标什么时候过期"的一整类新问题 + O(连接数) 常驻内存。客户端本来就免费知道自己的偏移 |
| 给合并加定时器 | 一个需要调的旋钮 + 一个延时/带宽的取舍(§4.3) |
| 反过来把合并去掉("为了更实时") | 同上 |
| 为了"快照要原子"搞跨库事务 / 全局版本表 / 每条数据加版本列 | 一整套分布式事务。收敛靠的是"下一次重读一定会来", 不是"这一次读得完美" |
| **再给房间加一把锁**(任何名字任何粒度) | §1.2 并发目标的全部收益 |
| 把各桶的 id 合并回一个 | 一把包住 DB IO 的锁 + 可诊断性(一桶判错会表现成"整个房间不收敛") |
| 给类三做**全桶字段级差量** | 一把锁 + "号必须连续"这一整类判断(幂等没了) |
| 无序集合按 key 版本 + 墓碑 | "删除怎么表示"这一整类问题。小集合整份走类三更便宜 |
| protobuf / 定长数组编码 | schema / 代码生成 / 前端 runtime / "未知键忽略"这条可升级性(体积上打平) |
| 让常驻 goroutine "起得来停不下" | 一整类只在关闭时出现、且只有 `-race` 才抓得到的竞争 |
| **统一形状** | (反过来的一条: **拒绝一种假的简单性**) |

最后一行值得单独说, 因为它是唯一一条反直觉的:
"所有数据走同一套 id 机制"看起来更简单, 但它**换来的是一把包住 DB IO 的锁**,
以及"一桶判错表现成整个房间不收敛"的不可诊断性。
**那不是简单, 那是把复杂度藏进了一个更糟的位置。**
