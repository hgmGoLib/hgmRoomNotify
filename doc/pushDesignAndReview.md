## 1. 第 1 步: 把五个指标写成五句可证伪的话

### 1.1 顺序和取舍规则

    正确性  >  延时  >  并发  >  带宽  >  简单性

**取舍规则只有三句:**

1. **正确性不是维度, 是门槛。** 只有"满足 / 不满足", **不参与任何取舍**。
2. **左边没打平之前, 右边一句话都不许说。** 例如: "这样写简单一点"在并发还没达标时是无效论据。
3. **简单性排最后, 但在左边四项打平时它说了算**, 选状态更少的那个。

> 违反后果: 顺序反过来最常见的两种结果 —— 为了"统一形状"把可追加的数据做成整份重推(带宽 O(n²)),
> 或者为了"先跑起来"在锁里放 DB IO(并发天花板被钉死, 后面要动整个协议才能拆)。

### 1.2 五句话(照抄, 把方括号里的数换成你自己的)

**在正确性成立的前提下:**

| 指标 | 目标(必须可证伪) | 怎么验 |
| --- | --- | --- |
| **正确性** | 只要两端最终都在线、网络最终双向连通并维持足够久, 客户端**最终**收敛到房间最新状态。中间态允许塌缩 | 故障注入场景 + `-race` 连跑 5 次 |
| **延时** | 一次业务变更从落库到出现在屏幕上, 客户端付出的**额外往返次数 = 0**, 上行 **0 字节** | 抓整条连接的帧, **数 RTT 个数和上行字节** |
| **并发** | (a) 没有任何一把**被多个用户共用的锁**里做过"按用户"的活;<br>(b) 更强的一条: **任何一把锁的临界区里都不许有 DB IO**, 一把也不行 | **只读代码, 不许用压测判**(§9 D17/D19) |
| **带宽** | 一次会话的累计下行字节与本次真正产生的新内容字节**同阶**(O(n) 而非 O(n²)), 且**每帧信封开销 <= [64] 字节** | 真 TCP 上量放大倍数 + **硬断言**信封字节 |
| **简单性** | 每一个"客户端在等 X"的状态、每一条降级路径, 都**有名字、有超时、有上限、有自动化测试**; 没有任何一条路径只在生产上才会被走到 | 数状态; 数"只有出事才跑的代码"有没有场景 |

### 1.3 三条量法纪律(写测试之前先接受)

**(a) 延时量"额外 RTT 数", 不量毫秒。**
开发机 RTT ≈ 0, 量毫秒只能量到自己机器有多快。RTT 个数是形状决定的常数,
乘上真实网络的 RTT 才是用户体感 —— 乘数改不了, 只能改常数。

    戳一下 + 回查全量: 服务端戳 0.5 RTT -> 客户端发请求 -> 响应回来 1 RTT = 1.5 RTT
    推内容 + 内生 id:  服务端直接推 = 0.5 RTT, 上行 0 次

| | 额外 RTT | RTT=1ms(开发机) | RTT=350ms(公网) |
| --- | --- | --- | --- |
| 戳一下 + 回查 | 1 个 | +1ms, 看不出来 | **+350ms, 每批变更都卡一下** |
| 本方案 | 0 个 | — | — |

> 违反后果: 在开发机上量毫秒, 会得出"这两种形状没区别"的结论, 于是选错形状 —— 而形状选错之后没有调参空间。

**(b) 带宽量"放大倍数"(累计下行 / 真正的新内容字节), 不量绝对字节。**
绝对字节和"这次内容多长"绑死, 没法横向比。**对比双方的合并程度必须一致**, 否则量出来的是合并率不是形状。

**(c) 并发这两条不许用实测判, 只读代码。**
一把锁里放着 DB IO, 逻辑上就是 O(排队人数) 串行 —— 这是**形状**, 和当下测出几毫秒无关。
串行段在人少时排队长度 0-1、被完全掩盖, 人一多是**断崖不是斜坡**, 压测对"再多十倍会怎样"没有预测能力。

> 违反后果: 等到压得出来的时候, 要改的是版本号的定义, 也就是整个协议。


## 2. 第 2 步: 把数据切成桶, 每桶单独选一种方案

**这是整套设计里最重要的一步, 后面所有章节都是它的下游。**
输出物是一张表, 照下面的格式填, 填完再往下走:

| 桶 | 装什么 | 选哪类 | id 字段 | 客户端动作 |
| --- | --- | --- | --- | --- |
| (你的桶 1) | | | | |

**一个房间里混用多类是常态, 不是妥协。** 不要试图让整个房间共用一套 id。

> 违反后果: 合成一套 id 就必然要一把包住 DB IO 的锁; 而且一桶判错会表现成"整个房间不收敛", 分不出是哪一桶。

### 2.1 选型: 三句话, 按顺序问, 第一个"是"就定了

**顺序不能换。**

**问题 1: 这一桶只在尾部追加, 从不重写中间, 也从不变短吗?**
* 是 + 载体是**连续字节流** → **类一 正文流**
* 是 + 载体是**一条条自带全序 id 的条目** → **类二 消息流**

**问题 2: 整份推下去也不心疼吗?**(经验红线: 单份几 KB 以内, **且按"每帧"算不是按"一次"算**)
* 是 → **类三 全量推内容**
* **问题 2b(问题 2 答"是"之前, 先插一句): 这一桶是不是"变得很勤 + 只关心最新值 + 差一两秒没人在乎"?**
  典型长相: **每秒都在变、每次都得整份带、而且用户根本分不清 0 秒和 1 秒的区别** ——
  动画式的进度、光标闪烁、会整屏重绘的终端输出、跑马灯式的计数器。
  它答"是"就**不能进类三** —— 类三的成本是 `变更次数 × 整份大小`, 这两个因子它都顶满了,
  于是它会**霸占每一帧的信封**, 把真正高频的那一桶(类一)的带宽账吃掉。
  **正确的动作是"把它从每帧的信封里拿出去", 而不是"改成轮询"。** 两条出路, 按这个顺序选:

  **(a) 首选: 退到类四(戳一下), 并靠客户端合并连续的戳(§5.4)。**
  成本随"**真的在看的人**"走 —— 没人打开那个面板就一次查询都不发生, 而且合并间隔就是延时旋钮。

  **(b) 只有在"上游根本没有可靠的 fire 点"时(说不清它什么时候变了, 所以戳不出来),
  才退到前端定时轮询**: 串行循环(**不是 `setInterval`**, 否则慢查询会叠罗汉)+ 版本号短路"没变就别重传"。

  > **(b) 是一次优先级倒挂, 必须当场写下理由才允许走。**
  > 它是整套设计里**唯一一个 O(在线人数) 的常驻负载** —— 顶在**并发**(第 3 优先级)上,
  > 换来的只是省**带宽**(第 4 优先级)。§1.1 的取舍规则本来不允许这么做。
  > 走 (b) 的四个条件, 缺一条就回 (a): ①查询是纯内存或极便宜; ②只有打开那个面板的人才拉;
  > ③有版本号短路; ④串行循环。一旦它变成一次真查库, **它就是性能炸弹**, 必须回 (a)。
  > (这和 §10 "不要轮询兜底"不冲突, 两者是不同的东西: 兜底轮询是**并行的第二条**可靠性路径,
  > 掩盖问题且没人测; 这里的轮询是这一桶**唯一的一条**路径, 走通走不通都看得见。)

**问题 3: 都不是 → 类四 仅戳一下**, 客户端自己去拉全量。

> 违反顺序的后果: 能追加的东西用类三 = 每次把全文重推一遍 = O(n²);
> 整份才几百字节的东西硬做追加 = 发明一套 id 和一堆缺口判断, 换来省几十字节。

完整判据(两句都为是才值得推内容): **变更描述的大小 << 重算全量的大小**,
且**客户端能原地应用这个描述**。类一类二是"远小于", 类三是"描述就是全量, 但全量本来就小",
类四是"描述比全量还贵, 或者根本说不清"。

### 2.2 四类横向对照(贴墙用)

| 维度 | 类一 正文流 | 类二 消息流 | 类三 全量推 | 类四 戳一下 |
| --- | --- | --- | --- | --- |
| **id 从哪来** | 数据自己(字节长度) | 数据自己(id 区间) | 外生计数 + 纪元 | 没有 id |
| **服务端要锁吗** | 不要 | 不要 | 只锁那一个整数 | 不要 |
| **客户端动作** | 裁剪后追加 | 去重后追加 | 整份覆盖 | 去发一个拉取请求 |
| **应用幂等吗** | 不幂等(靠偏移) | 幂等(靠 id 去重) | 幂等 | 幂等 |
| **丢一帧的后果**<br>(**只发生在断线之后**;<br>连接活着时不丢帧, §4.4) | 接不上 → 重新进房 | 接不上 → 重新进房 | 下一帧盖回来(自愈) | 停在旧数据(等下次戳)<br>重连会重进房, 也自愈 |
| **溢出/太大时** | 申报基准 + 回差值<br>**不许整页重拉** | 分页 + 整页重拉<br>(重拉有效) | 退回类一或类四<br>重新走 §2.1 | (本来就没内容) |
| **带宽** | O(n), 常数近 1 | O(n) | O(变更次数 × 整份) | O(变更次数 × 全量) |
| **额外 RTT** | 0 | 0 | 0 | 1 |
| **典型翻车** | 错位且静默 | 漏一条且无人发现 | 旧数据贴新号 | 被按 id 丢掉 |

**一条贯穿四类的判据: 只有类三需要一个外生的号, 也就只有它需要一个受保护的整数。**
任何时候你发现类一 / 类二也想加锁, 那说明你在给它们发外生号 —— 回 §2.1 重新找它们的内生号。

### 2.3 一个填好的例子

一个 AI 编程助手的 web 前端, 一个页面同时进 5 个房间:

| 桶 | 装什么 | 类别 | id 字段 | 客户端动作 |
| --- | --- | --- | --- | --- |
| 会话详情·正文 | AI 流式吐字 / 工具调用交错正文 | 类一 | `CallSeq` + `BaseLen` + `Text` | 按偏移裁剪拼接 |
| 会话详情·消息 | 聊天消息列表 | 类二 | `BaseMsgId` + `NewMsgs` | 按 id 去重追加 |
| 会话详情·状态 | 会话/计划/任务列表等约 20 个标量(三个库拼出来的) | 类三 | `Seq` | 整份覆盖 |
| 全局状态 | "运行中 / 排队中"两个数字 | 类三 | `Seq` | 整份覆盖 |
| 会话列表 / 任务列表 / 建任务 | 分页查询结果 | 类四 | 无 | 去拉一次全量 |
| (终端输出黑框) | TUI 尾部十几行, 会整屏上滚, 光标一直在闪 | **不进推送**(2b) | 版本号短路 | 前端 1 秒一轮拉 |

**最后一行是 2b 的实例, 但它走的是 (b) 那条退路, 不是首选的 (a)。**
它曾经放在类三里, 每帧从 37 字节涨到 1183 字节 —— 一桶"看着才 1KB"的东西, 因为**每帧都在变**,
把整条链路的带宽账吃掉了; 拆出推送之后帧回到 37 字节。
**但记录里没写当时为什么选轮询而不是 (a) 的戳一下**, 所以别把这一行当成"轮询是推荐做法"的依据 ——
新的一桶数据碰到同样的形状, 按 2b 的顺序先试 (a)。

顺带: **"统一形状"本身没有价值, 省下来的字节和 RTT 才有。**


## 3. 第 3 步: 写协议帧

### 3.1 帧信封: 只放每帧真的会变的东西

**信封预算: <= 64 字节。这是硬断言, 不是目标。**

一帧的信封只允许有: 帧类型 / **房间句柄** / 该桶的 id 字段 / map 头 / ws 帧头。

必须做的三件事:

1. **房间用整数句柄, 不用房间名字符串。** 句柄 = 进程内递增的小整数, 房间销毁重建时换号。
   > 违反后果: `"房间类型:20 位 id"` 这种字符串每帧要 30+ 字节, 而一帧正文才 24 字节。
2. **不要单独的房间纪元字段 —— 句柄兼任纪元。**
   房间只在最后一条连接离开时销毁, 所以"客户端还在房里期间号不会变"是**结构性成立**的。
3. **用整数键的二进制编码**(msgpack 整数键或等价物), 不用可读字段名。
   > 违反后果: 可读字段名 164 字节 → 整数键 37 字节。只换二进制不换键只能到 136 字节, **换键才是大头**。

再加两条纪律:

* **别让零值上线。** 计数从 0 起算, 编码器跳过零值 —— 否则那些"戳一下"类的帧会白背一个恒为 0 的 `Seq`。
  守这条的就是上面那 64 字节的硬断言: **加字段之前先看它还剩多少。**
* **只有"重放会出错"的帧才带 Seq。** 判据是"重放会不会出错", **不是"带没带状态桶"**。
  幂等的追加帧不带。
  > 违反后果: 用"带没带状态桶"当判据, 会漏掉"同一条 CallId 的第一截正文也是整份替换"那一格。

### 3.2 帧类型清单(可直接抄)

    // 连接级
    ping / pong
    hello                      // 客户端第一帧, 带协议版本
    deny{Reason}               // 服务端拒绝, Reason 必须让用户看得见

    // 进房
    roomEnter{RoomKey, 客户端申报的基准...}    // 基准: 见 3.3
    roomHandle{RoomKey, RoomHandle}            // "这个房间的句柄是几号", 见下面那条
    roomEntered{RoomHandle, ServerEpoch, 快照 + 差值 + Seq, NeedFullReload: bool}
    roomLeave{RoomHandle}

    // 推送
    roomChange{RoomHandle, [各桶的段, 每段可缺席], Seq?}

**`roomHandle` 必须有, 而且必须在订阅的那把锁里就排进写队列。**

`roomChange` 只带整数句柄不带房间名(§3.1), 而客户端是**按房间**缓冲 pending 广播的(§5.2) ——
所以它必须在收到第一帧 `roomChange` 之前就知道这个房间的句柄。
`roomEntered` 来得太晚: §4.2 第一步订阅之后广播就开始发了, 而应答要等第二、三步。

    第一步(锁内): 登记连接进房间 -> **同一把锁里** pushFrame(roomHandle)
    // 于是"roomHandle 一定排在本房间任何一帧 roomChange 之前"由 FIFO 结构性保证

> 违反后果: 客户端收到一个认不出的句柄, 只能整帧扔掉 —— **首次进房窗口内的广播全部静默丢失**,
> 而这正是 §8.1 那个 A/B 段场景要压的东西。
> (退而求其次的做法是"按连接缓冲所有未知句柄的帧, 拿到应答再按句柄捞出来", 那要多一个
> 连接级的缓冲和它自己的上限 —— 多一个状态, 不如多一帧十几字节。)
>
> 重新进房(resync / 应答超时重发)时**句柄不要清**: 房间只在最后一条连接离开时销毁, 重进一次不换号。
> 清掉反而会让这次应答回来之前的广播全被当成"不认识的号"扔掉。要清的是"我和服务端对齐着"这个标记。

**清单里没有任何一个"单独发的降级帧", 这是故意的。**

* `NeedFullReload` **不是一帧**, 它是进房应答 `roomEntered` 上的**一个布尔字段**(§3.4)。
* 没有 `roomResync{RoomHandle}`("我丢过帧, 你重新进房")这种帧 —— **这件事不存在**:
  连接活着的时候不丢帧, 缓冲装不下一律断线(§4.4)。
  > 违反后果: 那一帧"我丢过东西"**自己也在同一个装不下的队列里**。为了让它发得出去要给它单开一笔预算,
  > 那笔预算的容量算不出来于是要按房间去重, 去重会漏所以客户端又不能按 id 丢它 ——
  > 一条修补链长出四个互相咬合的设计, 而它们服务的是一个"关掉连接"就消失的问题。

**纪元 = 所有 id 的作用域, 它本身不是 id。** 两级:

* `ServerEpoch`: 进程纪元, 进程重启换值。
* `RoomHandle`: 房间句柄, 房间销毁重建换号。

纪元一变, 下面所有的号(字节长度 / 消息 id 链 / Seq)全部作废, 客户端无条件重新对齐。

> 违反后果: 没有纪元, 重启后的新变更会被当成旧消息忽略; 或者拿旧句柄下的号去比新句柄下的号, 撞上。
> 有了纪元, "跨重启单调的 id"这个不可能的需求就消失了, "房间不存在期间的变更"也不需要任何补偿逻辑。

### 3.3 各类的帧字段

**类一 正文流:**

    段: {Mode: append|full, BaseLen: int, Text: string}
    外层帧带: CallSeq          // 命名空间代号, 一帧里多段正文共用一份
    roomEnter 申报: {CallId, 我手上有多少字节}
    roomEntered 回带: CallSeq  // 客户端从这一帧把代号对齐过来

* **帧里必须同时有区间两端**: `BaseLen`(接在哪) + `Text` 的长度(接完到哪)。
  > 违反后果: 只有一端时, 客户端**只能靠"双方都记得上次到哪"**对齐,
  > 而这份记忆会因为断线/重连/整页重拉而分叉; 分叉后每次追加都接到错位置, 且 id 一路连续,
  > 没有任何东西会纠正它 —— **静默且不可恢复**。
* **`CallId` 不是版本号, 是字节空间的命名空间。** 正文会变短的所有情况(一次调用结束 / 换一条调用)
  它必须跟着变, 变了就走 `full` 整份换。**这是"只追加"这条前提的唯一守卫。**
* **每一帧都必须带这个命名空间**, 而且客户端**每一帧都要判它**(§5.3)。
  它不是"只在换的时候带一下"的东西 —— `BaseLen` 只在同一个命名空间内有意义,
  没有它, 一帧属于旧 call 的 `append` 会被硬接到新 call 的正文屁股上。
  > 违反后果: **静默错位**, 而且 `BaseLen` 一路连续, 没有任何东西会纠正它。
* **帧里带的是"代号"(进程内递增的小整数 `CallSeq`), 不是那个二十来字节的 `CallId` 字符串。**
  这是每帧都要判的东西, 带字符串等于每批变更白扔二十字节。两者是同一件事的两个字节版本:
  `CallId` 只出现在 `roomEnter` 申报里(客户端是从全量拉取那条路知道它的, 那条路给不出房间内部的代号),
  服务端进房时把代号回给客户端, 从此每帧只比代号。
* **别在每段正文里各带一份**, 放外层 —— 一帧里多段正文永远属于同一条 call。
  > 违反后果: 每批变更白扔七八十字节, 而一批正文才 24 字节。
* 客户端"还不知道代号"要有一个表示法(用 0)。刚整页拉过、还没进房时就是这个状态,
  此时**不判命名空间**(判不了), 由随后那次进房把代号对齐过来。

**类二 消息流:**

    段: {BaseMsgId: string, NewMsgs: []Msg}
    roomEnter 申报: {我的 LastMsgId}

* **左端点 `BaseMsgId` 必须带。**
  > 违反后果: 客户端停在 m3 收到 [m5,m6] 时**根本判断不出 m4 存不存在** ——
  > 离散 id 之间没有"下一个"的概念, 光看 id 发现不了空洞, 漏的那条会永久漏掉且无人发现。
* `BaseMsgId` 是空串是**合法值**(本批从最早一条开始), 判"有没有这一段"要看 `len(NewMsgs)`。
* 消息 id 必须**全序、不复用、不回收**。自增 / 雪花都行。
  > 违反后果: 拿"第几条"当 id, 条数会因为去重 / 补拉窗口而两边对不上。
  >
  > 全序**不只是为了排序**, 客户端的缺口判断直接建立在"能比大小"上面(§5.3 类二)。

**类三 全量推:**

    段: 整份字段(或字段级 diff: 缺席 = 没变)
    帧带: Seq

* **"没变"和"变成空"必须分得开** —— 用 `HasXxx` 布尔或 `*string` 指针。
  > 违反后果: "列表清空了"被当成"这次没带这个字段", 界面永远清不掉。
* 如果做字段级 diff(B 的变体): **这类帧必须带 Seq 才能剔重**, 因为它的应用不再幂等。

**类四 戳一下 / 指令:**

    只有 RoomKey (deny 多一个 Reason)。几十到两百字节。

### 3.4 `NeedFullReload`: 唯一用途 + 有效判据

**这是整篇最容易被想歪的一段, 别跳过。** 它看着像"通用的出错通知口子", 而它不是。

**它唯一的用途: 这次的进房应答太大了, 服务端让客户端走 http 拉一次。**

| | |
| --- | --- |
| **它是什么** | 进房应答 `roomEntered` 上的**一个布尔字段**。不是一帧, 没有独立的帧类型 |
| **谁在什么时候发** | 服务端, 在**组装这份应答的时候**, 发现这一份给不了 |
| **"给不了"是什么意思** | 只有一个意思: **太大**。没有第二个意思 |
| **客户端收到干什么** | 一件事: 发一个普通的 http 请求把整页拉回来, 然后带着新基准重新进一次房。<br>**不重连、不重试、不碰这条连接** —— 连接一直好好的 |
| **为什么 http 接得住** | http 响应体**没有体积上限**(流式下发, 只有请求头有上限); 长连接上那些上限全是你自己设的。<br>所以"退回 http"是整套设计的**最终兜底**, 它下面没有别的路了 —— 这也正是它值得存在的全部理由 |

**不许拿它干别的。** 下面这些看着都像"出问题了要告诉客户端", 但每一件都有自己的路:

    连接跟不上了 / 写队列满了       -> **断线**(§4.4)。这里一个 NeedFullReload 都不该出现
    客户端发现某一桶接不上          -> **重新进房**(§5.3)
    服务端拒绝这条连接 / 要用户刷新  -> **deny**(它才是终态信号, 带 Reason 给用户看)
    "我丢过一帧, 你重新对齐一下"    -> **这件事不存在**(§3.2)

**有效判据(写窄了就会漏):**

> **`NeedFullReload` 有效, 当且仅当"这次应答有多大"是客户端申报游标的函数。**

理由一句话: 它的全部作用是让客户端**换一份新的游标再来问**。拉完再来问, 如果答案还是一样大,
那这条路什么都没改变 —— 那不叫降级, 那叫每 5 秒白拉一次的死循环。
客户端能申报的游标就那么几个(§3.3 各类的 `roomEnter` 申报字段)。
**应答里的每一样东西, 要么它的大小被这些游标管着(拉完就变小), 要么它就不该在应答里 —— 没有第三种情况。**

从这一句直接推出两条硬规矩:

**推论一: 类一(正文流)那一桶永远不许走 `NeedFullReload`。**
全文有多大, 和客户端重拉过几次没有任何关系 —— 拉完还是一样大, 无限重拉。
它走的是"客户端申报基准 + 服务端只回差值", 结构上就不会大。

**推论二: 进房应答里不许出现"大小由用户决定、又不在任何游标里"的字段。**
这种字段一旦把应答顶过上限就触发推论一那个死循环, 而且**界面上完全正常**
(http 那条路没有上限, 内容照常显示), 只是每 5 秒白烧一次全量拉取, 没人会发现。

> 真踩过: 用户输入框里还没发出去的**草稿**跟着会话状态整份进了应答,
> 粘一段几百 KB 的日志进输入框就永久循环。
> **修法不是给它做降级, 是把它从推送这条路上摘掉**(组装应答时清空; 推送这一侧本来就一个消费者都没有)。
> 检查手法见 §9 D23。

反过来说清楚它为什么**够用**: 现在触发它的两条(§7 第一组 a/b)都被游标管着 ——
重拉把消息游标推到最新, 下次要补的条数变少; 重拉之后客户端手上就是全文, 申报的长度等于全文长度, 差值直接归零。
**两条都是一次就收敛**, 所以场景里可以把"整页重拉恰好 1 次"直接写成断言。


## 4. 第 4 步: 写服务端

### 4.1 房间状态: 不可变快照 + 原子指针

**照这个写, 别自己发明:**

    type RoomState_t struct {   // 不可变。要改就整个换一个新的
        Seq        int64        // 类三那一桶的号, 从 0 起算
        LastMsgId  string       // 类二的游标
        Text       string       // 类一的当前全文
        CallId     string
        ... 类三那些标量
    }

    type Room_t struct {
        Handle int64
        state  atomic.Pointer[RoomState_t]
        conns  map[*Conn_t]struct{}    // 由全局锁保护
    }

    写侧(worker): 读库 -> 组装一份全新的 state(Seq = 旧 Seq + 1) -> Store 指针 -> 广播
    读侧(进房):   Load 一次指针, 数据和 Seq 一起拿到

* **单写者多读者**: 同一个房间同时只有一个 worker 在改(脏房间 id 去重 + 等一轮做完才进下一轮)。
* **初值谁装**: 谁先到谁 `CompareAndSwap(nil, 新的)`。CAS 失败就用别人那份, 自己那次读库白读 ——
  **那是锁外的白读, 不阻塞任何人**, 比"所有人排队等一次读"好。

> 为什么用不可变快照而不是裸 seqlock: 一次 `Load` 同时拿到数据和它的号,
> "读侧先读哪个"这条纪律**自动成立**, 只剩写侧要人守。

### 4.2 进房: 三步, 锁的边界画在第一步和第二步之间

    第一步 (全局锁内, 纯内存, O(1)): 订阅
        检查单连接进房数上限
        -> 取或建房间对象 (**只建壳, 不读 DB**)
        -> 把连接登记进房间
        -> **同一把锁里** pushFrame(roomHandle)      // 见 §3.2, 少了它首次进房的广播全被扔掉
        // 这一步之后, 这条连接就已经是这个房间广播的收件人了

    第二步 (完全无锁): 取快照
        room.state.Load()   // nil 就读库 + CAS 装初值

    第三步 (完全无锁, 有 DB IO): 按客户端申报的基准算这次要给的东西
        类一: **先比命名空间**: 申报的 CallId != 快照的 -> 回 full 整份;
              一样才拿快照正文 vs 申报长度, 只回那一截
        类二: 查区间 (客户端的 LastMsgId, 快照的 LastMsgId], **两端都放进帧**
        类三: 整份给, 标上快照里的 Seq
        // 应答里回上快照的 CallSeq(§3.3 类一), 客户端从这一帧把代号对齐过来

    第四步 (无锁): 编码, pushFrame 送进这条连接的写队列

**三条必须守的:**

* **建房间只建壳, 绝不在锁里读 DB。**
  > 违反后果: 一个正在读大正文的房间会把**所有别的房间**的进房请求一起卡住。
* **第一步和第二步之间有空隙, 广播会插进来。这是故意的, 由客户端缓冲兜(§5.2)。**
* **进房不许为了对齐把房间"拽到现在"**(再读一次库并给全房间推一帧)。只用房间手上那份快照算差值。
* **客户端申报的长度允许超过服务端房间那份**(它可能刚拉过全量, 而房间要等 worker 才前进)。
  这时服务端一个字都不补, 由随后那帧广播自带的偏移让客户端自己裁。

### 4.3 广播: 写侧顺序, 一步都不能换

    业务侧(每批变更一次):
        1) 写库(提交)
        2) fire(roomId)                    // 只标脏 + 唤醒 worker, 纯内存 O(1)

    worker(每个脏房间一个 goroutine, 同一房间同时只有一个):
        3) 无锁读库, 组装一份全新的 state
        4) 和 Load 到的旧 state 比出增量
           没有客户端看得见的变化 -> 到此为止, 不 Store 不广播
        5) 新 state 的 Seq = 旧 Seq + 1, **Store 指针**
        6) 序列化一帧, 扇出给房间里所有连接

**顺序约束: 3 → 5 → 6(数据先于号, 号先于广播)。**

> 违反后果: 顺序反了会发出**旧数据贴新号**(标签高估数据的新鲜度)。后果不是"晚一帧",
> 是**永久静默错误** —— 客户端把自己顶到那个号, 真正属于这个号的帧被判成"不比我新"扔掉,
> 界面停在这里, 看不出任何异常。广播那条路还能被下一次 fire 纠正, **进房那条路纠正不了**。

**三条配套的:**

* **Seq++ 挂在 worker 的 Store 上, 不要让业务侧自己 bump。**
  好处: 业务主流程不用同步读库+扇出; 而且"忘了 bump"退化成"忘了 fire",
  后者漏了会立刻表现成"界面不动"这种**显性**故障, 不会变成一种新的静默 bug。
* **合并是机会主义的: worker 不加任何定时器。** 只有在它正忙着处理上一轮时, 新来的 fire 才被攒到下一轮
  —— 不忙时零延迟, 忙时自动省掉那些"反正马上要被覆盖"的中间态。
  > 违反后果: 加了定时器就变成拿延时换带宽, 那是另一个取舍; 去掉合并则是拿带宽换一点点延时。两边都不做。
* **脏标记必须在第 3 步(读库)之前就取走并清空, 不能等这一轮做完再清。**
  也就是: 一轮开始 → 把整张脏表**换出来** → 拿着这份名单去读库。

      正确:  roomIds := takeDirty()   // 锁内换走整张表, 就地清空
             for _, id := range roomIds { rebuildAndBroadcast(id) }   // 读库在清之后
      错误:  for id := range dirty { rebuild(id) };  clearDirty()     // 读完再清

  > 违反后果: 读库之后、清标记之前到达的那次 fire **会被这一轮的清空吞掉**,
  > 而它带来的变更并没有进这一轮读到的数据里 —— 界面停在旧数据上, 直到下一次别的 fire 把它带出来。
  > 这条**比"忘了 fire"危险**: 忘了 fire 是显性的(那条路一次都不动), 而这个是竞争窗口,
  > 平时全绿, 只在"读库刚好慢一点 + fire 刚好落在窗口里"时丢一帧。查法见 §9 D24。
* **没有客户端可见的变化就一帧都不发**(和旧快照 DeepEqual)。

### 4.4 写缓冲: 一笔账, 装不下就断线

每条连接一条 **FIFO** 写队列(顺序不能乱: 同一个房间的帧必须按发出顺序到达),
**一笔账**, 一个上限(参考值 4MB, §6.1)。

> **装不下一帧 -> 关掉这条连接。不丢帧、不记账、不补发。**

这是本篇最强的一条形状规则, 它有一个总纲(§5.2 的客户端缓冲是它的另一半):

> **凡是"缓冲装不下"引起的异常, 唯一允许的处理是断开这条连接。**
> 不许留着这条旧连接继续跑。

**为什么是这条, 而不是"把丢帧那条降级路径做对" —— 三个理由, 按重要性排:**

1. **测不到的概率极高。** 丢帧补救那类路径只在灾难时才走, 真实环境几个月碰不上一次, 只能靠模拟器人造;
   而断线重连是**天天都在走**的路(网络抖动 / 切 WiFi / 服务重启 / 合盖), 被反复验证过。
   与其给兜底另修一条只在灾难时走的路, 不如让灾难走那条天天都在走的路。
2. **状态组合爆炸。** "丢帧但留着连接"要求两端同时维护一堆跨帧的状态(哪个房间丢过、
   补救帧有没有在队列里排着、缓冲作废了没有), bug 只在特定到达顺序下出现, 正确性无法保障。
   断线只有一个状态转移: 连着 → 断了 → 重连 → 全部房间重进。
3. **在这个架构里断线是安全的**, 因为"我抄到第几页"存在**客户端**手上(进房时申报的那些游标),
   服务端不为任何客户端保存进度。补齐由**重连流程**负责, 不由推送路径负责。

**这也是业界的统一做法, 没有一家在长连接上做"丢这一帧但留着连接":**

| | 上限 | 超了怎么办 |
| --- | --- | --- |
| Redis pub/sub | `client-output-buffer-limit pubsub 32mb 8mb 60` | **关闭连接** |
| NATS | `max_pending` 默认 64MB | 标记 Slow Consumer → **服务端断开** |
| gorilla/websocket 官方 chat 示例 | 发送 channel 满 | 认为客户端已死 → **注销并关闭** |

它们的补齐方式也一样: 重连之后把错过的从主库读回来 —— 就是本篇的"重新进房带游标"。

**由此少掉的三样东西, 别加回来**(§9 D12 就是查这个):

* 写队列**不再分账**(广播 / 应答 / 兜底三笔)。分账的**唯一**理由是"降级帧必须在别的账满了的时候还发得出去";
  没有单独发的降级帧, 这个理由就不存在了。**分账从来不是目的, 它是那条修补链的一环。**
* 没有 `roomResync` 帧, 没有"我答不上来"的空 `NeedFullReload` 兜底帧。
* 没有"兜底帧按房间去重"+"客户端不看配对 Id"这一对咬合设计
  (§5.3 类四那条结论**仍然成立**, 但它现在的理由是纯粹的类四理由, 不再是活锁)。

**扇出时绝不同步阻塞在慢连接的 write 上** —— 否则一个弱网页面能拖住整个房间(队头阻塞, §9 D14)。
"不阻塞"和"装不下就断线"不冲突: **断线是 O(1) 的内存操作**, 扇出循环照样不等任何人。

**唯一一处不占账的帧: `deny`。** 它是终态信号("请刷新页面"), 而且发完连接就没了 ——
让它绕过上限直接排进队列, 是一个三行的特例, **不是一笔账**。

一条连接的服务端内存上界 = 写队列上限。这个数只有"连接被卡满"时才达到(正常态几 KB),
但它必须是一个**你算过的数**(§6.3(a))。

**一条正交但关键的分工:**

> **同一条连接上"帧不丢"由传输层保证(FIFO + 装不下就断线), 不由 id 保证。**
> id 只负责"跨来源"(快照 vs 广播)的对齐和剔重。想清楚这条分工能省掉一堆假想的连续性检查。

两条直接推论:

* **类三的 Seq 会跳号, 不许拿它判连续** —— 没有客户端可见变化的版本压根不发帧(§4.3 第 4 步),
  所以"号不连续"是正常现象, 不是丢帧。
* **传输上的缺口不存在。** 队列装不下的那一刻连接就断了, 断线由重连 + 重新进房收敛;
  **没有"连接还在但中间少了一段"这种状态。** 内容上的缺口由各桶自己的 id 发现(`BaseLen` / `BaseMsgId`)。

### 4.5 锁: 列一张清单, 定期逐个划掉

写完之后把服务端**所有**的锁列出来(全局的、每房间的、每连接的, 一个都不能漏), 逐个问:

1. 临界区里(含 `defer Unlock` 覆盖的整个函数体)有没有 **DB 查询**? 顺着调用往下追到底。
2. 有没有 `json.Marshal` / 序列化一份用户数据?
3. 有没有 O(某个用户的数据量) 的字符串比较 / 切片?

**有任何一个 = 不通过。修法不是再拆一层锁**(那只是缩小受害面), 而是回答:
这段代码为什么非得在锁里跑? 如果答案是"为了让某个版本号有意义", 就照 §2.1 换一个内生的号。

参考落点: 一个做对了的实现里只剩四把锁 —— 全局房间/连接表锁、脏标记锁、worker 句柄锁、每连接自己的锁,
**里面全是 O(1) 内存操作**。

### 4.6 goroutine: 每个 `go` 都要能停, 且停机要等它真的退出

把文件里所有 `go xxx()` 找出来, 逐个回答三句:

1. **谁能让它停?** 找不到答案的就是"起得来停不下来"。
2. 停它的那个函数, 是**通知完就返回**, 还是**等到它真的退出才返回**? **只通知不等待等于没停。**
3. 它读写的东西(全局服务 / db / 时钟 / 房间表)会不会在它退出之前就被别人换掉或关掉?

**一个必须注意的形状**: "等一个 goroutine 退出"这件事**必须在放开锁之后做** ——
拿着锁去等 goroutine 退出是标准的死锁形状。


## 5. 第 5 步: 写客户端

### 5.1 连接

* 应用层 **ping/pong + 两端读超时**。不要只依赖 socket 的关闭回调。
  > 违反后果: 中间盒丢包 / 客户端换 IP 时 TCP 仍是 ESTABLISHED, 你永远发现不了该重连(静默死链)。
* **无限重连**, 最小间隔 + 随机抖动。抖动是给服务端重启准备的(所有连接同时掉线同时重连)。
* 重连之后, 对**所有活跃房间**重发 `roomEnter`, 并**申报自己手上有什么**。

### 5.2 进房: pending 缓冲 + 重放

    发出 roomEnter 之后, 这个房间进入 pending:
        收到的 roomChange **缓冲**起来, 不直接应用
        (那些帧的基准还没确定)

**缓冲是按房间的, 所以"这一帧属于哪个房间"必须当场答得出来** —— 靠句柄表,
而句柄表是 `roomHandle` 那一帧建起来的(§3.2), 它保证排在本房间任何 `roomChange` 之前。
认不出的句柄一律整帧扔掉(那是上一代房间, 或者已经不在的房间)。

    收到 roomEntered 之后:
        1) 先应用快照
        2) 把缓冲**按到达顺序**重放, **每一桶用自己的 id 判**:
               帧的纪元和应答的对不上 -> 整帧扔掉
               类一段: 按 §5.3 三选一
               类二段: 按 §5.3 三选一
               类三段: Seq <= 我的就扔, 大于就整份覆盖
        3) 清空缓冲, 房间恢复正常

* **缓冲必须有上限**(帧数 + 字节数)。
  **注意这个上限是"每房间"的, 而重连时所有活跃房间会一起 pending** ——
  连接级的内存上界是 `同时进的房间数 × 这个上限`, 不是这个上限。算 §6.3(b) 时用后者。
* **溢出时不是丢最旧那几帧** —— 那会造成静默空洞。
  也**不是**"整个缓冲作废 + 应用完快照立刻重新进一次房" —— 那条路已经删掉了。
  正确做法: **关掉连接**, 由重连重进所有房间收敛(§4.4 那条总纲的另一半)。
  > 上限本身要留一个数量级余量(§6.3(b)), 正常进房碰不到它。
  >
  > 这一条和服务端那边有一点**不对称, 记在这里免得以后有人当成 bug**:
  > 服务端队列满意味着"这条连接真的跟不上了"(连接病了); 客户端缓冲满只意味着
  > "我在等进房应答期间服务端发得很多"(连接是健康的, 只是忙)。按体感, 后者本来更适合
  > "只重进这一个房间"。**仍然统一成断线, 就是 §4.4 那三个理由**:
  > 少一条只在灾难时走的路, 比省这一次卡顿值。
* **房间级超时必须有, 而且独立于连接**: 记下"这次进房是什么时候发出去的",
  超过一个读超时还没等到应答就**重发 `roomEnter`**。
  > 违反后果: 应答永远不到时, 房间永远停在旧数据上, 而连接是健康的、心跳照跑,
  > **连接级探活完全看不见它**。这条规矩推广开就是: **连接活着 != 房间活着。**
  > 有了缓冲之后这条**仍然必须留着** —— 一个刚打开页面、手上什么都没有的客户端,
  > 没有快照就是白屏, 缓冲再多也渲染不出来。

### 5.3 应用增量: 每类的规则(没有第四条)

**类一 正文流** —— **第 0 条: 先判命名空间, 不是三条是四条。**

    两边的代号都已知 且 帧的代号 != 我的代号
        -> 重新进房。**不许往下走**(两份根本不是一套字节空间)
    (我的代号 = 0 "还不知道", 判不了, 跳过这一条; 由这次进房把代号对齐过来)

> 违反后果: 拿旧 call 的 `BaseLen` 和新 call 的长度比大小, 然后把旧 call 的字节接到新 call 后面
> —— **静默错位**, 而且 `BaseLen` 一路连续, 没有任何东西会纠正它。
> 这一条**在 `append` 上和在 `full` 上一样必要**, 别只在 `full` 那一格判。

`append` 模式(过了第 0 条之后):

    我 >= BaseLen + len(Text)   整帧我都有 -> 扔
    BaseLen <= 我               裁掉重叠的一截再接
    我 <  BaseLen               中间缺了   -> 重新进房(带上我现在的长度)

`full` 模式:

    同代号 且 我不比它短   -> 保留我的(防回退)
    换了代号               -> 必须整份换掉(旧 call 的残留不能留在屏幕上)

* 应用完之后**把我的代号更新成帧里那个**。
* **防回退只在同一个代号内成立, 跨代号是故意不防的** —— 客户端光看代号分不出"更老"还是"更新",
  所以它不比大小, 只判等。
  > 那跨代号的回退谁来收敛? **靠 §4.3 的"Store 必配广播"+ 同连接 FIFO**:
  > 让快照前进到新 call 的那一次 `Store`, 后面必然紧跟一帧广播, 而这条连接在第一步就订阅好了,
  > 所以那一帧必然排在旧帧后面、必然会被应用。重放按到达顺序走, **最后落地的一定是最新的那一帧**。
  > 中间态会在屏幕上闪一下, 那是体验不是正确性。
  > **反过来说: 一旦你在 §4.3 里加了"Store 了但这次不广播"的分支, 这条论证就断了。**

**类二 消息流** —— **按序比较, 不是集合成员判定:**

    BaseMsgId == 我的游标   -> 追加, 游标推到帧里最后一条
    BaseMsgId <  我的游标   -> 按 id 去重后追加(重复是安全的那一边)
    BaseMsgId >  我的游标   -> 中间缺了 -> 重新进房

> 违反后果(写成"在不在我已有的消息里"): 客户端只保留一个窗口(进房补拉有条数上限, 整页拉取也分页),
> 于是 `BaseMsgId` 比我窗口里最早那条还老时, 会被判成"没见过 → 重新进房" —— 而它明明 <= 我的游标,
> 中间一条都没缺。§4.2 又明确允许客户端游标比服务端快照新, 所以这是**会稳定复现的一次白进房**。
> **id 全序就是用来做这个比较的**(§3.3 类二), 别退回集合判定。

去重**按 id, 不按位置**。

**类三 全量推:**

    Seq <= 我的  -> 扔
    Seq >  我的  -> **整份覆盖** 并更新我的 Seq

> 违反后果: 改成"字段级差量地应用", 幂等就没了, 于是要求号严格连续, 于是服务端又要一把锁。
> 这一类的全部宽容度("多收敛一次啥事没有")都来自"整份覆盖是幂等的"。

**类四 指令: 绝不许按 id / 按新旧丢弃。**

> 违反后果: 快照会过期, "你去重拉"不会 —— 它什么时候执行都是对的。按 Id 丢掉它只是白白多绕一轮。
>
> 历史上这条的理由更硬, 记在这里免得有人"顺手把 Id 判断加回来":
> `NeedFullReload` 曾经是**单独一帧**, 偏偏总在队列积压时才发出, 到达时客户端多半已经超时重发过,
> 配对 Id 必然对不上, 按 Id 丢就是**活锁**。那个形状已经删了(§3.2 / §4.4), **但结论不变** ——
> 它现在的理由是纯粹的类四理由。

### 5.4 客户端侧的两条降级纪律

* **自己合并连续的戳**(整页重拉设一个最小间隔, 如 5s), 否则一次爆发就是 N 次全量拉取。
  **限速期间要排队, 不许丢弃。**
  > 违反后果: 丢了就再没人来对齐了 —— 连接是健康的、各桶的号也是连续的, **两条回退路径一条都不会触发**。
* **进房应答里的增量接不上时, 不能原样再进一次房** —— 基准没变, 答案也不会变, 死循环。
  只能整页重拉换一份新基准。

### 5.5 客户端里所有"我在等 X"的状态, 逐个登记

把代码里所有 `if (还在等 X) { 丢掉 / 缓冲 }` 找出来, 每个填一行:

| 在等什么 | 等待期间收到的东西怎么处理 | 谁把它踢回去(超时) | 上限 | 溢出走哪条路 |
| --- | --- | --- | --- | --- |
| 进房应答 | 缓冲(按房间, 靠句柄归类) | 房间级超时, 重发 roomEnter | 64 帧 / 1MB **每房间** | **关掉连接**, 重连重进所有房间(§5.2) |
| (整页重拉在飞) | 丢弃该房间的推送和应答 | **拉取请求自己的超时** | — | — |

**第二行是最容易漏的一格, 而且真的漏过**: "等一个 ajax"也算一个冻结点。
那几个 POST 原来没传超时 —— 连接健康、进房超时也不会响(每次都收到了应答, 只是被丢掉),
房间就永远停在旧数据上。**修法: 凡是在"重拉计数 ++ 和 --"之间 await 的请求, 一律带超时。**


## 6. 第 6 步: 参数表 + 两条不变式

### 6.1 参数表(参考值, 按自己的业务调, 但要重算 §6.3)

| 参数 | 参考值 |
| --- | --- |
| 写队列上限(**唯一一笔**, 装不下就断线) | 4MB |
| 单次进房应答上限 | 256KB |
| 一次补拉消息条数上限 | 50 |
| 单条连接最多进房数 | 256 |
| 客户端等待缓冲上限 | 64 帧 / 1MB(**每房间**, 连接级要乘房间数, §6.3(b)) |
| 整页重拉最小间隔 | 5s(**限速期间排队, 不丢弃**, §5.4) |
| 客户端心跳 / 读超时 | 4.5s / 10s |
| 服务端读超时 | 120s(客户端的 12 倍, 保证客户端先发现) |
| 单帧写超时 | 30s |
| 进房应答超时 | **= 客户端读超时**(不新增配置项) |
| 最小重连间隔 / 抖动 | 5s / 2.5s |

### 6.2 时间参数按**真实网络的 RTT** 选, 不按开发机选

* 心跳 4.5s / 读超时 10s: RTT 350ms 时一次 ping-pong 往返 0.7s, 六倍余量;
  读超时是心跳的两倍多, 所以**丢一个 pong 不会误杀健康连接**。
  > 违反后果: 按开发机 RTT 压缩这两个数, 在真实网络上变成周期性假断连 + 重连风暴。
* 进房应答超时复用读超时: 正常应答是"一个 RTT + 一次读库"。
* 服务端读超时必须**远大于**客户端读超时, 保证**客户端先发现**断连。

### 6.3 两条必须成立的参数不变式(改任何一个数之前先重算)

**先注意它们的性质变了。**
"装不下就断线"(§4.4)生效之前, 这几条是**正确性前提** —— 算错了就是活锁。
现在算错的后果只是"没事就断一次线", 是**体验问题不是正确性问题**。
**账还是要算, 但它降级成了调参**, 所以下面每条只回答一个问题:
**这个数够不够大, 让正常操作碰不到断线?**

**(a) 单次进房应答上限 × 单条连接可能同时进的房间数 × 重试轮数 <= 写队列上限。**
例: 256KB × 5 = 1.25MB, 4MB 给到三轮余量。

"重试轮数"这个因子是**真实的**: 客户端整页重拉完会再进一次房(那条路不看长连接的状态),
上一份应答还没写出去时第二份就排进来了。
**以前这条必须做实**(否则活锁), **现在超了就是断线重连, 所以留余量就够, 不需要去重。**

> 中间那个因子按"一个页面上来会同时进几个房间"算就行, **不用按系统强制的进房上限算**。
> 那个上限(§6.1 里是 256)是防 bug 导致的无限进房用的, 不是一个会被正常用满的数;
> 而且**同时进的房间不等于同时有流量** —— 按上限乘出来的是一个不会发生的最坏值。

> 横向参照: Redis pub/sub 给订阅者的硬上限是 32MB, NATS 是 64MB —— 4MB 仍然偏小。
> 偏小可以是故意的(连接数个位数时内存更金贵), 但**再往小调之前先读这一段**。

**(b) 客户端等待缓冲上限 >= 一个 pending 窗口内正常能收到的广播量。**
例: 每批变更一帧、每帧一两百字节 → 64 帧 / 1MB。
**这条比以前更重要了: 以前溢出只是多绕一轮, 现在溢出是断线。**

**分母是 pending 窗口, 不是读超时。** 窗口 ≈ 一个 RTT + 一次读库(毫秒级),
**不是**进房超时那 10 秒 —— 拿 10 秒当分母算出来的余量是虚的。
**RTT 直接进这条账, 必须按真实 RTT 复核, 不能按开发机复核。**
> 违反后果: 按开发机算会得出"永远不会溢出"的结论, 于是 §9 的 D18(b) 那条溢出路径再也没人写场景。

**分子要按最热的那一桶的真实 fire 频率算, 不是按"每批变更一帧"这句话算。**
类一(流式吐字)一秒可能几十次 fire; worker 的机会主义合并只在它**正忙**时才起作用,
一轮几毫秒时合并率很低。**这个数是要按业务量重算的, 别照抄 64。**

**连接级还要再乘一次房间数**(§5.2): 上限是每房间的, 重连时所有活跃房间一起 pending,
连接的内存上界 = `同时进的房间数 × 这个上限`。**参数表上写的是每房间的数, 别当成连接的数。**

**(c)(已删除)** 原"兜底帧大小 × 单连接进房数上限 <= 兜底账上限"。
兜底帧和兜底账都没了(§4.4)。**编号留着不复用**, 免得引用它的地方指到别的条目上。

**一条不依赖上面这几笔账、因而留下来的纪律: 给帧信封加字段是有预算的, 尤其别让零值也上线**(§3.1)。
以前守它的是兜底账, 现在守它的是 §1.2 那条"每帧信封 <= 64 字节"的硬断言。


## 7. 第 7 步: 登记每一条降级路径

优化必然带来上限, 有上限就必然有降级("这次我给不了, 你退回去用笨办法")。
**每一条都填进这张表, 填不出第三列的就是活锁 —— 不是"慢一点", 是永远不收敛。**

贯穿全章的一句判据, 先记住它:

> **一条降级路径存在的理由, 是它能让"下一次尝试"变得不一样。做不到这一点的一律不要有。**

**降级路径只有下面三组。分组的判据是"这件事在哪一步被发现的" —— 别按"它是不是叫降级"来分。**

**第一组 —— 发之前就算出来这一份太大**: 结论塞进正常应答, 连接照常活着, 客户端走 http。

| 触发 | 动作 | **再来一次哪里不一样** | 有效? |
| --- | --- | --- | --- |
| (a) 缺的消息太多(> 条数上限) | 应答里 `NeedFullReload=true` | 重拉把游标推到最新, 下次要补的条数变少 | ✅ |
| (b) 单次进房应答太大 / 序列化失败 | 应答里 `NeedFullReload=true` | 重拉后客户端申报的长度 = 全文长度, 差值没了 | ✅ |
| (c) **正文本身就长** | **不许 `NeedFullReload`** | 全文多大和重拉过几次**没有任何关系** | ❌ **无限重拉** |

> (a) 里那个条数上限本身是"体积太大"的一个**便宜的前置判断**: 不查库就能判, 省掉一次注定要作废的大查询。
> 它和 (b) 是**同一件事的两个测法**, 不是两种不同的降级。
>
> (c) 是这张表存在的理由: 类一的"太大"只能靠"申报基准 + 只回差值"解决(§3.4 推论一),
> 它压根不该走到"太大"这一步, 因此**也不属于任何一组降级**。

**第二组 —— 收到之后才发现接不上**: 重新进房换一份新基准, 连接照常活着。

| 触发 | 动作 | **再来一次哪里不一样** | 有效? |
| --- | --- | --- | --- |
| (d) 某一桶接不上(`BaseLen` 对不上 / `BaseMsgId` 有洞) | 重新进房 | 进房带的是客户端**当前**的基准, 服务端据此重算, 一定接得上 | ✅ |

> 特例: **进房应答自己**接不上时不能原样再进一次房(基准没变, 答案也不会变 = 死循环),
> 只能整页重拉换一份新基准 —— **这一格才是 (d) 掉进 (a)/(b) 那条 http 退路的地方。**

**第三组 —— 已经排进缓冲了才发现放不下**: 一律断开连接(§4.4)。

| 触发 | 动作 | **再来一次哪里不一样** | 有效? |
| --- | --- | --- | --- |
| (e) 服务端写队列装不下一帧 | **关掉这条连接** | **队列被整个丢弃, 重连是从空队列开始的** —— 这才是严格改变的那个输入 | ✅ |
| (f) 客户端等待缓冲装不下一帧 | **关掉这条连接** | 同上(缓冲清空) | ✅ |

**(e)(f) 第三列不能写成"重连时申报当前基准"** —— 那个论证是**不成立**的:
断线可能发生在应答写出去之前, 这时客户端的基准一个字节都没变, 下一次进房的输入和这一次完全一样。
**真正让它有效的是"队列/缓冲被清空"**, 这是无条件成立的。

**第一组和第三组的分界线就是"发之前 / 发之后":**
发之前知道, 结论就能搭在那份应答上, **结构上丢不掉**;
发之后才知道, 那句"我丢了东西"**自己也在同一个装不下的队列里**, 于是只能断线。

**第三组没有任何补发 / 记账 / 事后通知**, 三样删掉的东西列在 §4.4, 别加回来。


## 8. 第 8 步: 搭测试

### 8.1 要覆盖什么(场景清单)

分两组, 两组都要有:

**网络类** —— 逐条验 §1.2 的正确性目标:
断线重连 / 换 IP / 静默死链(只丢包不 RST)/ 服务端重启 / 房间重建 /
两个客户端停在正文的**不同字节**上收同一帧 / 长时间离线后上线 / 随机混沌压测 /
**类一换命名空间**(旧 call 跑完接新 call, 断言客户端没把新 call 的字节接到旧 call 屁股上, §9 D25)。

**缓冲类** —— 逐条验降级路径(§7 三组各自都要有):
服务端写队列压满(**断线**)/ 进房应答太大(`NeedFullReload`)/ 缺的消息太多(`NeedFullReload`)/
慢客户端不影响快客户端 / 进房应答一直不来(房间级超时)/ 进房窗口 A 段与 B 段 /
客户端等待缓冲溢出(**断线**)/ 用户可控大小的字段把应答顶爆(§9 D23, 断言**两次进房都不许** `NeedFullReload`)。

> 第三组那两条(断线)的断言要写成"**客户端确实断了一次线, 重连之后收敛**",
> 而且**不许靠整页重拉 / 进房超时把场收了** —— 那些都是更贵的下一层, 让它们兜住的话这个场景就是空转的。
>
> 压客户端缓冲溢出时**撑帧数不要撑字节数**: 字节上限要灌几十 KB, 会先顶掉服务端的写队列,
> 压出来的就成了另一条路(服务端断线)。

**进房窗口那个场景要分两半压, 而且三桶各压一遍**(这是最容易漏的一组):

    用两个延时钩子把 §4.2 第一步和第二步之间的窗口撑开:
        A 段: 广播比快照旧 -> **必须剔掉**, 否则重复应用
        B 段: 广播比快照新 -> **必须重放**, 否则静默漏一段
    然后: 一个场景只灌类一, 另一个分两段只灌类二 / 只灌类三

> 为什么要每桶各压一遍: 只灌正文的话, 消息和状态那两段判断**根本不会被执行到**,
> 一桶的 id 写错不会被另一桶掩盖 —— 反过来说, 也就抓不到。

**两个陷阱:**

* 压类三那一半只能改**一次**状态。改两次(A→B→A)会被 worker 合并成"和快照相比没变",
  一帧都不发, 窗口就白开了。**机会主义合并在写场景时是个陷阱。**
* **这组场景本身依赖 `roomHandle` 那一帧**(§3.2): 窗口撑开期间客户端还没收到 `roomEntered`,
  认不出句柄就整帧扔掉, 于是 A/B 两段都"通过"了 —— **一个什么都没验的绿。**
  所以这组场景要**两头都断**(§8.2 第 3 条): 先断言"这个窗口里客户端确实缓冲到了 N 帧",
  再断言"重放之后收敛到了 X"。

### 8.2 四条测试纪律

1. **真 TCP, 不靠 `if` 跳进降级分支。** 看"缓冲被压满了几次"这个计数器
   (现在的表现是**断线**, 不是丢帧): **它是 0 却绿了 = 这个测试在空转。**
2. **打印不算数, 断言才算数。** 场景里"这条路走到了 N 次"如果是覆盖证据, 就**必须是断言**。
   > 光打印的话它悄悄变成 0 也没人会发现 —— 一个从来没红过的分支和没写的分支一样可靠。
3. **覆盖证据要两头都断。** 结尾"于是走到了 Y"要断言, 开头"我已经把环境弄成 X 了"**同样要断言**。
   > 只断结尾的话, 环境没弄成的那些轮次会安安静静地绿着过去。这个形状踩过两次。
4. **新场景写完必须做一次变异验证**: 把被测逻辑改坏, 看着它当场变红, 再改回来。**没红过的场景不算数。**

另外两条: 断言尽量写成**可观测的代价**("这次进房花了几个来回""重拉了几次"), 而不是内部计数器;
`-race` 要**连跑 5 次全绿**, 单跑一次绿说明不了任何事。

### 8.3 值得做一遍的一件事: 独立重写第二遍

用一个独立重写的模拟器把同一套协议再实现一遍(跑真 TCP、能注入网络故障、参数按生产等比缩小,
让 stall 几毫秒就顶满缓冲)。
**它的价值不在"多一份测试", 在于它会用不同的方式把同一个形状实现一遍 —— 形状错了两边对不上。**

### 9.1 D22 展开: 压缩是唯一一处"配错了也完全不报错"的优化

没谈成 / 模式选错 / 阈值调过头 —— **三种情况下功能全都正常, 别的用例全绿, 只是线上字节多几倍**。
应用层永远看到明文, 所以**只能到 TCP 那一层去数字节**(在测试里包一层 `net.Conn`)。

**四关, 一关也不能少(它们互相抓不到对方):**

1. 握手响应头里有 `permessage-deflate`, 且**没有** `no_context_takeover` → 抓"模式配错 / 没开"
2. **(a)** 最热的小帧, **线上字节 <= 明文字节 + 每帧 8 字节的帧头** → 抓"阈值被调小了"
   **(b)** 同一批小帧, 每帧线上字节 <= 64(和 D8 同一个数) → 抓"帧信封长胖了"
3. 一条 5100 字节的大消息, 线上字节 < 明文的 1/5 → 抓"压缩其实没在干活"

**2a 和 2b 必须分成两条**(第一版只写了 2b, 抓不到阈值退化 —— 详见 pushDesignRationale.md R12.1)。

**连带的一条硬纪律:**

> **任何一条带宽账都不许把压缩算进去。D8 那 64 字节必须靠编码本身站住。**
> 压缩一旦顶在前面, 编码退回 JSON 也测不出来 —— 重复几百遍的字段名恰恰是 deflate 最擅长压的东西。
> **所以压缩必须排在编码之后做。顺序反了, D8 就再也没有牙齿。**

**选 ws 库时要确认的一件事**: 能不能**保留压缩上下文**。
有的库把 `client_no_context_takeover` 写死在握手串里、没有开关, 而不保留上下文时每条消息都从空字典开始,
大块 JSON 差一个数量级。

### 9.2 D12 展开: 装不下的时候, 逐个分支确认它走的是"断线"

把两端**所有**"队列/缓冲装不下"的分支找出来(服务端的入队函数、客户端的 pending 缓冲那段),
逐个确认它走的是**关闭连接**, 而**不是**下面任何一条:

* 丢这一帧, 然后记一笔"这个房间要重拉";
* 事后补一帧 `roomResync` / 空的 `NeedFullReload`;
* 给这类"补救帧"单开一笔预算。

**有任何一条 = 不通过。** 理由和历史见 §4.4。

> **反向检查同样重要**: 降级信息如果是**搭在正常应答上的一个字段**(`NeedFullReload`), 那它是合法的,
> **别顺手把它也改成断线**。
> **判据是"这一帧被队列丢掉时谁来收敛", 不是"它是不是叫降级"。**
> 搭在应答上的那个字段和快照同一帧, 丢不掉 —— 所以它不需要断线; 而任何**单独发的**降级帧一律不许存在。

### 9.3 D23 展开: 逐字段问两句

打开组装推送数据那个函数, 对推下去的**每一个**字段问:

**(a) 推送这一侧谁读它?**
找不到读它的代码, 它就不该进这条路 —— **直接在这里清掉**, 全量拉取那条路照常给全。
注意"前端把它赋值给了某个变量"**不算读**: 要找的是**用它渲染或做判断**的地方。

**(b) 它的大小谁说了算?**
用户能决定大小的字段(输入框内容 / 用户填的文本 / 可粘贴的任何东西),
**要么不进推送, 要么必须落在某个客户端游标里** —— 否则它会把进房应答顶过上限,
变成 §3.4 推论二那个死循环。

**两句里 (b) 比 (a) 硬:**

* 只犯 (a) = **白烧带宽**。真实数字: 一个"最后活跃时间"字段(每批变更都跟着变, 而推送侧没人读)
  一度占了 77% 的推送量。
* 同时犯 (a)(b) = **永不收敛且完全静默**的死循环(§3.4 推论二那个草稿字段)。

**这条和 D8 是一对**: D8 管**信封**(每帧固定开销), D23 管**负载**(每个业务字段该不该在这)。
类三那一桶尤其要盯: 它是"整份覆盖", 所以桶里任何一个字段变胖, 代价都乘上"这一桶发了多少帧"。

场景怎么写: 让那个用户可控的字段大到超过单次进房应答上限, 然后断言
**两次进房都不许 `NeedFullReload`** —— 第二次那条钉的就是死循环
(那个房间没有别的内容, 客户端能申报的游标一个字节都没变);
再断言纯改那个字段时一帧都收不到。**做一次变异验证**(把清空那行去掉, 看它当场变红)。


## 10. 明确不做的清单

**这些不是"暂时没做", 是"做了会更糟"。** 每条注明它省掉了哪一类状态。

| 不做 | 省掉了什么 |
| --- | --- |
| 反馈式窗口 / 阻塞流控 | 一整套窗口状态机 + 队头阻塞(一个弱网页面拖住整个房间)这一类故障 |
| 把"装不下就断线"改回"**丢帧但留着连接**" | 一整条修补链(补救帧 → 给它单开一笔预算 → 预算算不出来 → 按房间去重 → 去重会漏所以客户端不能按 id 丢), 以及一堆只在灾难时才走、因而**永远测不到**的跨帧状态。<br>想加回来之前先回答一句: 那一帧"我丢过东西"**自己**被丢掉时, 谁来收敛?(§4.4) |
| 无界队列("那就别让它装不下") | OOM。内存有硬上界, 代价只是让那**一条**连接重连一次 |
| 反馈式确认 / 服务端为每条连接记"你收到哪一帧了" | 一整套按连接的进度状态。内存上界靠的是"装不下就断", 不是靠记账 |
| **给 `NeedFullReload` 加第二种含义** | 客户端"收到它之后到底该做哪个动作"的分叉, 以及每个新动作各自的收敛证明。<br>它就是"这次应答太大, 你走 http 拉一次", 到此为止。想表达别的, 去 §7 那三组里找对应的那条路(§3.4) |
| **往进房应答里加"大小由用户决定、又不在任何游标里"的字段** | §3.4 推论二那个**完全静默**的死循环(界面正常, 只是每 5 秒白烧一次全量拉取)。查法见 §9.3 |
| **轮询兜底**(在推送之外再挂一层"定期拉一次防止漏") | 一条**永远不会被测到**的并行路径 + 常驻开销换一个概率性的好处。正确的替代是把失效场景写成自动化测试。<br>**注意和 §2.1 的 2b(b) 不是一回事**: 那里轮询是某一桶**唯一的**取数路径(走通走不通都看得见), 这里是**并行的第二条**路径(它专门用来掩盖第一条的 bug) |
| 服务端为每条连接存正文游标 | "这份游标什么时候过期"的一整类新问题 + O(连接数) 常驻内存。客户端本来就免费知道自己的偏移 |
| 给合并加定时器 | 一个需要调的旋钮 + 一个延时/带宽的取舍(§4.3) |
| 反过来把合并去掉("为了更实时") | 同上 |
| 为了"快照要原子"搞跨库事务 / 全局版本表 / 每条数据加版本列 | 一整套分布式事务。收敛靠的是"下一次重读一定会来", 不是"这一次读得完美" |
| **再给房间加一把锁**(任何名字任何粒度) | §1.2 并发目标的全部收益 |
| 把各桶的 id 合并回一个 | 一把包住 DB IO 的锁 + 可诊断性(一桶判错会表现成"整个房间不收敛") |
| 给类三做**全桶字段级差量** | 一把锁 + "号必须连续"这一整类判断(幂等没了) |
| 无序集合按 key 版本 + 墓碑 | "删除怎么表示"这一整类问题。小集合整份走类三更便宜 |
| protobuf / 定长数组编码 | schema / 代码生成 / 前端 runtime / "未知键忽略"这条可升级性(体积上打平) |
| 让常驻 goroutine "起得来停不下" | 一整类只在关闭时出现、且只有 `-race` 才抓得到的竞争 |
| **统一形状** | (反过来的一条: **拒绝一种假的简单性**) |

最后一行值得单独说, 因为它是唯一一条反直觉的:
"所有数据走同一套 id 机制"看起来更简单, 但它**换来的是一把包住 DB IO 的锁**,
以及"一桶判错表现成整个房间不收敛"的不可诊断性。
**那不是简单, 那是把复杂度藏进了一个更糟的位置。**
